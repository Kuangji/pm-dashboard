# Input v0：内容监控 AI 项目解读（v7.6.2）

> 阶段：`input_v0_review`
> 版本：`v7.6.2`（短写 `762`）
> 日期：2026-08-20
> 立项结论：**必须开版本**
> 首期路线：**方案 B「证据型 AI 项目解读报告」**
> 下游顺序：`input -> spec -> design -> prd`
> 本文性质：供产品、设计、前端、后端、数据、AI、计费和 QA 评审的输入，不是最终 PRD 或接口承诺。

## 0. 一句话定义

在内容监控项目的数据看板中，用户按当前项目、筛选和观察区间发起一次分析；系统先冻结可审计的确定性事实包，再生成一份与频道/品牌 AI 报告心智统一的中文 AI 解读，并把每条主要判断回链到原始内容、频道、标签或数据状态。

确定性项目摘要是报告的事实骨架，可以独立解释数据范围和限制；它**不能**替代通过数据门槛后的生成式 AI 文案，也不能被前端包装成 AI 成功结果。

## 1. 版本定位与决策前提

### 1.1 为什么现在开 v7.6.2

**[事实]** v7.6.1 已将内容监控的项目、观察区间、数据看板、变化榜、趋势、达人/频道贡献和标签贡献等底座收敛到项目工作台；其 Input 明确把“报告系统/AI 分析”留在后续范围。

**[事实]** 当前线上内容监控已经有可用于解释的真实数据入口，但没有专属 AI 入口。已有页面可看到项目摘要、趋势、Top 内容、频道贡献、标签贡献和任务状态。

**[事实]** 频道详情和品牌监控已经建立用户熟悉的“AI 读取数据并给出解释”的心智，但两个实现的流式、字段和证据能力不一致；它们可以提供体验参考，不能直接复制 schema。

**[用户决策]** 本版本不是可行性探索或是否立项评估，而是把已确认的 B 方案整理为可拉人评审的正式 Input。是否进入研发仍由后续 Gate、数据补证和 PRD 评审决定。

### 1.2 版本不做的事情

- 不把 v7.6.1 的既有数据看板重写成新的分析产品。
- 不把品牌 AI 的三栏文本或频道 AI 的达人合作报告直接套到项目内容。
- 不先建设独立的报告中心、聊天 Copilot、订阅通知或自动动作。
- 不用固定模板句伪装“AI 已生成”。

### 1.3 本版本成功的最小定义

在一个有足够数据且用户有权限的 scope 上：

1. 用户能在数据看板中按需发起 AI 项目解读；
2. 返回结果同时包含确定性事实摘要和非空生成式中文文案；
3. 主要主张可以打开依据，回到现有内容/频道/标签/数据状态页面；
4. 事实不足、权限失败、过期或生成失败时，状态和降级说明明确，不输出伪造结论；
5. 结果不会因为筛选、观察区间或权限变化而错误复用。

### 2.3 实现与线上 AI 参考

**[事实]** 频道 AI 目前使用 EventSource 状态机和额度预检；品牌 AI 前端是一次性 GET/Vuex，缺少前端可审计的 evidence、metric refs、模型/Prompt 版本、重试/反馈等字段。

**[事实]** 线上品牌 AI 样本存在空文本列、密集长文、原始指标暴露且没有证据按钮；这应作为 v7.6.2 的质量反例，而不是视觉参考。

**[建议]** v7.6.2 可以复用“统一 AI 工作面、生成状态、额度/权限状态和折叠展开的心智”，但应为内容监控建立独立的事实与证据契约。

### 2.4 尚不能由当前证据证明的事实

- 当前监控数据是否固定按日/小时采集。
- 是否存在可稳定重放的 baseline、snapshot ID、freshness、coverage 或 metric version。
- 线上 AI 服务是否预计算、缓存、单独扣点或有专属配额。
- 服务端是否能在重放缓存时重新校验项目/内容/协作者权限。
- 评论、视频画面、字幕、ASR/OCR 是否足以支持项目级内容语义理解。

这些项目必须留在 `[待确认]`，不能在生成文案中变成确定语气。

## 3. 用户与任务

### 3.1 目标用户

| 用户 | 触发时机 | 需要完成的任务 |
| --- | --- | --- |
| 品牌/营销负责人 | 周期复盘、客户汇报 | 快速说清本期变化和主要贡献 |
| 内容监控运营 | 日常查看项目 | 找出值得复盘的内容/频道/标签 |
| 代理商/协作者 | 接手或共享项目 | 根据证据继续核查，不靠口头转述 |

### 3.2 核心 JTBD

> 当我打开一个内容监控项目并选择观察区间时，我希望不用逐个翻图表，就能知道本期发生了什么、变化集中在哪些对象、数据有哪些限制，并一键打开原始依据继续复盘。

### 3.3 非目标任务

- 不回答“这次增长的真正原因是什么”。
- 不回答“这批内容带来了多少销售/ROI”。
- 不替用户判断视频创意质量或评论总体情绪。
- 不替用户执行改规则、分派任务、发送通知等动作。

## 4. 候选方向与路线选择

| 路线 | 形态 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- | --- |
| A 纯确定性摘要 | 规则/模板生成项目变化摘要 | 快、可控、易解释 | 无法满足“生成式 AI 文案”前提，和已有 AI 心智不统一 | 不作为首期主路线 |
| B 证据型 AI 项目解读 | 确定性事实包 + LLM 结构化文案 + 证据回链 | 满足立项前提；可审计；能和现有 AI 报告统一 | 需要事实聚合、校验、权限、成本一起建设 | **首期采用** |
| C 自由问答/项目 Copilot | 用户围绕项目自由追问 | 想象空间大、后续可扩展 | scope 难冻结；容易无证据推理；成本和权限复杂 | V1 明确 Out |

### 4.1 为什么选 B

1. 它保留确定性数据能力，先让用户看到“系统依据什么说”。
2. 它能在成功结果中明确交付生成式中文文案，而不是把模板摘要换个标题。
3. 它比自由问答更容易冻结 scope、定义质量门和做权限审计。
4. 它为后续“追问某个异常/生成客户简报”留下结构化 claim/evidence 基础。

### 4.2 B 方案的亮点候选

以下是可在评审中保留的差异化方向，均以事实包和证据为前提：

- **项目脉搏**：把本期变化、集中度和数据健康放在一句“发生了什么”里，而不是只给指标。
- **贡献者相对基线**：后续若服务端能提供可信 baseline，再比较频道/内容的相对贡献；当前只做观察期内贡献，不假装有基线。
- **内容生命周期解释**：后续可按新发布、持续增长、衰减、长期稳定等确定性状态组织复盘；当前不把离散点自动命名为生命周期，需先确认口径。
- **证据优先追问**：未来允许用户从某条 claim 继续问“依据哪几条内容”，而不是开放无边界聊天。
- **支持样本与反例样本**：当数据足够时，同时展示贡献内容和未贡献/下降内容，避免只用 Top10 写出单向叙事。

这些是 `[建议]`，不等同于 v7.6.2 Must；Input 评审需要决定哪些留在首期。

## 5. 首期产品假设

### 5.1 入口与触发

**[建议]** 入口放在内容监控详情页的 `数据看板`，靠近观察区间概览；建议名称为 `AI项目解读`。不在项目列表自动生成，不在进入页面时自动扣额。

**[建议]** 默认分析范围显示在入口附近：`项目名称 · 当前筛选 · 观察区间`。分页和排序只影响展示；筛选或观察区间改变后，旧报告标记为 `已过期`。

**[待确认]** 入口是否受现有品牌/频道 AI 权限、内容监控套餐、团队额度或单独 quota 控制；需要服务端确认 entitlement 与扣点规则。

### 5.2 生成中

建议使用与其他 AI 功能统一的任务感知状态：

1. `正在整理项目数据`；
2. `正在生成项目解读`；
3. `正在核对解读依据`。

不虚构百分比进度。若服务端使用 SSE，可复用频道的状态机思路；若使用普通请求，也必须有可取消/过期/重试语义，避免旧结果覆盖新筛选。

### 5.3 成功报告骨架

报告是数据看板顶部的独立工作面，不新增独立 AI 首页，也不把多个卡片嵌套成卡片：

```text
项目 AI 解读                         [刷新] [收起]
范围：项目 · 当前筛选 · 观察区间      数据截至：时间/状态

事实摘要条：观看增量 | 互动增量 | 互动率变化 | 活跃内容 | 可见内容

本期核心解读
  生成式主张 · 查看依据

主要贡献与机会
  内容/频道/标签主张 · 查看依据

风险与建议动作
  数据缺口/复盘建议 · 查看依据或打开筛选

数据范围与限制                         [查看详情]
```

**[硬条件]** 三个正文区至少有一个非空生成式 section，且返回明确 `generationMode=llm`；事实摘要条可由确定性计算提供，但不能让它代替正文。

### 5.4 证据回链

每条主要 claim 提供 `查看依据`，打开证据抽屉或带筛选条件的现有列表/详情。证据至少包括：来源类型、对象名称或 ID、指标、观察时间、数据状态、回链动作。

证据抽屉不复制完整数据表，也不允许只有模型解释而没有原始对象。

### 5.5 用户动作

首期建议提供：

- 收起/展开；
- 重新生成当前 scope；
- 查看依据；
- 打开内容、频道、标签筛选或数据问题筛选。

复制、反馈、保存简报、订阅通知、自动分派暂不列为 Must；若统一 AI 框架已有能力，可在 Spec 阶段评估复用。

## 6. 数据输入与事实包

### 6.1 最小输入范围

```json
{
  "projectIds": ["当前用户有权访问的项目"],
  "filters": "当前已生效的内容资格筛选",
  "observationWindow": {
    "start": "timestamp",
    "end": "timestamp",
    "timezone": "页面/服务端确认的时区"
  },
  "requestContext": {
    "accountId": "服务端获取",
    "authorizationFingerprint": "服务端生成"
  }
}
```

### 6.2 可纳入事实包的字段

| 事实组 | 首期表达 | 依赖/限制 |
| --- | --- | --- |
| 范围 | 项目、平台、筛选、观察区间、内容数量 | 必须能回显冻结后的 scope |
| 变化 | 观看、互动、互动率、活跃内容的增量/变化 | 需明确分母和空值规则 |
| 趋势 | 返回数据点的升降和集中时点 | 不宣称固定采样频率 |
| Top 内容 | 当前值、增量、作者、发布日期 | 必须标明 Top/可见范围，不能代表全量 |
| 频道贡献 | 内容量、增量、贡献率 | 只描述项目内相关性，不做因果 |
| 标签贡献 | 标签内容量、增量、贡献率/分布 | 依赖当前筛选和标签口径 |
| 数据健康 | 短链、预算、评论样本等缺口 | 缺失不等于真实值为 0 |

### 6.3 事实包必须带的元数据

**[建议]** 服务端输出以下元数据，前端不自行拼接：

- `snapshotId`、`generatedAt`、`dataAsOf`；
- `baselineStatus`（`available/unknown/not_applicable`）；
- `coverage`、`eligibleContentCount`、`missing`、`reasonCodes`；
- `metricVersion`、`schemaVersion`；
- `authorizationFingerprint` 对应的缓存隔离信息。

**[待确认]** 当前服务是否已具备这些字段；如果暂时不能提供，报告必须显式显示“数据口径/截至时间待确认”，而不是补写固定值。

## 7. 生成式输出契约（输入级提案）

### 7.1 顶层状态

```json
{
  "analysisId": "string",
  "status": "success|partial|insufficient|permission|stale|error",
  "generationMode": "llm",
  "schemaVersion": "content-monitor-ai-v1",
  "scope": {},
  "snapshot": {},
  "dataHealth": {},
  "factSummary": {},
  "sections": [],
  "evidence": []
}
```

成功态硬条件：`generationMode=llm` 且至少一个正文 section 有非空生成式文本；不能由前端依据“字符串非空”推断。

### 7.2 Section 与 Claim

```json
{
  "sectionId": "core-insights|contribution-opportunities|risks-actions",
  "title": "本期核心解读",
  "claims": [
    {
      "claimId": "string",
      "claimType": "fact|association|interpretation|action|gap",
      "text": "生成式中文文案",
      "metricRefs": ["fact.viewsDelta"],
      "entityRefs": ["task:...", "channel:..."],
      "evidenceIds": ["evidence-1"],
      "support": "supported|qualified|not_supported",
      "actionLinks": []
    }
  ]
}
```

规则：

- `fact` 可以直接陈述事实包中的值；
- `association`/`interpretation` 必须用“与……同时出现”“可能反映”“建议核查”等限定语；
- `action` 只能连接现有页面或筛选，不直接执行写操作；
- `gap` 必须说明缺口对结论的影响；
- `not_supported` 不渲染为确定性结论。

### 7.3 示例文案（仅用于评审风格）

> 本观察期项目新增观看 16.64 万、互动 1,074 次，共有 392 条内容产生数据变化。增长较为集中：Fubgun 贡献了 36.2% 的新增观看，Top10 内容合计约占本期新增观看的 38.4%。建议先复盘 Fubgun 的上榜内容，再判断这种表现是否能在其他频道中复现。当前项目 454 条内容均未配置短链和预算，因此本次解读不判断转化或投入产出。

这段文字只示意“事实 + 限定解释 + 动作 + 限制”的结构；数字来自一次样本，生产结果不得写死，也不得把“集中”升级为“原因”。

## 8. 允许、禁止与降级

### 8.1 允许的首期解读

- 描述观察期内的变化、趋势、集中度和贡献对象；
- 从事实包中选取少量优先复盘对象；
- 将数据缺口解释为“本次结论的限制”；
- 给出打开原始对象、补充配置、继续筛选的建议动作；
- 在证据不足时使用限定词并主动说明未知。

### 8.2 首期禁止的解读

- 因果归因、确定性的爆发原因、策略效果结论；
- “实时”“每天采集”“全量覆盖”等未经证明的时效/覆盖承诺；
- 从 Top10 外推全项目；从频道贡献率推断因果影响；
- 把短链/预算缺失写成转化为 0；
- 把评论样本不足写成项目级舆情；
- ROI、销售、成本回报、投放归因；
- 视频创意、画面、字幕、ASR/OCR 和多模态理解；
- 事实包之外的数字、实体、时间、基线或比较对象。

### 8.3 状态降级

| 状态 | 可展示内容 | 不可展示内容 |
| --- | --- | --- |
| `success` | 事实摘要 + 非空生成式文案 + 证据 | 无证据确定结论 |
| `partial` | 可用 section、缺口和限制 | 把缺失 section 补成模板结论 |
| `insufficient` | 确定性范围/缺口说明 | 声称已完成 AI 解读 |
| `permission` | 无敏感数据的权限提示 | 暴露缓存报告或证据对象 |
| `stale` | 过期原因、刷新入口 | 静默沿用旧 scope |
| `error` | 可重试、错误原因和 analysisId | 伪造摘要或吞掉失败 |

## 9. 首期范围分级

### Must：进入 v7.6.2 首期闭环

- 单项目、当前内容资格筛选、一个观察区间的 scope 冻结。
- 数据看板按需生成入口，不自动生成、不默认扣额。
- 确定性事实摘要：范围、变化、Top 内容、频道/标签贡献、数据缺口。
- 至少三个报告主题：本期核心解读、主要贡献与机会、风险与建议动作。
- 成功态包含 `generationMode=llm` 和非空生成式中文文案。
- claim 到 metric/entity/evidence 的结构化绑定。
- 查看依据能回到现有内容、频道、标签或数据问题入口。
- 生成中、成功、部分、数据不足、权限、过期、错误状态。
- 筛选/区间变化后的旧结果失效或明确标记过期。
- 服务端权限校验和缓存按授权指纹隔离（具体实现待确认）。

### Should：Input 通过后评估是否纳入

- 重新生成当前 scope；
- 统一 AI 报告的复制/反馈动作；
- 证据抽屉展示支持样本与反例样本；
- 生成耗时、数据截至时间和数据健康摘要；
- 可选的 SSE 阶段状态；
- 支持项目内多个平台的统一叙事，而不是分平台割裂报告。

### Out：明确不进入 v7.6.2

- 跨项目比较、管理层周期简报；
- 自由问答/聊天式 Copilot；
- 主动通知、订阅、保存 brief；
- 自动改规则、自动分派或外部执行；
- 因果、ROI、实时告警；
- 项目级评论舆情、ASR/OCR、视频创意/多模态理解；
- 独立 PDF/图片报告系统。

## 10. 质量、权限与成本假设

### 10.1 质量门（建议在 Spec 固化）

| 质量项 | 首期门槛建议 | 备注 |
| --- | --- | --- |
| 生成条件 | 成功结果 `generationMode=llm` 且正文非空 | 硬门槛 |
| 数字/实体一致性 | 离线评估不低于 95% | 需定义样本和容错 |
| 证据有效性 | 不低于 95% | 深链、对象和指标均核对 |
| 高风险因果主张 | 0 | 发现即阻断或改为限定语 |
| 越界实体/数字 | 0 | 不能出现事实包之外信息 |
| 状态覆盖 | 6 类状态均有可验证样例 | 不能只测成功态 |
| 权限重放 | 无越权返回 | 需含项目/协作者变化场景 |

这些是 `[建议]` 验收门，不是已测结果；评审需确认可执行的离线和线上测试方式。

### 10.2 权限、额度、缓存

**[待确认]** 必须由服务端/计费共同确认：

- 使用现有 AI 权限还是内容监控专属 entitlement；
- 生成请求是否扣点、重复 scope 是否复用且不重复扣点；
- 缓存 key 是否包含账号/团队/授权指纹、项目、标准化筛选、观察区间、snapshot、schema version；
- 权限收回、项目归档、内容删除后，缓存是否立即失效；
- 失败、部分和过期请求是否计费；
- 首期延迟和成本上限，以及超时后的可解释状态。

### 10.3 服务端边界

建议由服务端聚合器/BFF 冻结 scope 并读取现有 monitor API 族，流程为：

```text
scope/权限冻结
  -> 事实聚合
  -> 数据健康门
  -> 结构化 LLM 生成
  -> claim/数字/证据校验
  -> 缓存与审计
  -> 前端渲染和 deep link
```

**[待确认]** 新 endpoint 家族路径、同步/流式协议、model/Prompt/schema 版本、审计字段和失败重试由技术评审确认。现有频道 SSE 只能复用状态机思路，不能直接复用达人报告 schema。
