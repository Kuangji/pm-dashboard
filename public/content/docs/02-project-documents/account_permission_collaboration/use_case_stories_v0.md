## 阅读方式

先读八章故事，再按需查规则和 Demo。每个故事都说明谁为什么操作、操作发生在哪一类页面、系统如何响应，以及结束后留下什么状态。

- **规则已定**：故事主规则已确认；界面和技术细节仍可能留给 Spec。
- **含待定分支**：已定部分可以读到结果，未定部分停在明确的问题上，不替团队补结论。
- **范围待裁决**：记录需求目标和决策点，不假装已有可执行流程。
- **一期接收/回归**：需接收交付证据，不把规划前提描述为已上线事实。

当前覆盖对象是已有 Input、梳理文档及 Demo 元数据中可识别的场景，共 8 章、43 个故事及 16 条导出子场景，不宣称穷尽未来所有真实用户行为。故事编号用于回溯，保留历史缺号、不顺延，不代表优先级或分期。

## 第一章：开始使用

<a id="S01"></a>
### S01 老客户上线后照常工作
**状态：一期接收/回归。区域：后台初始化，用户原业务页面。**

小陈所在企业尚未使用新分组。底层替换生效时，系统初始化真实默认组、有效成员关系及已接入对象归属，小陈不需要先走迁移向导才能继续工作。

存量原monitor/creator两类字典及已有打标关系一并由默认组承接，无需用户重新打标；旧创建人/创建时组缺失仍标未知，不伪造。真实一期归组与关系保留必须验收，不把默认组初始化当开放项目迁组。

原负责人、协作、附加能力、有效额度和历史访问须按迁移方案保留；组长默认协作仍默认关闭，不因默认组里新增 T2 扩大权限。CRM 旧分组设置暂定弃用但历史记录初始归组仍须设计；四项写设置继续生效并限制在记录组，不能把旧组、权限来源和自定义视图混为一谈。正式支付单旧宽写不能迁成协作授权。存量有支付权限组织的默认组上线自动开通、共享组织尚未分配的可用资金，不另划专用余额、不动其他组专用款；后续充值直接增共享可用。旧承诺仍按原账路、不重绑周期或重复扣款；其他/新建组专用资金照常。该迁移例外已定，真实映射和对账须验收，不把 Demo 预置值当已部署证明。异常初始化、未覆盖对象进入接收清单，不报作“已完成”。

**核对：** Input §2、§4；议题 25、N10。Demo：业务组及各模块；迁移是否真实交付须另验。

<a id="S02"></a>
### S02 个人账号第一次建立企业
**状态：规则已定，建企业及付费交互留给 Spec。区域：个人/付费入口、组织管理。**

小赵新注册时没有企业关系。他可以自行付费建立企业，也可以选择接受现有企业邀请，而不是注册就自动生成一份企业业务空间。建立企业后，组织是独立实体，有唯一 Owner，并具备开展业务所需的初始组与成员关系。

个人账号不等于某个企业的别名；后续企业到期、清退或注销要分别判断，不能都解释为删除登录账号。

**核对：** Input §5.3–§5.4；议题 N1。Demo：仅有成员与组织概念说明，未演示注册/付费建企业。

<a id="S03"></a>
### S03 邀请新人并让他具备工作条件
**状态：规则已定。区域：组织管理 → 组织成员；成员额度后续进入本组管理 → 成员与配额。**

周总搜索并确认邀请邮箱，发出邀请，小赵接受后才取得有效成员关系。邀请与入组只处理组织/组关系及业务身份，不提供个人额度输入；新关系的可分配 Scope 默认 inherit，支付账号上限默认 unlimited，后续由本组组长在委派开关允许时逐项配置。不引入岗位权限包或分组默认模板；不可分配权益随组织状态。

邀请只由 Owner/Admin 发起，组长不能邀请。表单可选择首组，默认选择始终存在且有效的默认组；小赵接受后建立所选组的成员关系。默认组不可归档。组长后续按需调额度，不把人工填写额度当成邀请步骤。

**核对：** Input §5、§8；议题 1、2、3、11，D03/D04 已确认。Demo：组织成员，邀请可选首组、默认默认组；只有 Owner/Admin 有邀请入口。

<a id="S04"></a>
### S04 邀请尚未接受，席位或配置已经变化
**状态：规则已定，已有席位/提示需回归。区域：组织管理 → 组织成员。**

邀请发出后，企业席位已满，或管理员希望撤销邀请。系统在邀请前、提交和接受时检查资格与席位，不能让旧邀请绕过当前上限；撤销后不能继续凭原邀请加入。验证邮件和错误提示应说明当前问题与处理方向。

待接受期间不提供修改目标组或身份的入口；需要调整时撤销后重新邀请，原邀请不能再接受。接受时重验目标组当前有效状态与席位资格，不在邀请中修改个人额度。昵称/邮箱搜索只帮助定位候选，不扩大可邀请、可管理或可协作范围。

**核对：** 议题 2、11，D04；一期已有提示需回归。Demo：组织成员。

## 第二章：把团队组织起来

<a id="S05"></a>
### S05 先建空组，再把人安排进去
**状态：规则已定。区域：组织管理 → 业务组。**

周总准备成立乙部门，先创建乙组、填写组名，暂时不加成员。之后由周总或有权 Admin 加入成员、配置 T2/T3，不在成员表单设置个人额度。每组可以有 0..N 名 T2，不要求先找一名组长才能建组，也不设置首席 T2；若要调整成员额度但暂无组长，先任命组长再由其配置，不能管理员越级。

乙组初始没有项目和两类标签，不从默认组或其他组自动复制。组织Owner/Admin在“业务组”选择乙组后，可在组策略分别配置达人/监控标签定义限制，两开关默认关闭；配置策略不等于可跨组维护定义，后者仍须乙组有效身份。

后续维护时，有权组织管理者可在组管理中修改组名、任命或解除 T2。改名不改变组 ID 和对象归属；身份变化后，动态 T2 协作来源按新身份重算，不能连带删除独立显式授权。

组织管理者进入“业务组”，同页选择目标组，再切“成员与身份 / 组配额 / 组策略”三个平级 Tab；添加成员及任免位于成员行，改名、冻结归档位于组标题旁操作菜单，不再进入第二层管理页或返回组列表。在“组配额”查看组织约束、组已用和实际可用，打开编辑窗口设置组上限；保存后留在当前目标组及 Tab 核对。管理目标组不改变顶部业务工作组，也不因此开放个人额度编辑。

组长不因业务身份取得邀请、加人、移出或任免组身份的权限；2026-11-04 已收回此前允许组长主动移出组员的结论。人员决定在组织侧，组长只处理本组业务交接，不撤销人员移除，也不操作其他组。Admin 全组织管理，不设置逐人的管理组范围；发起成员移出须满足对应 Owner-only 开关。

**核对：** Input §3、§5；议题 1、3、N1，D01/D02。Demo：业务组；本组管理另承接本组业务，不重复人员治理入口。

<a id="S06"></a>
### S06 任命 Admin，但不把业务项目全部交给他
**状态：管理范围及两个敏感动作开关已定，完整管理动作矩阵汇总后统一讨论。区域：组织管理 → 组织成员、全局策略。**

周总任命林经理为 Admin。任命改变组织管理身份，不改林经理在甲组的 T3 身份，不自动把他加入其他组，也不授予邮件、CRM 或支付对象权限。

Admin 采用全组织管理，可邀请成员、创建组，不配置逐人的管理组范围或重叠范围。周总在组织策略里决定是否允许 Admin 移出成员、是否允许 Admin 归档业务组；两个开关仅 Owner 可配置、默认关闭，Admin 不能自行开启。成员移除开关同时约束 Admin 发起组织/单组移出、撤销未完成单组移除、组织侧确认无业务项的关系结束，不能换入口绕过；有效组长处理既有本组业务交接不受影响。Owner 不受这两个开关限制，默认组仍不可归档。汇总查看与项目明细访问始终区分；其余敏感动作继续按动作矩阵收口。

矩阵统一讨论时须同时核对资金汇总与单据明细的授权差别、普通成员可见的组配额范围；当前未补齐不等于默认全开，也不重开已经确认的组织/业务权限分离、组长资格和配额配置分工，不另设一套角色配置。

**核对：** 议题 1、16、N1，D01/D02。Demo：组织成员、全局策略。

<a id="S07"></a>
### S07 同一个人参与多个部门，切换工作组
**状态：规则已定。区域：全局当前组入口、具体业务模块。**

小李上午处理甲组项目，下午切到乙组。切组后，列表、候选协作者、新建对象和无对象业务消耗使用乙组上下文；小李在甲乙两组的身份与额度可不同。

已存在的项目不随切组搬家。通知或外部链接指向另一组对象时，先说明目标组并显式切换；有未保存内容时需告警。组织策略、组织钱包和全组织汇总等页面不跟随当前组伪装成组级设置。没有有效组关系时不能靠切换器进入该组。

**核对：** 议题 1、24。Demo：全局业务组切换及各业务模块。

<a id="S08"></a>
### S08 加入新组，先不搬走原来的项目
**状态：规则已定。区域：组织管理 → 组织成员、业务组 → 成员与身份。**

周总把小陈加入乙组，确认乙组身份；新关系配额默认值及后续组长配置不变。小陈可保留甲组关系，但甲组项目、CRM记录和两类标签始终留甲组，在乙组从空业务开始，不因为同一个人入组就复制。

本期不提供入组迁移选项，也不询问是否整批搬项目；独立迁组入口同样取消。S34保留编号仅说明边界，不是下一步操作。同组Owner交接和清退业务移交照常，不跨组搬项目或标签。

**核对：** 议题3/24；26本期已裁剪。Demo：组织成员/业务组只加关系，S34说明无项目迁组。

## 第三章：配置工作条件

<a id="S09"></a>
### S09 给组和成员设置可使用的额度
**状态：配置层级已定，普通Scope特殊项评审时确认。区域：组织管理 → 业务组 → 组配额配置组上限；本组管理 → 成员与配额配置成员额度。**

周总先查看组织实际权益，仅为甲组设置各可分配 Scope 的组上限；本组张组长在全局 t2Quota 开关允许时，逐 Scope 为自己及同组成员设置 inherit 或 capped。周总若不是甲组有效 T2，不能代张组长配置小陈额度；兼任组长时也必须满足同一开关。无组长则先任命，不设组织管理越级兜底。inherit 是不追加这一层限制、使用父级共享额度，不是无限供应；组本身也可继承父级。

周总在“业务组”同页选目标组，切“组配额”打开编辑窗口，按项核对组织上限及剩余、本组原上限、当前周期已消耗，并预览新值的影响。常用数值集中展示，详细规则可展开查看；保存后停留当前组的组配额 Tab。以组邮件上限 6000、已消耗 1400 为例，改为 1000 后允许保存，但须确认用量仍为 1400、可用量为 0，将阻止继续消耗；改为 2000 时，本组自身余量为 600，实际可用还须取与组织剩余的较小值。修改上限不是重置周期、返还消耗或变更历史。

若现有某成员的 capped 上限高于新组上限，不由组织管理者自动代改；该成员实际使用受父级组额度拦截，后续由组长调整。普通组上限可上调、下调或改回 inherit；支付金额不使用普通额度编辑，另走组专用余额的追加分配和未承诺余额归还。各 Scope 的计量单位与周期各自独立，年度父额度下新增月度子级预算本期不做，留后续 TODO。

没有统一的模块禁用开关；有的能力受额度控制，有的仍是套餐门禁或其他 Scope 类型，不能把所有功能改成一个数值框。额度为零阻止对应消耗，不删除已有对象授权。支付金额另走 S25，不能套用普通额度的超配规则。

收藏夹要分开看：数量 Scope 31 按现有普通配额逻辑；Scope 32 是全局统一单夹容量，不下分组/个人，也不是每次收藏扣一次，但夹内容量仍须拦截。收藏夹内新解锁邮箱 Scope 4、WhatsApp Scope 59 按操作者，组织历史解锁可复用，删条目或夹不返还解锁次数。数量/容量用尽不撤销已有读取；配额与已确认三模式/Owner 治理分开判断，Demo 不实现真实配额或解锁。

内容监控也不套统一次数消费：Scope24 沿用时长折算和会员周期，常规个人用量按当前项目 creator 归集；56按网红记录 creator、状态和到期条件计席位，用户主动暂停8释放、其他暂停6仍可占位，释放56不自动退24。65是套餐天数，25/33是能力资格，不变成组员可分配次数；规则并行数和INS日限继续独立。按已确认组边界叠加约束，不改变原核算主体，映射与预检差异仍由研发核对。

Demo 中，组配额与组内个人配额均同时排列“邮件发送”“搜索次数”“频道详情页解锁次数”，每项独立选择不追加上限或设置上限，展示对应单位、已用、父级约束及保存后实际可用；可一次保存多项，某项无效时整次不保存。“本组管理 → 成员与配额”保留成员行配置、逐 Scope 用量矩阵和批量操作，不另设组员配额导航，也不因页面合并削减内容。样例数值及统一月周期仅用于审阅共存、排列与交互，不确认全量 Scope 映射或发放周期；搜索次数与不可分配的搜索频率不混用。邮件额度保留配置与已用展示，查看核算说明，不通过通用“消耗”按钮模拟从当前操作人扣量；其他示例消耗不代表邮件链路。

周总或Admin在“业务组”同页选择甲组，于“组策略”开启支付组长审核；默认关闭，不继承组织默认值。甲组组长在“本组管理 → 本组策略”只读查看，支付模块保留规则摘要和有权者的设置跳转，不保留第二个编辑开关。组织管理者配置策略不要求当前业务组是甲组，也不因此获得甲组支付单明细或审核执行权。立即付款在系统审核后等任一有效 T2；手动付款在支付者放行后等 T2；预约付款在系统审核后、预约时间前完成预审核。逾期不能因迟到审核突然恢复自动转账，要走重新预约、转立即或作废的既定处理。

多个组长任一人放行即可；到达闸门时，实际提交人是同组有效 T2 则豁免。闸门当下没有任何有效组长时自动跳过组长审核，只跳过这一层，不跳系统审核、资金或支付执行资格。列表提供“待我放行”、预约提示，跨组通知可引导切组，不建跨组审批工作台。策略实时影响尚未转账的单，不做创建时快照隔离。

**Spec／研发边界：** 实时审核和无有效组长自动跳过已定，不再作为产品选择点；等待单如何随实时策略推进、重新预约/关键变更、并发及历史订单接入仍须细化验收。T2 审核权不等于 Collaborator 或 can_execute_payment，D11 保留工程边界而非重开已定规则。

**核对：** 议题 N5，D11。Demo：业务组 → 组策略、本组管理 → 本组策略、跨境支付。开启目标组审核后，该组已预约样例进入待预审核；尚未审核时点击“模拟到达预约时点”会进入逾期，阻止补审及自动转账，保留资金占用，可作废。真实时钟、系统审核和待定状态分支不在示意范围；本地步骤不等于三种支付路径的完整验收。

<a id="S29"></a>
### S29 根据创作者快速选用历史收款信息
**状态：组织共享快捷模板及维护范围已定。区域：跨境支付 → 创建付款、频道收款信息。**

在已开通支付的组内，小陈填写创作者频道后检索本组织该频道历史收款记录，选用收款信息，避免重复录入。记录可来自其他组，但复用不授予来源支付单明细，也不是无条件浏览全组织收款目录；未开通支付的整页 placeholder 不因模板共享绕过。

频道收款信息作为快捷填充模板，而非支付业务记录；所有具备有效业务资格的组织成员可管理。同频道允许多条不同版本/信息记录，但相同内容去重，精确去重键和字段留 Spec；不另建复杂版本审批体系。选用时保存支付单自己的收款信息快照，模板后续改删不回写已保存单据，也不授予来源支付单访问权限。

**核对：** 议题 N6，D12。Demo：跨境支付 → 编辑草稿 → 按频道选用历史收款人。选中样例可回填收款信息，保留未保存的金额；频道模板维护与支付单信息分开，样例不证明真实去重或跨组织隔离已实现。

### S30 付款失败、取消或退款后核对资金
**状态：原则已定，异常矩阵与账本细节待 Spec/评审。区域：支付详情、资金及结果记录。**

付款未正常完成时，用户需看见状态、已占用及下一步。共享来源的取消/失败释放或退款回组织未分配可用部分；专用来源仅原组有效、已开通且匹配原周期时回组，否则回组织未分配。专用组关闭再开不接旧周期回补，存量组织钱包承诺沿原账路。历史仍记原付款和承担快照，不换成当前执行人，不因重试重复扣款；组支付关闭后整个模块不可用，不取消后台结算、释放及退款责任。

成功退款按实际金额冲回原 fundingUid + fundingGroupId 的个人已用，从而恢复其可用额；部分退款对应恢复，不提高配置上限，不转给接替人/执行人，也不恢复已退组、冻结或清退账号的使用资格。个人用量恢复与资金回组/组织是独立投影，不能把回款去向当作接替人获额度。原关系/周期字段及幂等留 Spec，是否恢复已定。币种手续费沿现有账务，不新增配置或自助改账，异常冲正沿现有人工；不承诺任意状态均可取消/退款，移交、冻结、归档不清除资金承诺。

**核对：** 议题 8、N4/N5/N8；Input §5.2、§5.8。Demo：示意原资金来源回补和原承担关系个人用量恢复，不提高上限/转给新 Owner；真实部分退款、历史身份、周期及回调幂等须独立验收，不将局部模拟当完整资金状态机。

## 第六章：看清工作与使用情况

<a id="S31"></a>
### S31 老板看全局，组长看部门与项目，成员看本人实际工作量
**状态：个人/选单人真实动作、组长项目整体与同页资格合并已确认；原整体指标及日期规则保留，实际来源/覆盖/历史/SLA继续核验。区域：总览 → 使用情况。**

以下五段是同一个故事的审阅路径，不新增故事编号。切统计范围不等于切业务身份；Demo 的“体验账号”选择器只用于模拟不同人物，产品不要求用户换角色后才看报表。

#### 场景一：组员核对本人动作，按项目查看自己的工作

**体验入口：** 许念或孙可 → 使用情况 → 个人维度 → 业务概览。许念想确认自己在所选期间做了哪些工作，而不是领取整个项目的成果。

**步骤：** 选择日期，先看本人全部动作，再在邮件分析中选择具体项目；切到 CRM、内容监控对照本人动作。另核对“有协作权限但期间没有操作”的分支，可在已覆盖日期看无人工记录的方禾；不要求为此真实发送或写入数据。

**结果与边界：** 项目只过滤本人动作，不能切成项目总量。本人有权限但没有操作时，可靠覆盖下的工作量为0；来源缺失则为未知，不以零代替。个人邮件看可靠人工发送及可核效果，来信和项目整体新增对话不直接算本人动作；CRM看人工新增/改状态备注，不是当前Assignee全部记录；监控看手工建项目/加条目，不拿观看增长当工作量。本人资源仍沿原计量主体。

#### 场景二：组长对照本人、全组和项目，不把三种结果混为一谈

**体验入口：** 周明 → 使用情况。周明既管理增长团队，也亲自参与业务，需要分别核对自己的工作、团队整体和某个项目结果。

**步骤：** 在个人维度看本人动作，并按项目过滤；切组维度查看增长团队整合结果、组员排行，选择许念看其实际动作，再返回组汇总；在模块内开启合法组长项目统计并选择本组项目。全页整体/实际操作量选择放在总览之前，项目整体选择只作用当前模块；日期在这些操作间保留。

**结果与边界：** 本人范围按普通成员统计，全组是整合数据，项目统计是项目整体结果。组长可看所辖组整合、成员动作和本组项目整体，不依赖默认协作开关；不能看其他组。组员排行按可靠人工动作单指标排序，不自动称绩效。统计资格不授予项目正文或写ACL，不能因报表可见就进入无权项目操作。

#### 场景三：Admin 从全组织下钻到单人，不越过统计边界

**体验入口：** 林知夏 → 使用情况 → 组织维度。林知夏在增长团队不是组长，用组织Owner身份示意仅组织管理资格的路径；Admin仅凭组织身份同样不能取得项目整体统计。

**步骤：** 先看全组织结果，选择增长团队看组汇总，再选择许念核对单人，返回组及全组织；同时检查目标组没有有效组长资格时，不提供该组“组长项目统计”。

**结果与边界：** Owner/Admin能看全组织、分组汇总和单人；选单人即切成该账号实际动作，不是其当前负责项目总量，口径应与本人个人页面一致。单人可按获准组拆开。组织管理身份不赋予项目整体统计或业务正文权限，不能从汇总下钻越权查看内容，也不能借导出绕过。

#### 场景四：Admin 兼任组长，在同页使用合并后的资格

**体验入口：** 陈予安 → 使用情况 → 组织维度。陈予安同时是Admin和增长/品牌团队的组长，无须为了查看不同报表切换账号或身份。

**步骤：** 保持同一体验账号，先查看全组织与分组汇总，再选自己任组长的组，在模块内开启项目整体统计；切个人维度核对本人动作。反向检查未任组长的目标组不因Admin身份开放项目整体；默认组可作为该边界的样例，若无项目不虚构结果。

**结果与边界：** 同页合并的是实际可用资格，不是把组长项目权限扩至全组织；逐目标组检查有效组长关系。仍可切组织/组/个人统计范围，个人范围按普通成员统计。CRM没有项目，不强造项目整体入口；资格变化不能靠旧筛选参数继续读取无权项目。

#### 场景五：核对动作、效果与资源承担，解释为什么数值不必相等

**体验入口：** 周明或林知夏 → 使用情况 → 业务概览，再对照选单人及资源使用。管理者发现团队发送数与成员手工发送合计、个人邮件资源用量不同，需要知道差异来自哪里。

**步骤：** 先看组织/组业务汇总，再切“实际操作量汇总”或选单人查看人工动作、自动执行和历史未覆盖说明；进入资源使用，比较同期间邮件消费与当前上限/剩余。只读核对，不在看板调额或执行发送。

**结果与边界：** 自动任务、自动跟进/追踪单列，不算配置者当期手工动作；整体业务效果与人工动作不必强行对齐。邮件发送/解锁仍按入口原核算主体，承担资源、实际执行和发件身份可能不同，不改成谁操作扣谁。组织/组人数和会话在目标范围重新去重，不直接相加成员值。历史actor缺失标未知，当前Owner/责任UID及交接后UID不能反推人，Demo以显式操作事件mock而非旧UID换名。工作量不自动承诺绩效、因果或完整效果分摊。

多人实际操作量的卡片写“本范围”，选择某账号写“所选成员”，个人范围才写“本人”；不能让全组数字看起来属于当前登录人。核心指标后优先看分组和成员摘要，邮件趋势、完整口径随后按需展开，指标和导出不因此删除。

资源页可按原名检索或分类定位，默认仍是原序23项总览/22列矩阵，手机可选单资源纵向比较。区分次数消费、当前容量/席位、资格和日/月限制，有证据才给单位及周期，未知继续待核。林知夏在看板选品牌组去配置时，应进入品牌组“组配额”，不误进顶部增长组；全组织先选目标组。周明去组内个人配置仍须有效组长及委派资格，目标与业务当前组不同时先明确确认切组，再到“本组管理 → 成员与配额”，取消不改变身份，组织管理身份不代替组长权。

#### 共用的页面与指标规则

Dashboard 另有独立实时交接待办，不随日期、所选成员、统计视角或资源显示筛选变化，不计入业务指标和统计导出。林知夏以组织Owner看清退进度摘要并进入组织移交任务，不取得增长/品牌业务明细或逐项分数据权限；陈予安同时是两组有效组长，合并相应业务处理入口。周明只见增长团队、乔南只见品牌团队待办，跨当前业务组先显式确认切组，再进入“本组管理 → 业务交接”，取消不执行移交。永久归档组标“归档免交接”关闭业务待办，组织进度统一“x/y组已处理”，明细分已交接和归档免交接，不称全部数据已移交。普通组员不见他人待办；选择预置的沈岚只看本人清退进度和失权说明，不看统计、业务详情或操作，具体过程见[S36–S38](#S36)。

林知夏选择全局开始/结束日期后，切组/个人、业务/资源或邮件/CRM/监控领域均保留日期，不静默改回某个月。在业务概览先读模块页签前的四个紧凑分区：触达看发送/回复率，沟通看新增/活跃对话，合作看期间新增CRM/其中当前合作中，内容看期间新增监控条目/期间观看增长。四区复用原指标但不是跨模块转化漏斗，各自期间/当前状态和实际观察截止不能省略。

四区随全页统计模式：合法组织/组整合看业务结果，个人/选单人看实际动作；全页“整体业务 / 实际操作量”控件位于四区之前。合法组长项目整体开关和项目选择留模块内，不把局部项目范围套到其他分区。下方单邮件项目只筛对应分析，入模块保留范围/日期并重置项目；普通账号不会因此得到项目总量。

合法整体邮件分析保留发送/送达/已读/回复四位七值，三率仍除发送数、随对应数量展示；额外四项可展开，原11项、独立对话/CSV不因折叠缩水。原邮件抽屉继续保留账号→任务八项及原分页/导出，Dashboard只在获准组长项目内保留对应明细，不宣称全身份完整替代原抽屉，也不给Admin新增项目统计权。个人和选单人仅用可靠人工事件表达动作，来信、打开/回复效果不能硬套完整11项或分摊给所有协作者；无可靠来源标未知，不复制项目总量凑字段。

林知夏在邮件趋势同时看发送、送达、已读（原打开数）、回复四线；重复的邮件效果漏斗已取消，四线按发送日期看截至更新时间效果。若回复未被追踪为打开而高于已读，保留原数值及提示，不为展示裁减原值，也不把原三率改成逐阶段比例。

趋势在不同宽度保留首尾和可读刻度，不让末端日期重叠；可按日期点查看四项读数，表格替代仍在。核心单位、上限、状态和必读口径不能只靠低对比小字说明。

整体范围的“对话沟通”新增/活跃两项仍按精确对话和消息时间，不是达人数/消息条数改名。个人/选单人另看本人实际沟通动作，不能将来信或整体新增对话直接认作个人量；效果分摊未核不承诺因果。来源/历史未知各自保留，不假零，见 [整体规则](./mail_dashboard_conversation_rules_2026-11-11.md)及 [实际动作/RQ-ACTOR-01–04](./dashboard_actor_workload_rules_2026-11-11.md)。

每个视角分“业务概览”和“资源使用”：先看邮件、CRM、内容监控的已说明口径。资源使用按[11-11 线上清单](./quota_inventory_live_2026-11-11.md)展示原名及顺序，组织总览23项、账号矩阵22项，子账户数量仅组织层。期间发生量与当前额度/占用分开，原当期/累计按原核算解释，不从两者相减反推任意区间。有依据时才展示相应上限和有效剩余；未知配置用“—／待核”，不伪造0或把组织数值复制给每个下级。真实“无限制”与本层“不追加上限”不混同。

非邮件也按统一日期的已定语义统计：CRM用本组业务记录创建日期，显示期间新增及其中当前合作中/已完成；监控新增项目/条目按创建/加入日期，观看互动增长复用观察期daily，包含旧存量内容。资源区分期间发生量与当前额度状态：容量/资格标当前，消耗/解锁按原有效记录时间，不能拿区间消耗重算当前剩余。完整23项分类和例外见 [时间规则](./dashboard_time_rules_2026-11-11.md)。

看板只读，不搬调额按钮；组织管理者配置组上限，获委派组长配置个人上限。去配置携带准确目标组及Tab，返回仍保留看板范围；不因资源展示齐全就认为所有Scope均已批准下分。

资金敏感汇总仍走独立资金权限；寄样/短链/泛活跃不在本轮新增。组织/组人数及会话重新去重，不直接相加成员值；整体结果和个人动作不必强行对齐，配额承担仍独立，不改成谁操作扣谁。

**核对：** Input §5.10、§6；议题 N7，D10；[邮件看板证据及 RQ-DASH-01–04](./email_dashboard_evidence_2026-11-11.md)。Demo：使用情况，用三视角、双视图、统一日期和邮件明细审结构，不把样例数值当线上可用。D10 仍核真实来源、历史和更新时间 SLA，而非重开已定覆盖/角色结构。原邮件抽屉仅收账号范围，不与新看板交互等价；Dashboard 审阅后继续真实页面任务映射。

<a id="S32"></a>
### S32 查看跨组成员和历史趋势，不把今天的组织倒填到过去
**状态：归因原则已定，历史可算范围待核验。区域：使用情况 → 趋势、明细。**

#### 场景一：选好日期后，在各模块之间查看同一期间

**体验入口：** 林知夏或周明 → 使用情况 → 业务概览。管理者想看一段跨月日期的工作，而不是每切一个模块就重新选月份。

**步骤：** 设置跨月开始/结束日期，切组、选单人，再切邮件/CRM/监控与资源使用，核对日期保留；回到邮件，将四线趋势依次切日、周、月。

资源处于当期或累计时，日期控件禁用并就地说明实际窗口，不能暗示任意日期会重算当前额度或累计值；切“期间发生量”再使用保留的日期，回业务仍不丢选择。

**结果与边界：** 同一日期范围不表示所有字段是同一种时间口径。合法整体邮件按发送时间选取数据、看截至更新时间效果，原沟通三项按消息时间；个人/选单人按实际动作发生时间，不把整体打开/来信分摊为本人动作。组织/组人数重新去重，整体三率按总数量重算，不平均账号比率。

趋势切日/周/月时日期不变：周一开始的自然周、自然月首末桶裁在原选期内，不扩大到完整周/月。四封数按桶聚合，原三率按相应总数量除发送数，不平均日比率；对话两项按完整日期范围精确去重，不把每天去重数相加。粒度控件不表示已有时间×账号周/月明细或自定义报表。

#### 场景二：跨组工作或交接后，回查历史贡献

**体验入口：** 陈予安 → 使用情况 → 个人维度；管理者也可在组织维度选择陈予安，核对多组动作。迁移/交接后的历史结果仅需准确说明，不要求Demo补完整持久化流程。

**步骤：** 看本人全部组及单组动作，再按项目筛选；随后同组换Owner或清退交接，回查仍对照原动作人/发生组，不归给新负责人。本期不演示或提供项目迁组。

**结果与边界：** 陈予安在增长和品牌两组工作，后来项目换Owner。管理者选陈予安或陈予安看个人时均统计其真实动作，可按获准组/项目过滤，不变成项目整体。组长另有所辖组项目整体入口；Admin若也任组长可同页使用，不用换身份。历史人工动作保留原actor/发生组，不因Owner或组关系变化回写；资源仍按原核算，自动另列。

若旧 Creator 是兼容镜像、UID 被历史交接改写或缺乏事件组快照，展示“历史未覆盖/未归属”等状态，不能回填今天所在组、用零替代未知或伪造个人业绩。延迟、异常、无权限和真实零值分开表示，必要时明确新口径起算时间。

#### 场景三：区分新对话、老对话和多人共同跟进

**体验入口：** 周明 → 使用情况 → 组维度 → 邮件数据 → 对话沟通。组长要知道本期新建立了多少沟通、多少老对话仍在跟进，而非把消息条数当对话数。

**步骤：** 同范围对照新增沟通对话和期间活跃对话，再选单人查看其实际发送和跟进动作；核对“首次回复即活动”“老对话再次往来”“多人跟进同一对话”和“仅单向邀约未回复”四个分支。

**结果与边界：** 整体新增/活跃是对话指标，单人是实际沟通动作，不互相改名。两人跟进同一对话时各自可有动作，组内去重对话不直接相加；不能拿整体新增对话或来信算成某个人手工产出。

发送/送达/已读/回复四线采用同一发送日期队列及截至更新时间原值，回复未被追踪打开可以高于已读数，不能为图形裁数或把相邻比例强压到100%以内。“对话沟通”另按消息事件看：精确对话全历史首次有效红人回复在期间内才算新增；此前已回复的老对话，期间再有效收/发算活跃而非新增。首次有效回复本身即为活动，不要求再追加消息；仅未回复邀约或首次回复前的发送不算沟通活跃。

同达人不同来源任务/组精确对话分别计，不按组织达人并。firstReply不能用选期首条替代，历史不足各自未知，完整同范围才核new≤active；键/消息/退组交接历史归因仍RQ-CONV，不从当前组或负责人倒填，不恢复已取消迁组。

#### 场景四：核对 CRM、监控和资源的不同时间口径

**体验入口：** 林知夏或周明 → 使用情况 → CRM/内容监控，再切资源使用。管理者希望知道本期新增、存量内容的本期增长和当前额度分别意味着什么。

**步骤：** 对照“上月新增、本月才完成”的CRM记录、“此前已监控、本期继续增长”的内容；改变日期范围后，核对期间发生量变化但当前资源上限/占用/剩余不被重算。再选单人，确认整体效果不冒充个人操作量。

**结果与边界：** 整体CRM按本组记录创建日期选新增、看其中当前状态，10月新增11月完成回查10月会更新当前完成，但不是10月完成事件。个人CRM人工新增/改状态备注按真实动作时间，不等于现Assignee全部记录；updateTime不能代跟进/完成事件，字段/历史交RQ-TIME及ACTOR核验。

整体监控项目/条目新增按创建加入日期，daily增长含旧存量并显示截至昨天等实际截止、缺失不假0；个人只核手工建项目/加条目，自动追踪单列，观看增长不作个人工作量。整体覆盖/基线/去重仍RQ-TIME，actor来源/自动历史另RQ-ACTOR，不新建快照伪造缺失。

资源按原有效消费/首次解锁记录日期计期间发生量：5历史创建不因删除抹去；31/56/17是当前容量，2/10是资格；24时长折算及调整日期、45当前授权与89未知保持待核；71新增授权删除不释放；7502/7503是同一导出双限制不可相加。当前上限/占用/剩余仍按原规则实时读取，不能由任意选期消费重新计算，也不从当期/累计相减猜历史；逐项单位/返还和组范围、实时SLA交RQ-TIME-03/04。

#### 场景五：遇到零值、未知、延迟和读取失败

**体验入口：** 使用情况 → 审阅数据状态，并配合日期选择查看历史覆盖说明。这是查看状态与解释，不要求模拟真实故障或补全历史。

**步骤：** 在有效范围查看无记录，改选actor未覆盖历史；再依次查看数据延迟、来源异常、无统计权限，核对汇总、明细和导出是否对应同一种状态。点击刷新后比较“数据截至/来源更新时间”与“本次读取时间”，再在异常状态体验重试；无权时不能靠重试或导出绕过。

**结果与边界：** 可靠空数据才是0；未知/未覆盖显示说明，不能假0；延迟标明上次有效结果及更新时间；异常/无权不展示可误认正常的数据并禁用导出。局部未知保留字段及原因，不因整段不可用而捏造结果。真实起算时间、覆盖与SLA继续研发核验。

数据来源时间与读取时间统一用北京时间并分开表达；刷新不能用新读取时间掩盖旧来源。来源异常允许重试，导出仍禁用；无权限不重试越权。Demo仅恢复示意读取状态，不连接真实刷新/重算服务，也不声称延迟数据已更新。

邮件发送/解锁用量仍按入口原核算主体，不能与actor动作强行相等。个人邮件按可靠成功人工事件、CRM按人工新增/改状态备注、监控按手工创建/加条目；不以当前Assignee/creator或观看增长代替工作量。失败/skip/重试、自动与人工来源、历史起算及缺失继续RQ-ACTOR核验，不承诺完整效果分摊或绩效因果。

**核对：** Input §4、§6.3–§6.8；议题N7/N10；[非邮件时间规则及RQ-TIME-01–04](./dashboard_time_rules_2026-11-11.md)。Demo按已定时间语义示意，不把缺失假0、当前结果伪装期间事件或历史归因；实际接口覆盖、daily截止/基线、逐Scope时间单位、组范围和SLA仍须验收。

### S36 离职清退时，把工作整体交给现有或新同事
**状态：接手路径、执行授权、触发方式与配额处理已定；真实模块覆盖和任务实现留 Spec/研发验收。区域：组织成员 → 移出组织；使用情况实时待办／通知与记录 → 本组管理 → 业务交接。**

小陈离职，Owner 或在“Admin 可移除成员”开启时的 Admin 发起组织清退，不能撤销。保留三条接手路径：邀请新账号完整接替、指定一个已有账号增量接替、清退后由各组组长分别处理数据移交。前两条是清退专用的生命周期管理能力：有权操作者指定接收人并提交后由系统统一执行，不另设操作者确认、组长批准或接收人确认接替，也不提供独立“确认接替/执行统一移交”按钮；不因此取得日常业务明细或任意逐项改派权。第三条由各组长处理未归档组子任务，不依赖原发起人；无组长且有人工决策业务则等组织安排业务负责人，无业务项可由有权组织侧确认结束。永久归档组在三条路径中均无需接收人、不执行业务替换或补接收人组关系，原责任/ACL/资金快照留历史，任务标“归档免交接”；先归档后清退同理。

新账号接替或已有账号增量接替时，只补齐组关系，不复制原账号的组长角色。新关系默认组员，已有关系保留接收人自己的组内身份；不自动升组长，也不降低其本来已有的组长身份。原账号若为唯一组长，接替后可以暂时无组长，须显式另行任命，不通过接替自动产生新组长。

新邀请未接受时展示 WAITING_FOR_TARGET、邀请与按组进度，原账号已失权，但不提前改写项目责任。接受邀请是必要的组织准入，不是移交审批；接受及资格、席位、组关系校验通过后自动开始移交。现有接收人提交后即可启动。前两条将离职者在未归档组涉及的项目 Owner、CRM 对接人与其他对象的有效显式协作关系统一交给该接收人，项目/CRM记录留原组；CRM无记录ACL可移交，原解析CRM管理员身份不继承。不是替换登录邮箱或creatorUid。第三条各组长分别处理未归档组时，项目与CRM接收人仍可分开，CRM按组可选0..1人，未选最终置未分配；后续写权限仍按原配置和当前对接人来源重算。归档组不改原Owner/Assignee/ACL，也不将CRM置未分配。

配额不继承、不相加：接收人已有某组有效关系时，保留自己的逐 Scope 上限、已用和占用；缺失关系按普通 inherit、支付个人 unlimited 初始化，仍受父级与资金约束。影响摘要说明新增默认可能比原 capped 更宽，需要限制时由获委派组长另走组内配额入口，不在移交表单调额或加确认勾选。“收回离职账号配额”仅指其未来使用资格与个人上限配置失效，不退还历史消耗、不释放支付占用、不增加组织/组余额；原记录留审计及结算。

本轮 Demo 在“组织管理 → 组织成员 → 移出组织”示意上述自动触发、邀请等待及配额边界；各组长在当前组处理第三条路径的本组任务，不显示发起或撤销人员移除入口。示例对象的替换不代表真实全模块覆盖、核算链或后台任务已验收。

第三条路径可从通知开始体验：Owner 清退一个跨组成员并选择各组长处理后，周明在“通知与记录”看到增长团队的待交接通知，品牌组组长看到品牌团队的通知；非目标组组长及仅有组织管理身份的账号不取得业务待办。通知显示组和离职成员，点击后定位“本组管理 → 业务交接”的具体行；不在当前组时先确认切组。组长再打开交接表单，选择同组项目接收人，CRM 可另选或保留未分配，提交才执行交接。仅查看通知不改对象责任，取消表单也不完成任务；此过程不是批准清退，不能撤销组织移除。

也可无需先发起新清退，直接体验预置的沈岚（`u-removing`）：其组织及增长团队、品牌团队关系均已 REMOVING，采用各组长分别处理，每组各有一个收藏夹 Owner 待交接。Dashboard实时待办提供按资格进入的入口；Owner/Admin只看组织进度和摘要，兼有目标组有效组长资格才可处理对应业务，普通组长只见自己管理组。可逐组交接，也可在满足资金条件后永久归档其中一组免业务交接。选择沈岚本人只见自身清退进度和失权说明，无统计、业务详情或交接动作。原7个ACTIVE账号、席位/邀请、资金和历史用量示例保持不变，不据此推定真实席位释放时点。

席位校验/替换保留、失败重试和最终释放须清晰；不能提交清退就当成全部移交完成。频控反作弊另列议题，不在这里发明阈值。

**核对：** 议题 11、22、N8/N9，D16 产品规则已定。Demo：使用情况实时待办、组织成员、组织移交任务、通知与记录及本组管理 → 业务交接；真实邀请、通知投递、任务快照、席位、核算字段与全模块覆盖留 Spec/研发验收。

<a id="S37"></a>
### S37 交接只完成一部分，管理者知道剩下什么
**状态：反馈与全对象移交范围已定，真实覆盖待工程验收。区域：使用情况实时待办、组织移交任务、本组管理 → 业务交接、通知与记录。**

管理者离开页面后回到任务摘要，看到各组/各对象已交接、归档免交接、失败、等待接收及可重试项。一个组处理完时，结果写明组及处理方式，不能当成全组织清退完成；全部必要组已处理后才发组织清退完成通知，汇总统一“x/y组已处理”。配置、资金、授权变化都有必要摘要和来源记录，不扩成全站审计中台。

分组处理的待办按实时有效组长资格展示：多名组长任一人完成同一任务后，其余人的该通知显示本组已交接，不再提供重复处理按钮；改走统一接替后旧待办也不可继续手动处理。组长降级或组关系失效后不再看该业务待办，新任命有效组长可承接未归档组尚未完成的任务。未归档组无组长且有业务项时显示待安排组长，不越权给 Admin 选择业务接收人；永久归档组则记“归档免交接”，保留原责任和授权历史并关闭业务待办，不设特殊组长或归档交接权限。只处理一组时组织仍为 REMOVING，统一汇总“x/y组已处理”，明细区分“已交接 / 归档免交接”，不得把免交接称为全部数据已移交。

组织管理者从组织移交任务查看进度、处理人员安排；组长在当前组处理组织侧产生的本组业务交接，包括组织清退的本组子任务，不按发起人划分权限。二者可复用摘要和完成反馈，但人员移除及撤销仍仅在组织侧，不能因共用任务结构开放同样的动作。

预置沈岚的两组任务可核对部分处理：周明交接增长团队收藏夹后，该组记已交接，品牌团队继续等待，组织仍为 REMOVING；若满足资金条件后永久归档品牌团队，则该组记归档免交接，原收藏夹Owner/创建人/ACL不改，关闭其业务待办。两组都已处理后才最终 REMOVED，不宣称全部数据已移交；先归档再清退也一样。Dashboard实时待办独立报表筛选，组织管理者看进度，组长只处理有资格的未归档目标组；本人摘要不恢复业务权。历史原权限不扩大，不复活REMOVING/REMOVED。

分页执行、幂等和断点续跑不等于数据库全量可回滚，也不把中途成功显示成全部完成。未归档组全部业务对象必须接入清退移交，包含旧研发附件曾排除的精选任务、TikTok Shop私信等，不再候选排除或冻结保留；日常功能不改不等于清退可遗漏。永久业务组归档免交接与资金历史快照例外保持，模块内部对象归档不自动获得该豁免，创建人/历史操作和用量不改写。须按模块逐项证明真实接入与结果，Demo有限对象或既有接口不足以宣称全量完成。

**核对：** 议题 22、26、N8/N9，D16。Demo：使用情况实时待办、本组业务交接、组织移交任务、通知与记录，可对照带组名的分组完成通知和最终的组织完成通知；真实后台分页、失败重试及对象覆盖另验。

### S38 部门停止运营，把组封存而不是删掉
**状态：已确认归档，不提供自助解除归档。区域：组织管理 → 业务组 → 组标题操作菜单。**

有权管理者预览组内对象、任务、资金和 REMOVING 关系后永久冻结归档，允许遗留业务对象及原责任记录，不要求先清空或指定业务接收人。组内原 Owner/Assignee/创建人/ACL及资金快照留历史，不移交、不迁移、不挂Admin；已有待交接任务记“归档免交接”并关闭业务待办，先归档后清退同理。归档保留groupId、关系历史及账务责任，不发起清退或清退普通成员；已有组织清退须全部必要组已处理才最终REMOVED，单组移除最后有效组仍须安排另一有效组或改组织清退。

只有 Owner 或“Admin 可归档组”开启时的 Admin 可归档，开关仅 Owner 配且默认关，默认组不可归档。二次确认不可自行恢复，异常走线下；归档组不再为普通当前组，不能新建对象/ACTIVE关系或普通写，不新增特殊组长或归档交接权。历史只按原权限可读，不扩大范围、不复活REMOVING/REMOVED；查询入口留Spec。内容监控项目自身归档/恢复不受业务组规则改变。

仍需组内人员推进的资金事项须先完成或转既有人工流程妥善处置，未处置前阻塞归档；可按既定后台链路结算的已有承诺不一概阻塞。归档或免业务交接不取消、核销旧单、占用、退款、结算或承担快照。专用组未承诺额另记归还，旧占用/已付保留，原周期失效后释放/退款回组织未分配；支付关闭再开从零新周期、不接旧周期回补，不是解除组归档。共享默认组若单独关闭支付，整页placeholder，但不清零组织共享资金或回收不存在的专用款。

**核对：** 议题 N2、N4，D08 已确认不提供自助恢复；Input §5.8。Demo：业务组、组织资金、通知与记录；归档只示意动作、二次确认和结果，没有归档后查看历史对象的入口。产品仍要求按原权限可读历史，不开放普通业务写，不要求补完整状态机。

### S40 企业会员到期，成员仍能查历史但不能继续业务
**状态：主规则已定。区域：登录后业务页、成员列表、配额说明。**

会员到期，组织和数据保留，只有组织 Owner 活跃，其余成员全部冻结。被冻结的林经理、张组长和小陈仍能登录、切换原本可进入的业务组、按原权限读历史；Admin、T2 或显式协作者都不能绕过业务限制。

### S41 由 Owner 按当前名额选择恢复成员，续费后也不自动全员恢复
**状态：主规则已定。区域：组织管理 → 组织成员。**

续费恢复未注销组织的权益，不重建组织、不自动全员解冻。周总在成员列表看当前子账号限额、已用和可激活数量，选择被冻结成员激活，直到达到上限。是否可以激活取决于当前限额，不额外要求必须先续费；免费/Basic 若仍有可用子账号名额，同样按当前限额处理。多组成员只占一个名额且各组统一恢复，Owner 不占子账号名额。

激活不新增 ACL 或额度，仍按当前有效规则执行。不提供主动/再次冻结轮换名额，释放名额走清退和必要移交；清退/新增频控另议。正规线上流程不提供套餐降级；线下特殊处理不在此视为支持能力。注销组织不能靠续费复活。

**核对：** Input §5.4；议题 20，D15 已定。Demo：组织成员、覆盖与待确认，仅说明席位与选择激活规则，没有激活操作。

### S42 公司换负责人，但业务项目不跟着全量换人
**状态：原则已定，转让资格和确认细节留给 Spec。区域：组织管理 → 组织成员 → 所有权。**

<a id="S43"></a>
### S43 公司决定永久停止使用，整组织注销
**状态：核心规则已定，资金清理与执行细节评审时确认。区域：组织管理 → 注销入口及资金阻塞清单。**

Owner 发起注销。免费/已到期企业可自助，付费有效期内先转人工处理。钱包余额、冻结金额或未完成支付阻塞最终完成，须自行清理或人工处理，不能确认风险后跳过，也不预设退款结果。

不支持组织暂停及对应状态。注销中间态不视为已注销，原 Owner 仍不能加入其他组织；只有最终注销解除全部关系后，才满足作为个人账号接受其他组织邀请的前提。组织之间不支持业务数据转移或复制。

### S44 先干净退出原组织，再加入另一家
**状态：加入条件已定；暂停组织与自动恢复路径明确不支持。区域：邀请接受、个人与组织身份。**
