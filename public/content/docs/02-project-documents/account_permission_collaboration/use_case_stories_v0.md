## 阅读方式

先读八章故事，再按需查规则和 Demo。每个故事都说明谁为什么操作、操作发生在哪一类页面、系统如何响应，以及结束后留下什么状态。

- **规则已定**：故事主规则已确认；界面和技术细节仍可能留给 Spec。
- **含待定分支**：已定部分可以读到结果，未定部分停在明确的问题上，不替团队补结论。
- **范围待裁决**：记录需求目标和决策点，不假装已有可执行流程。
- **一期接收/回归**：需接收交付证据，不把规划前提描述为已上线事实。

当前覆盖对象是已有 Input、梳理文档及 Demo 元数据中可识别的场景，不宣称穷尽未来所有真实用户行为。故事编号用于回溯，不代表优先级或分期。

## 第一章：开始使用

<a id="S01"></a>
### S01 老客户上线后照常工作
**状态：一期接收/回归。区域：后台初始化，用户原业务页面。**

小陈所在企业尚未使用新分组。底层替换生效时，系统初始化真实默认组、有效成员关系及已接入对象归属，小陈不需要先走迁移向导才能继续工作。

原负责人、协作、附加能力、有效额度和历史访问须按迁移方案保留；组长默认协作仍默认关闭，不因默认组里新增 T2 扩大权限。CRM 旧分组不能无条件压成一个默认组，正式支付单的旧宽写权限也不能当成应保留的协作授权。异常初始化、未覆盖对象进入接收清单，不报作“已完成”。

**核对：** Input §2、§4；议题 25、N10。Demo：业务分组及各模块；迁移是否真实交付须另验。

<a id="S02"></a>
### S02 个人账号第一次建立企业
**状态：规则已定，建企业及付费交互留给 Spec。区域：个人/付费入口、组织管理。**

小赵新注册时没有企业关系。他可以自行付费建立企业，也可以选择接受现有企业邀请，而不是注册就自动生成一份企业业务空间。建立企业后，组织是独立实体，有唯一 Owner，并具备开展业务所需的初始组与成员关系。

个人账号不等于某个企业的别名；后续企业到期、清退或注销要分别判断，不能都解释为删除登录账号。

**核对：** Input §5.3–§5.4；议题 N1。Demo：仅有成员与组织概念说明，未演示注册/付费建企业。

<a id="S03"></a>
### S03 邀请新人并让他具备工作条件
**状态：含待定分支。区域：组织管理 → 成员与邀请、配额与用量。**

周总搜索并确认邀请邮箱，发出邀请，小赵接受后才取得有效成员关系。在最终确定的邀请或入组配置步骤中，须显式确认新成员所需的业务身份、可分配 Scope 和支付上限等配置；这里不预先固定所有配置都在发邀请前完成。可分配额度默认 inherit，不引入岗位权限包或分组默认模板；不可分配权益只展示随组织状态。

**选择点：** 邀请时是否选择首组、是否自动加入默认组，或接受后另行入组，仍待定；不能写成已经选好其中一条。T2 是否还能依策略邀请本组 T3 也待会议裁剪定案。无论选哪条，必须说清小赵何时有有效业务组、何时完成额度配置，不能无解释地直接开放业务。

**核对：** Input §5、§8；议题 1、2、3、11，D03/D04。Demo：成员与邀请，现有邀请路径为讨论假设。

<a id="S04"></a>
### S04 邀请尚未接受，席位或配置已经变化
**状态：部分回归、部分待定。区域：组织管理 → 成员与邀请。**

邀请发出后，企业席位已满，或管理员希望撤销邀请。系统在邀请前、提交和接受时检查资格与席位，不能让旧邀请绕过当前上限；撤销后不能继续凭原邀请加入。验证邮件和错误提示应说明当前问题与处理方向。

待接受期间能否修改目标组、身份或额度，以及接受时如何呈现变化，留为待定分支。昵称/邮箱搜索只帮助定位候选，不扩大可邀请、可管理或可协作范围。

**核对：** 议题 2、11，D04；一期已有提示需回归。Demo：成员与邀请。

## 第二章：把团队组织起来

<a id="S05"></a>
### S05 先建空组，再把人安排进去
**状态：规则已定。区域：组织管理 → 业务分组。**

周总准备成立乙部门，先创建乙组、填写组名，暂时不加成员。之后由周总或有权 Admin 加入成员，分别配置 T2/T3 和组成员额度。每组可以有 0..N 名 T2，不要求先找一名组长才能建组，也不设置首席 T2。

后续维护时，有权组织管理者可在组管理中修改组名、任命或解除 T2。改名不改变组 ID 和对象归属；身份变化后，动态 T2 协作来源按新身份重算，不能连带删除独立显式授权。

T2 不因组长身份取得增删既有组成员、修改其组身份或发起退组的权限。Admin 能操作哪些组仍待矩阵定案，不能在本故事中自动视为全组织可管。

**核对：** Input §3、§5；议题 1、3、N1，D01/D02。Demo：业务分组。

<a id="S06"></a>
### S06 任命 Admin，但不把业务项目全部交给他
**状态：含待定分支。区域：组织管理 → 成员、组织策略。**

周总任命林经理为 Admin。任命改变组织管理身份，不改林经理在甲组的 T3 身份，不自动把他加入其他组，也不授予邮件、CRM 或支付对象权限。

**选择点：** 是否继续为每名 Admin 配置 0..N 管理组、是否允许范围重叠，以及哪些管理动作可执行，尚未锁定。范围配置和全组织管理都是待评审口径，不能因示意 Demo 可操作就视为批准。汇总查看与项目明细访问始终区分。

**核对：** 议题 1、16、N1，D01/D02。Demo：成员与邀请、组织策略。

<a id="S07"></a>
### S07 同一个人参与多个部门，切换工作组
**状态：规则已定。区域：全局当前组入口、具体业务模块。**

小李上午处理甲组项目，下午切到乙组。切组后，列表、候选协作者、新建对象和无对象业务消耗使用乙组上下文；小李在甲乙两组的身份与额度可不同。

已存在的项目不随切组搬家。通知或外部链接指向另一组对象时，先说明目标组并显式切换；有未保存内容时需告警。组织策略、组织钱包和全组织汇总等页面不跟随当前组伪装成组级设置。没有有效组关系时不能靠切换器进入该组。

**核对：** 议题 1、24。Demo：全局业务组切换及各业务模块。

<a id="S08"></a>
### S08 加入新组，先不搬走原来的项目
**状态：规则已定。区域：组织管理 → 成员/业务分组。**

周总把小陈加入乙组，确认乙组身份与配额。小陈可以同时保留甲组成员关系；如果不选择迁移项目，他在甲组的项目原封不动，在乙组作为没有原项目的新成员开始工作。

成员关系建立与项目搬迁是两个结果，不能把“入组成功”显示成“项目已全部迁移”。只有默认组身份的成员加入新组时，应主动询问是否整批迁移名下项目，不能静默搬迁。选择迁移后进入 S34。

**核对：** 议题 3、24、26。Demo：业务分组、移交与迁移。

## 第三章：配置工作条件

<a id="S09"></a>
### S09 给组和成员设置可使用的额度
**状态：规则已定，Scope 矩阵待核实。区域：组织管理 → 配额与用量。**

周总先查看组织实际权益，再为甲组设置可分配项的组上限，为小陈设置 inherit 或 capped。inherit 是不追加这一层限制、使用父级共享额度，不是无限供应。组本身也可继承父级。

没有统一的模块禁用开关；有的能力受额度控制，有的仍是套餐门禁或其他 Scope 类型，不能把所有功能改成一个数值框。额度为零阻止对应消耗，不删除已有对象授权。支付金额另走 S25，不能套用普通额度的超配规则。

**核对：** 议题 3、9、18；Scope 规则；D07。Demo：配额与用量。

<a id="S10"></a>
### S10 允许组长自行安排本组成员额度
**状态：规则已定，Admin 配置动作待矩阵确认。区域：组织策略 → 配额与用量。**

有权配置者开启组织全局“允许 T2 管理本组账号权限”策略。张组长可以调整甲组自己和其他成员的可分配额度，但不能抬高甲组上限、修改组织权益或借此维护成员进出与 T2/T3 身份。

关闭策略后，T2 不再以这一来源调整成员配置；多名 T2 权限对等。是否能修改全局策略由管理动作矩阵控制，不因 T2 能调组内额度就让其修改开关。

**核对：** 议题 3、9、N1。Demo：组织策略、配额与用量。

<a id="S11"></a>
### S11 有协作权限，但发送时额度不足
**状态：规则已定。区域：邮件等消耗型业务页面。**

小陈能编辑邮件项目，点击发送时系统仍检查套餐、有效身份，以及适用于该 Scope 的组织、组、账号限制。普通子级上限之和可以大于父级，但实际消耗不能突破任一有效上限；提示应指出阻断层级，不暗示协作权限丢失。

额度足够却没有项目授权时，同样不能发送。按次数消耗、容量占用、一次解锁、频率和门禁分别沿用其规则，不统一扣一次；组织内可复用的已有解锁不重复收费。免费、无权益、耗尽和来源异常应分开反馈。

**核对：** 议题 9、18；Input §3 及 Scope 规则。Demo：邮件项目、配额与用量；示例扣量不代表完整 Scope 生产矩阵。

<a id="S12"></a>
### S12 一次给一批成员追加额度
**状态：规则已定。区域：组织管理 → 配额与用量。**

有权管理者搜索并勾选一批甲组成员，输入增加量，先查看预览再提交。只对适用的 capped 数值增加；inherit 和不可分配项跳过，不能悄悄改成 capped。

完成后显示成功、跳过和失败摘要，以及需要重试的对象。不把“批量增加”混成统一覆盖原值，也不对未选成员操作。

**核对：** 议题 2、10、N8。Demo：配额与用量、通知与记录。

<a id="S13"></a>
### S13 成员查看余额时，分清共享额度和自己的上限
**状态：部分已定、展示口径待细化。区域：组织管理 → 配额与用量、组织策略。**

小陈查看当前可用量。系统按其允许看到的范围返回个人上限、共享层约束和实际周期，而不是把组织全部用量明细都交给前端隐藏。团队额度可见性策略不授予项目访问权。

inherit、套餐无限、当前剩余和无权益不能显示成同一个“无限”；不可分配项不伪造个人剩余量。具体特殊值展示、可用量口径和各 Scope 周期仍需统一。月份统计不是月度重置的证明。

**核对：** 议题 9、15、18。Demo：配额与用量；无限与剩余展示仍为待确认入口。

<a id="S14"></a>
### S14 年付企业希望每个月给部门设预算
**状态：范围内待定方案。区域：组织管理 → 配额与用量。**

周总希望年度套餐下按月限制部门或成员使用，另一类企业则是年付但组织权益按月发放。两者不能仅凭“按月”使用同一重置逻辑。

**选择点：** 下级月度窗口是否提供、自然月还是会员月、剩余结转、期中调整、时区和历史展示尚未定。不得先画一个月度数字框就宣称已经支持，也不改变真实套餐发放周期。

**核对：** 议题 15、17，D07。Demo：配额与用量的月度讨论入口。

## 第四章：在业务里协作

<a id="S15"></a>
### S15 创建项目，并让同组同事一起工作
**状态：规则已定，模块完整动作矩阵留给 Spec。区域：邮件、收藏夹、内容监控等项目设置。**

小陈在甲组创建项目，项目固定归甲组，小陈是项目 Owner。他搜索甲组有效成员，把小李加入 Collaborator；小李获得该对象允许的常规读写，不再先选择通用 Viewer/Editor。

删除、转交、归组、管理协作者和支付执行等不随普通读写一并赠送；不能选择乙组独有成员。收藏夹的公开/部分可见等既有范围不因统一协作概念被抹掉。品牌监控按自身已接入对象规则核对，不因通用示例自动承诺接入所有品牌对象。

**核对：** 议题 2、5、16；Input §3、§5。Demo：邮件项目、收藏夹、内容监控；完整模块接入仍需验收。

<a id="S16"></a>
### S16 让协作者帮忙增减人，但不能继续转授权
**状态：基本规则已定；组织管理身份的授予动作待矩阵。区域：具体项目 → 协作者设置。**

小陈授予有效 Collaborator 小李 can_manage_collaborators。小李之后能按对象规则增减同组协作者，却不能把这项管理能力再授予另一人；普通协作者并非天然可管理成员。

项目 Owner 可收回该能力。只读访问对象不能得到它，普通协作来源和附加能力要分别显示与计算；组织 Owner/Admin 不因名称相似自动取得此对象能力。

**核对：** 议题 5、16。Demo：各项目的协作者设置。

<a id="S17"></a>
### S17 让组长统一参与组内项目，再关闭该策略
**状态：规则已定。区域：组织管理 → 组织策略；业务模块 → 协作者列表。**

周总预览影响并确认开启全局“组长默认成为组内所有项目协作者”，原本未被逐项邀请的甲组 T2 因系统来源取得已接入甲组项目的普通协作能力；列表锁定展示这个来源，而不是伪造显式 ACL。

关闭开关、降为 T3 或关系失效后，该来源失效，独立显式授权仍保留。不自动赠送管理协作者、资金执行或高风险治理权限。默认关闭，主动开启是权限扩展，必须单独安全验收。管理汇总权限始终不等于项目协作。

**核对：** 议题 5、16、N8。Demo：组织策略、各业务模块、通知与记录。

<a id="S18"></a>
### S18 想让同事只看项目，不一起编辑
**状态：含待定分支。区域：具体业务模块的访问设置。**

小陈希望同事只看项目。不能把该人加入 Collaborator 后再期待其只读，因为 Collaborator 是常规读写。

**选择点：** 是否建设通用对象级显式查看授权尚待裁剪确认。无论是否建设，都不能顺带删除正式支付单同组只读、CRM 现有读取、收藏夹既有可见范围等模块语义；这些范围也不能被扩展成全模块 Viewer 角色。

### S25 给部门增加资金预算，必要时纠正一笔分配

正式单对所属组有效成员固定只读，不写入 Collaborator；没有写来源的成员不能编辑或执行。组织敏感信息策略默认关闭，组内只读者看到脱敏信息且不能下载回执；打开也不增加写权限。Owner 不能主动转交支付单，生命周期移交不改写既有资金承诺。

### S28 部门要求组长在转账前审核
**状态：核心规则已定，状态边界含待定分支。区域：具体组支付设置、支付列表、系统通知。**

**选择点：** 关闭策略如何处理等待中订单、无有效 T2、并发审核及相关状态边界仍需收口；T2 审核权不等于 Collaborator 或 can_execute_payment。

### S30 付款失败、取消或退款后核对资金
**状态：原则已定，异常矩阵与账本细节待 Spec/评审。区域：支付详情、资金及结果记录。**

<a id="S36"></a>
### S36 离职清退时，把工作整体交给现有或新同事
**状态：主流程已定，替换席位和对象覆盖需细化。区域：成员详情 → 整体移交、邀请与任务页。**

小陈离职，Owner/Admin 发起组织清退，不能撤销。可选一个现有账号作为整体接收人，也可填新同事邮箱发起接替邀请；接收人需要具备涉及各组的有效身份和配置，不能默认取得跨组权限。

接收人未就绪时展示 WAITING_FOR_TARGET、邀请与按组进度；项目责任及有效显式对象关系按规则移交，不能只替换登录邮箱或 creatorUid。CRM 按组可选 0..1 名接收人批量改派，未选则最终置未分配，这是生命周期清理例外，不是 Admin 日常改派权。

席位校验/替换保留、失败重试和最终释放须清晰；不能提交清退就当成全部移交完成。频控反作弊另列议题，不在这里发明阈值。

**核对：** 议题 11、22、N8/N9，D16。Demo：成员、移交与迁移；整体替换全路径与新邮箱接替仍须核验，不能由局部示意声称完备。

<a id="S37"></a>
### S37 交接只完成一部分，管理者知道剩下什么
**状态：反馈原则已定，对象缺口待裁决。区域：移交与迁移、通知与记录。**

管理者离开页面后回到任务摘要，看到各组/各对象成功、失败、等待接收及可重试项，完成后收到系统通知。配置、资金、授权变化都有必要操作摘要和来源记录，不扩成全站审计中台。

分页执行、幂等和断点续跑不等于数据库全量可回滚，也不把中途成功显示成全部完成。精选任务、TikTok Shop 私信等研发排除对象须明确纳入移交还是保留责任并冻结，不能笼统说“名下所有业务都已转给新人”。

**核对：** 议题 22、26、N8/N9，D16。Demo：移交与迁移、通知与记录；模块真实覆盖另验。

<a id="S38"></a>
### S38 部门停止运营，把组封存而不是删掉
**状态：归档已定，恢复待定。区域：组织管理 → 业务分组。**

有权管理者预览组内对象、任务、资金和 REMOVING 关系后冻结归档，允许遗留数据及无人负责的对象，不要求先彻底清空。归档保留 groupId、关系历史和账务责任。

归档组不能成为普通当前业务组、创建对象、增加 ACTIVE 成员或继续普通业务写；已有资金与系统责任不因归档消失。历史入口需要保留，但谁能看仍受原权限。解除归档及恢复细节未定，不能暗示一定能恢复业务。

**核对：** 议题 N2，D08。Demo：业务分组、通知与记录。

<a id="S39"></a>
### S39 想把整个部门并进另一个部门
**状态：范围待裁决。区域：业务分组。**

周总希望甲乙部门合并，业务继续留在乙组，而不只是把甲组封存。需要一起处理成员去重、T2 身份、项目/CRM 责任、ACL、共享配置、配额、资金和历史统计。

是否提供完整合并、如何处理冲突仍待确认；不能用小陈个人名下项目迁组冒充整组合并，也不能把归档解释为业务已接续。

**核对：** 议题 N3，D08。Demo：业务分组的讨论入口，无执行闭环。

## 第八章：套餐、所有权和组织生命周期

<a id="S40"></a>
### S40 企业会员到期，成员仍能查历史但不能继续业务
**状态：主规则已定。区域：登录后业务页、成员列表、配额说明。**

会员到期，组织和数据保留，只有组织 Owner 活跃，其余成员全部冻结。被冻结的林经理、张组长和小陈仍能登录、切换原本可进入的业务组、按原权限读历史；Admin、T2 或显式协作者都不能绕过业务限制。

Owner 仍按免费/Basic 实际权益工作，不是一切付费能力照常。已提交邮件、导出、Agent 及预约支付不因成员冻结自动取消或释放占款，持续任务按组织权益继续判断，配置不被删除；草稿保留，人工步骤等待其他有权活跃成员处理。冻结不是退组、清退、移交或注销。

**核对：** Input §5.4；议题 20，D15 已定。Demo：规则说明，尚无完整冻结状态模拟。

<a id="S41"></a>
### S41 由 Owner 按当前名额选择恢复成员，续费后也不自动全员恢复
**状态：主规则已定。区域：组织管理 → 成员列表。**

续费恢复未注销组织的权益，不重建组织、不自动全员解冻。周总在成员列表看当前子账号限额、已用和可激活数量，选择被冻结成员激活，直到达到上限。是否可以激活取决于当前限额，不额外要求必须先续费；免费/Basic 若仍有可用子账号名额，同样按当前限额处理。多组成员只占一个名额且各组统一恢复，Owner 不占子账号名额。

激活不新增 ACL 或额度，仍按当前有效规则执行。不提供主动/再次冻结轮换名额，释放名额走清退和必要移交；清退/新增频控另议。正规线上流程不提供套餐降级；线下特殊处理不在此视为支持能力。注销组织不能靠续费复活。

**核对：** Input §5.4；议题 20，D15 已定。Demo：规则说明，尚未实现成员激活操作。

<a id="S42"></a>
### S42 公司换负责人，但业务项目不跟着全量换人
**状态：原则已定，转让资格和确认细节留给 Spec。区域：组织管理 → 所有权。**

周总把组织 Owner 身份移交给另一名成员，组织仍只有一名 Owner。组织管理身份交接不等于项目 Owner、CRM Assignee、组身份或资金承担历史全部改名，也不把新 Owner 自动变成所有项目协作者。

正常成员管理不能清退当前 Owner 或删除最后成员；要离开时先完成合法所有权交接，或走独立注销流程。完整接收资格、验证与反馈不靠本故事新造。

**核对：** 议题 N1；梳理文档组织所有者。Demo：成员与邀请 → 所有权示意。

<a id="S43"></a>
### S43 公司决定永久停止使用，整组织注销
**状态：核心规则已定，资金清理和执行边界待细化。区域：组织管理 → 注销入口及资金阻塞清单。**

Owner 发起注销。免费/已到期企业可自助，付费有效期内先转人工处理。钱包余额、冻结金额或未完成支付阻塞最终完成，须自行清理或人工处理，不能确认风险后跳过，也不预设退款结果。

满足条件后经过三次确认，完成时全员解除有效企业/组关系，回到个人账号，原组织数据不可达；不要求先逐个清退或内部交接项目。非资金业务一键停止/放弃，用户不必等任务自然完成；资金回调与账务不能丢弃。已外发邮件不承诺撤回。

注销不可恢复，登录、续费、离开别的企业或人工恢复都不能复活旧组织；以后建企业创建新身份。申请/取消时点、通知、物理清理与必要审计保留、人工退款细节仍待设计，但不重新讨论不可恢复与三次确认。

**核对：** Input §5.3；议题 N1。Demo：仅规则/议题入口，没有执行注销操作。

<a id="S44"></a>
### S44 原来有自己的企业，现在想加入另一家
**状态：未批准路径，需独立审阅。区域：邀请接受、个人与组织身份。**

小赵原本拥有企业，又收到其他企业邀请。研发附件出现过“暂停原成员身份，加入外企，离开后恢复原企业”的路径，但它不是当前已经批准的自动业务故事。

单账号只能有一个有效企业归属，当前组织不能缺失 Owner；是否须先转让或注销、原企业与资源如何保留、何种情况下允许恢复都需另行确认。不得借此复活注销组织，也不能把到期后的冻结/激活当成跨企业恢复方案。

**核对：** Input §5.3 末段、研发附件状态路径。Demo：未实现该路径。
