聚星的账号和权限设计，将一个组织账号按两个不同维度（账号管理维度、业务维度）进行定义和设置：账号管理维度定义组织身份和管理范围，业务维度定义组成员关系、当前业务组和对象协作权限。两个维度除必要的管理设置动作外不相干，组织身份本身不产生业务对象权限。

## 账号管理维度

从**账号管理维度**来看，首先一个`【客户】`要有一个`【组织】`实体。`【组织】`内应有1..n个`【成员账号】`，成员账号中有且只有`1`个账号拥有`【组织所有者】`身份，另外还可能有0..N个`【管理员】`身份的账号，其余账号皆为`【普通成员】`。组织身份与账号在各组中的业务身份分开保存。



### 组织

- 组织是独立于登录账号的实体。新注册个人账号不自动归属企业；无企业关联的账号可在付费建立企业时创建组织，或接受邀请加入现存组织。
- 【2026-10-28 已确认】会员到期保留组织、成员关系和数据，不自动解绑或注销。历史数据原则上按原权限可读，新增/发送/刷新/容量等按免费实际权益限制；产品负责人确认该方向符合线上行为，本轮未重新实测。续费恢复未注销原组织的对应权益，不重建组织，也不能恢复已注销组织。
- 【已纳入本版，主流程已确认】会员到期时仅组织所有者保持活跃，其余成员全部冻结，不删除成员、数据或原权限记录。冻结成员能登录、按原权限查看历史数据和切换原有可用组，但所有组统一禁止其参与业务；T2/Admin 身份和协作关系不能绕过冻结。该项来自原反馈行 33、原 Input E2，现为统一版本第 20 项。
- 【已确认】【UI交互】组织所有者在成员账号列表中按当前子账号数量限额选择激活冻结成员，达到上限后不能继续激活；列表展示已用、限额和可激活数量。Owner 不占子账号名额，多组成员仅占一个名额并统一激活；激活不新增业务授权或配额，原规则仍须满足。续费不自动全员解冻，详见 [统一版本 Input §5.4](./phase2_input_v0.md#54-会员到期续费与超额成员2026-10-28-补充)。
- 【已确认】套餐原则上不支持降级，正规线上流程不提供降级入口，本版不新增即时或预约降级流程。线下特殊处理不预设为支持能力；原“降级续约”需求按到期冻结、续费后按当前限额激活的主线收口。
- 【已确认】不提供主动冻结/再次冻结操作；释放已激活子账号名额只能走组织清退流程，保留数据移交等要求，不能以冻结代替清退。清退与新增子账号的频率控制、反转卖等反作弊要求单列议题，暂不展开具体规则。
- 【已确认】冻结不自动取消已提交业务，不触发数据移交。邮件、导出、Agent 等已提交任务及持续监控/周期任务按原规则和当前组织权益执行，监控配置不因创建人冻结而删除；已提交/预约支付不因冻结取消或释放占款，仍遵循支付、审核和资金规则。草稿保留，冻结成员只能按原权限查看；需人工推进时由其他有对应权限的活跃成员操作，不因组织管理身份自动获得业务权限。各模块权益检查时点和状态细节留到 Spec，不套用注销时的一键停止。
- 组织拥有**成员账号列表**。
- 组织拥有**组织策略**配置，组织策略默认影响组织中所有成员与业务。
- 组织由当前的组织所有者进行**管理**。
- 组织拥有多个业务组；业务组可以为空，也可以暂时没有组内 T2。组织始终保留一个有效默认组，默认组不可归档。
- 【2026-10-28 已确认】组织所有者可发起注销：免费或已到期组织走自助路径，付费有效期内转人工处理，处理完成且满足条件后才能最终注销（方案 C）。这替代原“不能解散组织”的绝对限制，不代表可无条件立即注销；资金处理细节、数据处置、通知和执行前申请/取消边界仍待确认，见 [统一版本 Input §5.3](./phase2_input_v0.md#53-组织注销与付费状态2026-10-28-补充)。
- 【已确认】注销允许带成员整体处理，不要求先逐个清退至只剩 Owner；完成时统一解除全员有效组织/组关系和业务访问资格，不执行原组织内部的项目 Owner/CRM Assignee 交接或协作权限移交。普通成员清退仍必须按既定流程移交。
- 【已确认】【UI反馈】钱包余额、冻结金额或未完成支付均阻塞最终注销，须自行通过已有业务流程清理或转人工处理，解除阻塞后才可继续。页面须展示阻塞事项及处理方向，不允许仅确认风险后跳过；不以清零数值、删除订单或注销数据代替结算。退款/退余额和人工处理细节仍待细化。
- 【已确认】注销时一键停止本组织全部业务动作，非资金任务统一放弃，不要求用户逐个取消或等待完成。邮件/Campaign、监控、Agent、导出、CRM 批处理及本组织内正在进行的数据移交/迁移，均不另设注销阻塞项；资金处理统一进入上一条资金阻塞校验。
- 【已确认】【UI交互】注销完成后不可恢复，最终执行前须三次确认，参考 GitHub 删除仓库。登录、重新付费、续费回调、离开其他企业后的身份恢复或人工恢复不得复活已注销组织及其成员/资源访问关系；以后再次建立企业应创建新组织。
- 【UI建议，Spec 细化】依次确认目标组织、确认注销影响及不可恢复后果、输入组织名称后最终提交。具体文案和交互留到 Spec；三次确认不替代付费期内人工处理及资金阻塞校验。只参考 GitHub 的确认方式，不沿用其部分仓库可恢复规则。
- 【研发提醒，不是产品阻塞项】停止调度和重试、防止注销后继续外发、扣额度或回写可用数据，处理迟到回调、导出链接和残留锁；已发往外部的邮件/消息不承诺撤回。非资金任务可后台作废或收尾，不要求用户等其终态；资金回调与结算不得丢弃，也不得误停其他组织或破坏全局登录身份。
- 注销完成后，原成员失去组织业务数据可达性并成为无企业关联的个人账号；不是删除登录账号或把组织数据交给成员。会员到期保留成员与历史读取，冻结/激活按统一版本 Input §5.4 执行。
- 【2026-11-10 已确认】不提供“暂停组织”操作及对应状态；注销中间态不算已注销，Owner 在流程未完成前不能加入其他组织。加入须“干净账号”，即没有其他有效组织关联或未完成的退出/清退/注销关系；Owner 应先转让所有权并完整退出原组织，或完成不可恢复注销。历史审计记录不算有效关联；组织间不转移、复制业务数据，不支持离开外企后自动恢复旧组织或身份。
- 组织成员日常移除仍受生命周期和数据移交约束。组不彻底删除，改为冻结归档并保留 `groupId`、业务对象、成员历史、任务、资金账本和审计。【UI反馈】移出或归档前需展示数据影响；业务组归档须二次确认并标明不可自行恢复，不提供解除归档入口，异常恢复转线下数据恢复流程。
- 新规则上线时不要求存量客户先配置分组。系统原子创建一个真实默认组，将存量有效成员和已接入的项目型业务对象归入默认组；CRM 历史记录的初始归组另定实施方案，不按弃用的旧 CRM 分组设置自动映射，也不向全部组复制。默认组不是隐藏分组或特殊兼容空间。
- 存量组织初始化时，组织所有者成为默认组 T2，线上原 `adminStatus=2` 的组长迁为默认组 T2，其他成员迁为默认组 T3；组织 Owner/Admin 身份单独保留。
- 存量项目的 `ownerUid`、显式协作关系、查看来源、附加能力、配额有效状态和支付历史身份按迁移真值表承接；CRM `ownerUser` 映射为可空对接人/记录负责人，未分配保留。CRM 四项写设置及默认值继续生效，但任何授权都不能越过记录所属组；旧组来源的实际映射及历史初始归组须单独验收，不能声称全模块无损。正式支付单/草稿迁移也继续单独处理。
- 存量 Scope 不为补齐 `groupId` 伪造历史归属：组织级用量、占用、已解锁状态和剩余额度保持线上口径；当前容量按迁移后对象组计算，可靠的账号上限和本周期个人用量迁入默认组 GroupMembership，无法可靠归属的事件型历史用量只留在组织层。组织内已经完成的一次解锁继续复用，不重复收费；上线后的新消耗须区分真实组归属、实际 actor 与该入口既有核算主体，记录 actor 不等于按 actor 扣量。
- 组织策略“组长默认成为组内所有项目协作者”对新组织和存量组织均默认关闭，因此迁为默认组 T2 不会在上线时自动扩张项目权限；后续主动开启才产生 T2 系统协作者来源。

### 成员账号

- 一个成员账号只能属于一个组织，不支持跨组织复用；同一账号可以通过多条组成员关系加入同一组织内的多个组。
- 未接受邀请或尚未加入任何客户组织的账号，可以没有有效成员关系。
- 正常存续的组织不能没有成员或所有者。
- 日常成员管理须阻止删除最后一名成员、移除当前所有者；组织整体注销作为独立流程，不能借普通清退绕过条件。
- 组织成员关系和组成员关系均需区分 `ACTIVE`、`REMOVING`、`REMOVED`；移出组织不可撤销，Owner 必须保留至少一个 ACTIVE 组成员关系。

| 组织身份   | 数量     | 说明                                             |
| ---------- | -------- | ------------------------------------------------ |
| 组织所有者 | 恰好 `1` | 唯一、可移交，拥有所有者专属动作                 |
| 管理员     | `0..N`   | 由所有者任命，全组织管理，敏感管理动作受组织策略限制 |
| 普通成员   | `0..N`   | 不具备组织管理能力，但可以通过组成员关系参与业务 |

#### 组织所有者（超级管理员）

- 【UI交互】组织所有者可以向另一个成员账号移交所有者身份。
- 组织所有者可对另一个成员账号进行管理员身份任命/解除，不再设置逐 Admin 的管理组范围。
- 【UI交互】组织所有者可以邀约/移除成员账号。
- 【UI交互】组织所有者可以**管理组**。管理组的具体定义见业务维度**组**描述。
- 【UI交互】组织所有者可以编辑业务维度配置（组设置）。
- 【UI交互】组织所有者可以修改组织策略配置。
- 组织所有者和 Admin 均采用全组织管理，不提供逐 Admin 管理组范围或范围重叠配置。
- 【已确认】【UI交互】仅组织所有者可配置“Admin 可移除成员”和“Admin 可归档组”，两个开关默认关闭；Owner 自身不受限制，Admin 不可自行开启。移除成员包含移出组织与移出某组；归档组不代表彻底删除组，默认组始终不可归档。
- 组织所有者可在使用情况的组织视角查看全组织、分组汇总及单人统计；汇总属于管理行为，不自动开放组成汇总的业务明细。
- 组织所有者不因组织身份自动获得任意业务对象的查看、编辑、删除或资金执行权限；参与业务时仍需具备对应组成员关系和对象权限。



#### 管理员

* 管理员角色由组织所有者任命/解除
* 管理员角色拥有部分组织所有者权限，受组织所有者配置；具体动作由管理动作矩阵约束
* 【已确认】管理员采用全组织管理，可邀请成员、创建组，不配置逐人的管理组范围或范围重叠
* 【UI交互】管理员可在使用情况的组织视角查看全组织、分组汇总及单人统计；该管理能力不等于这些组的业务对象明细权限
* 管理员参与具体业务时，仍按自己当前组的组成员身份和对象授权工作
* 管理员的汇总查看属于管理行为，不自动开放组成汇总的项目、CRM 记录或支付单明细
* 【已确认】管理员移出组织成员或某组成员、撤销尚未完成的单组移除、组织侧确认无业务项的关系结束，均须 Owner 打开“Admin 可移除成员”；不能通过换入口绕过，但有效组长处理既有本组业务交接不受此开关限制。管理员归档业务组，须 Owner 打开“Admin 可归档组”。两个组织策略均默认关闭，只有 Owner 可配置，Admin 无法自行提权；其余管理动作仍按动作矩阵收口



#### 普通成员

* 普通成员仅由组织所有者/管理员角色邀请加入组织；组长不能邀请新成员
* 普通成员**不能**对组织进行管理
* 普通成员不能自行修改组织身份或既有组成员关系；退组、移出组织和数据移交由有权的组织管理角色发起



### 成员账号邀约

* 【UI交互】成员加入组织，仅由组织所有者/管理员进行**邀约**；组长不能邀请新成员
* 【UI交互】邀请可选择首组，默认选择始终存在且有效的默认组；接受时建立所选组关系。成员与邀约流程不提供个人额度配置，不设置分组默认配置模板
* 补建组关系时，可分配型 Scope 默认 `inherit`，支付账号上限默认 `unlimited`；不可分配 Scope 随组织权益。邀约者不能逐项改为 `capped` 或填写支付金额上限，后续由本组有效组长在全局 `t2Quota` 委派开关允许时逐 Scope 配置
* 【已确认】待接受邀请不提供修改目标组或身份的入口；需要变化时撤销原邀请再重新邀请，撤销后的原邀请不可接受
* 【UI交互】【UI反馈】成员加入目标组本身与其 Owner 名下项目迁移分开处理；是否迁移必须显式选择，不能静默搬迁项目
* 【已确认】邀请首组选择不是待定候选流程；默认组不可归档，接受时仍须校验所选组的当前有效状态与席位资格，不能由旧邀请绕过校验



### 组织策略

组织策略为一系列配置项，用以决定业务维度中的数据权限与协作行为，以及一些全局的账号管理维度设置。

组织策略的可编辑主体按具体动作约束；“Admin 可移除成员”和“Admin 可归档组”明确只有组织所有者可以设置，均默认关闭。

- 【现状事实】正式支付单当前全组织可读，服务端正式单写接口也只校验同组织和订单状态；`editFlag` 只是前端创建人展示信号。草稿则仅创建人可读写。创建正式支付单时即冻结组织钱包 `pending`，历史收款账号按组织+频道+平台共享。

- 管理员是否可以修改组织策略中的高风险配置，具体动作留待管理动作矩阵确认





## 业务维度

**业务维度**主要定义组织成员在使用平台功能时，对数据的读写操作范围，以及以**组**为结构的数据隔离规则，和组内权限层级规则。



### 组

组是组织内人员划分和业务隔离的形式。一个账号可以加入组织内的多个组；每条组成员关系单独记录其 T2/T3 身份和可分配型 Scope 配置。每个组有0..N个组长（T2），其余为组员（T3），允许先建立空组或暂时没有组长。

组的创建、人员加入/移出、身份任免、撤销移除、组总配额和归档由组织所有者和有权限的管理员进行；Admin 发起成员移出及业务组归档分别受两个默认关闭的 Owner-only 开关控制。组织始终保留有效默认组，默认组不可归档。组长在当前组管理本组业务、按委派设置成员额度，并处理组织侧产生的本组业务交接，不邀请、主动移出或撤销移除成员。



- 每个组织成员可以**加入**1..N个组
  - 每个组成员关系独立保存 T2/T3、状态和可分配型 Scope 的 `inherit / capped`；同一账号在不同组可以拥有不同身份和配置。不可分配 Scope 不保存组成员数值配置。
  - 账号必须通过全局当前组切换进入某一组的业务上下文；切组不改变既有项目的归属，也不自动获得其他组的业务权限。
  - 账号只能与当前组内的 ACTIVE 成员进行项目协作；不支持跨组协作、跨组 Owner 转交或跨组协作者候选。
  - 【UI交互】【UI反馈】组织 Owner/Admin 在组织业务组详情发起单组移除，在组织成员页发起组织清退；组长不能发起或撤销人员移除。单组移除只影响该组，关系先进入 `REMOVING`，立即失权但不提前改写 Owner、ACL 或配额。组长可在当前组处理本组业务交接，包括组织清退子任务，不依赖原发起人；完成后由系统按既定移除决定结束关系。2026-11-04 本条覆盖此前组长主动移出组员的结论。



- 组织所有者和有权限的管理员可以**管理组**
  - 【UI交互】创建组、修改组名
  - 【UI交互】将组织成员加入某个组；移出成员时 Admin 须满足“Admin 可移除成员”开关
  - 【UI交互】为组成员设置 T2/T3；新组关系的各可分配 Scope 默认 inherit、支付账号上限 unlimited，不在成员关系表单调整个人额度。组织管理者仅配置组上限，成员额度交本组组长配置；不可分配 Scope 只读展示组织权益状态
  - 【UI交互】将组成员设置为 T2、解除 T2 身份；每组允许0..N个 T2，不强制设置组长
  - 将组成员移除出组
    - 退组先进入 `REMOVING`，对该账号来说已经是现实退组，不能继续执行需要组身份的动作
    - 【现状差异】当前 `/ws/userRelation/setAdmin status=2` 会立即执行同步资产迁移、删除关系并把多类对象转给团队管理员；新流程进入 `REMOVING` 时不得复用该分支，最终移交也必须改为目标同组接收人和独立 `ownerUid`，不能继续改写历史创建人
    - 【UI反馈】项目留在原组；本组有效组长选择已有同组 ACTIVE 接收人并完成数据交接，不依赖由谁发起，包含组织清退中的本组子任务。CRM Assignee 单独展示，可另选同组接收人批量改派，未选最终置未分配，不强造项目 Owner。无组长且有人工决策业务时等待组织安排业务负责人，不回退为 Admin 逐项分数据；无业务处理项可组织侧确认结束
    - 【UI交互】【UI反馈】接收人必须拥有目标组有效 GroupMembership；接替不继承、不相加离职者的个人额度。已有接收关系保留自己的逐 Scope 配置、已用与占用；缺失关系按普通 inherit、个人支付 unlimited 初始化，不复活失效/退组中的关系。仍受父级限制，移交表单不提供个人 capped/支付金额快捷补权，需要调整时由获委派组长走组内配额入口
    - 【UI交互】【UI反馈】组织清退保留新邀请完整接替、已有账号增量接替、各组长处理三路径。前两条由组织 Owner 或“Admin 可移除成员”开启时的 Admin 提交后系统统一执行，无组长审批、接收人确认接替或单独“确认接替/执行统一移交”按钮；只整体替换离职者的既定有效业务关系，不开放日常业务明细或任意逐项改派。组长分办路径继续保留，不取得组织清退、邀请或补组关系能力
    - 缺组时仅补组关系；新账号接受前保持 `WAITING_FOR_TARGET`，原账号已失权，不提前转写对象责任。接受邀请是组织准入，不是移交审批；接受后校验资格/席位/组关系并自动开始移交。已有接收人提交后自动启动，不增加额外确认勾选。仅退组新增账号需正常席位；组织清退替换保留原账号释放的一个席位，校验与席位机制不因自动执行而取消
    - 接替待补 GroupMembership 默认组员，已有组身份保留，不自动继承组织 Owner/Admin 或原组长身份。唯一组长离职后可以暂无组长；第三条各组长处理路径有人工业务时须组织显式安排业务负责人，前两条整体接替不因此等待组长批准
    - 【2026-11-10 已确认】新增关系默认值可能比原 capped 更宽，影响摘要须说明，但不另设配额确认动作。“收回离职账号配额”是收回未来消费资格和个人上限配置效力，不退已消耗、不释放已有支付占用、不增加组织/组余额；普通个人上限不预占父级，旧配置/历史用量保留审计结算，不当可转回资金。三条接手路径与现行分工以统一 Input §5.7 为准
    - 整体移交只替换当前有效业务关系：目标账号已有同对象授权时去重并合并正向能力，成为 Owner/Assignee 后不保留重复 Collaborator 身份；禁用 ACL 和系统派生来源不复制。`createdBy`、历史操作与用量、既有支付 `fundingUid + fundingGroupId`、组资金账本均不改写
    - 全组织整体移交按组原子执行，失败组独立重试，全部组完成后才最终移出组织；任务页展示邀请状态、身份/配额准备、对象数量、进度、失败原因、结果摘要并发送完成通知
    - 【UI交互】【UI反馈】仅退组且尚未最终完成时可以撤销；移出组织不可撤销
    - 账号仅剩最后一个 ACTIVE 组时可以进入 `REMOVING`，但必须重新加入其他真实组，或升级为不可撤销的组织移出，才能完成该组的 `REMOVED`
  - 【UI交互】【UI反馈】组不彻底删除，改为冻结归档。归档前展示对象、任务、资金和 `REMOVING` 成员关系影响，但这些内容不阻断归档；归档组不能成为当前组、创建新对象、增加新的 ACTIVE 成员关系或执行普通业务写动作，历史数据和已形成的系统/资金责任继续按原 `groupId` 保留。
  - 【已确认】【UI反馈】非默认业务组归档须二次确认并说明不可自行恢复；不提供自助解除归档。异常数据恢复转线下处理，不作为本期产品能力；默认组不可归档。内容监控项目本身的既有归档/恢复不受此处业务组规则改变。
  - 【UI交互】【UI反馈】组织 Owner/Admin 只为普通可分配 Scope 设置组上限，不可分配项不出现输入。支付普通组显式开通并逐笔分配/归还专用余额；存量有支付权限组织默认组自动开通共享未分配可用部分，不另划专用款。关闭/归档不取消旧承诺；个人上限仍仅组长在委派允许时配置，组织资金页不越级。
  - 【UI交互】【UI反馈】账号加入目标组时，可以选择迁移该账号名下、且原本属于某个来源组的全部项目；本期不支持项目多选，也不触及其他 Owner 的项目
    - 如果账号当前仅属于默认组，必须主动询问是否迁移其在默认组名下的全部项目；不迁移则只建立新的组成员关系
    - 成员关系建立成功与项目迁移批次独立；迁移逐项执行，失败项留在来源组并可重试
    - CRM 记录不属于 Assignee 名下项目，不随 Assignee 进组或切组迁移；本版不提供 CRM 记录的组间迁移，既有记录的初始归组与权限迁移规则仍待专项确认

#### 组长

- 组织策略“组长默认成为组内所有项目协作者”开启时，组长（T2）通过系统授权来源成为本组项目的普通 Collaborator，替代线上旧的管理员强制协作；该授权只对当前组对象生效，提供常规业务读写。策略默认关闭，关闭时 T2 身份本身不产生项目权限。
- 开关开启时，T2 的系统协作来源在协作者列表中锁定勾选展示，不能被项目 Owner 手动移除；开关关闭、T2 降级为 T3 或进入 `REMOVING` 时立即失效，但同一账号的显式授权保留。
- T2 系统来源不自动获得 `can_manage_collaborators`、跨境支付 `can_execute_payment` 或模块高风险治理动作；同一账号另有显式能力来源时，系统来源与显式来源分别保留并合并正向能力。CRM 不接入系统协作，也不另给组长独立分工权；组长普通写和改派沿用 CRM 四项设置，所有来源受记录组限制；空对接人沿原管理员兼容分支计算。
- 【UI交互】组织策略开启“允许 T2 管理本组账号权限”（`t2Quota`）后，任一同组有效 T2 可以在组上限内逐 Scope 修改自己及本组成员的可分配型配置、执行本组批量增加，并设置组内支付个人上限；不可分配 Scope 仍只读继承组织权益。所有 T2 权限对等，不设置首席 T2。Owner/Admin 只有同时是该组有效 T2 且满足同一开关时才可按组长身份操作，不能以组织管理身份越级；无 T2 时由组织管理先任命 T2。
- T2 不负责 GroupMembership 的加入、移出、任免或撤销移除；这些人员决定仅由组织 Owner/Admin 操作。T2 可处理组织侧产生的本组业务交接，包括组织清退子任务，不按原发起人限制；完成后由系统执行既定关系终结，不扩大为其他组治理能力。
- 【已确认】组长不能邀请新成员；人员关系加入及邀请只由 Owner/Admin 操作，不因组长可处理本组业务交接而开放邀请。
- 有效组长可看所辖组整合、成员实际动作及所辖项目整体，不依赖隐式协作开关；个人范围仍只本人动作。Admin兼组长同页合并可用入口，不必切身份，但不越过目标组；统计不授正文或写ACL，动作排行须真实actor、自动与未知另列，不自动称绩效。



#### 组员

- 组员（T3）可以在当前组满足组织 Entitlement、GroupMembership 和对象权限的前提下，作为项目 Owner，或通过项目级 Collaborator 参与项目；可分配型 Scope 的有效可用量为 `0` 不直接撤销已有对象授权，但不能完成对应消耗型业务动作。
  - Collaborator 默认获得对象允许的常规业务读写；只读仅按模块固定可见范围表达，不进入协作者列表，不新建通用显式只读 ACL。删除、转交、归组、管理协作者等高风险动作按对象类型独立判断。
  - 项目 Owner 和组织 Owner 的旧“主账号最高权限”表述统一按当前模型解释为具体授权来源；组织 Owner 身份本身不能绕过对象组边界。
- 【UI反馈】可分配 Scope 才按“组织 → 业务组 → 该路径核算账号的组成员”逐层拦截；普通子级 capped 之和可超父级，消费时校验。inherit 不追加本层上限，每项主体/周期/返还沿 Scope 矩阵，邮件预检/落账差异独立核对，不统一 actor；不可分配项不伪造个人余量。支付不套普通超配：未开通模块不可用，开通后取钱包、适用来源可用及个人上限的最小值。普通组仅专用；迁移共享默认组仅未分配可用部分，绝不动其他组专用款。
- 【UI交互】【UI反馈】业务分组提供每组的“组配额”入口，进入明确目标组后按项展示当前上限、已用、组织剩余及新设置影响。普通组上限低于已用时允许下调，但须明确提示可用量为 0、历史不回滚；提高或改回 inherit 不重置用量和周期。现有成员上限不被自动修改，仍受父级拦截并由组长后续调整；支付另走专用余额分配和未承诺余额归还，不用普通额度编辑。



### 项目

项目型对象保留持续唯一负责人，提供**项目所有者**、**项目协作人**；是否支持主动转交依模块原业务规则，不是接入前提。邮件项目、资源夹/收藏夹、内容监控项目和支付单/草稿是接入对象；邮件和支付不提供日常主动 Owner 转交。收藏夹按三模式及 Owner 专属治理，内容监控按模块原动作权限，二者不下放名单治理；邮件名单管理按线上可再授予能力单独处理。CRM 无项目容器或协作者，仅有可空记录对接人；读写和改派沿现有 CRM 权限并加记录组边界，不套用本节项目协作或项目迁组。

项目直接从属于且只能从属于一个组，保存稳定的 `groupId`；项目同时保存唯一 `ownerUid`，不能通过 Owner 当前所在组动态推导项目归属。

【UI交互】项目创建时使用账号的全局当前组作为 `groupId`。切换当前组只影响之后创建的项目和当前业务上下文，不改变已有项目归属；创建表单展示归属组。

【UI交互】【UI反馈】访问和操作项目时，当前业务组必须切换为项目所属组；从通知、收藏或外部链接打开其他组项目时，应先明确展示目标组并要求显式切换。



#### 项目所有者（Owner）

- 项目有且仅有1个Owner，Owner拥有此项目最大权限
- 项目 Owner 必须是项目所属组内的 ACTIVE 成员；待执行具体动作时，再按相应 Scope 类型检查组织 Entitlement，以及可分配型 Scope 的组/成员上限。
- 收藏夹、内容监控等支持主动转交的对象，可转交给项目所属组内成员，不允许跨组转交。下列主动转交流程不适用于邮件项目或支付单；二者仅在账号级生命周期交接中处理负责人变化。
- 新 Owner 必须是项目所属组内的 ACTIVE 成员；缺失的可分配型 Scope 配置默认补为 `inherit`，支付账号上限默认 `unlimited`，已有组关系保持原配置。Owner 转交表单不提供个人额度快捷调整；需要改变上限时由本组组长在委派开关允许时随后配置。不可分配 Scope 只检查组织 Entitlement。可分配型 Scope 的有效可用量为 `0` 不删除对象授权，但相应消耗型动作需等额度恢复后才能执行。
- Owner 转交在同一事务中更新 `ownerUid`，并清理新 Owner 在该对象上原有的显式 Collaborator 及附加能力；其他账号的 ACL、对象 `groupId`、不可变 `createdBy` 和历史数据不变。新 Owner 若同时命中动态 T2 系统协作，权限和界面仍只呈现 Owner，不落重复显式 ACL。
- 【已确认】Owner 主动转交时不提供“转交后将我设为协作者”快捷项，不自动新增原 Owner 的 Collaborator；动态组长等其他独立授权来源仍按自身规则生效。
- Owner 主动转交不需要新 Owner 接受，也不产生待接受或双 Owner 状态。原 Owner 二次确认后同步生效；提交时重新校验双方身份和组关系，失败时整次不生效，成功后通知新 Owner 并向原 Owner 反馈结果。
- 【UI交互】【UI反馈】Owner 退组时项目留在原组，Owner 权限立即失效，进入待交接；本组有效组长可处理组织侧产生的本组交接并选择已有同组接收人，不依赖原发起人。第三条分办路径无组长且有人工业务时等待组织安排业务负责人，Admin 不越级逐项分数据。组织清退选择前两条整体接替时则按 §5.7 的有权提交后自动执行，配额不继承、不相加；等待新邀请接受与自动移交期间仍展示进度，不能将原账号失权当成任务完成。



#### 项目协作人（Collaborator）

- 项目协作人不再分 Viewer 和 Editor。Collaborator 默认具有当前业务对象允许的常规读写，不新增通用 `can_edit`；具体删除、归档、转交、归组、管理协作者和支付执行等动作另行判断，消耗型动作还需通过对应配额校验。
- 【已确认】不设置只读协作者，不建设通用对象级显式只读 ACL。模块固定可见范围和线上既有读取语义保留，读取命中者不因此成为 Collaborator，也不获得写权限。
- 【UI交互】显式协作人按模块名单治理权限设置，选取范围为项目所属组内的 ACTIVE 成员。邮件允许 Owner 和具有 `canManageMembers` 的有效正式协作者维护名单，并保留再次授予该能力；收藏夹与内容监控名单仅 Owner 可设置，不提供该附加能力。其他允许委派的模块仍按各自不可传递约束，不从邮件例外类推。
- 【UI反馈】组长默认协作开关开启时，项目所属组的 ACTIVE T2 通过系统授权来源成为协作人；该来源不需要逐项目写入 ACL，不因组织 Owner/Admin 身份自动产生。协作者列表锁定展示该授权来源；开关关闭时不展示、不生效。
- 邮件名单管理员沿现状可继续授予/收回 `canManageMembers`，不受旧通用“非 Owner 不可再授予”限制；普通协作或固定读取来源不自动获得它。收藏夹与内容监控 Owner 仍不能下放名单管理，支付 `can_execute_payment` 等其他能力不因邮件例外被放宽。组织 Owner/Admin 身份本身不产生这些对象权限，具体管理动作仍按模块及动作矩阵判断。
- 不允许跨组协作。账号即使同时加入其他组，也必须在当前项目所属组保持 ACTIVE GroupMembership，才能成为候选协作者或使其显式对象授权生效。
- 【UI交互】【UI反馈】项目迁移时，不属于目标组 ACTIVE 成员的显式 Collaborator 和附加能力不删除而是整体禁用。成员之后加入目标组且满足组成员关系等硬限制时，原授权自动恢复；可分配型 Scope 的有效可用量为 `0` 只阻断消耗型动作，有权账号显式删除后不再自动恢复，删除前需二次确认。



#### 跨项目资源

跨项目资源通常指某个功能下的通用资源/配置，可由所有此功能下的项目访问使用。比如内容监控功能的“监控项标签”。



- 跨项目资源在组内共享，跨组隔离。
  - 项目迁移到另一组时，资源引用随项目逐项检查；本期只支持 Owner 名下项目整批迁移，失败项留在原组并可重试。
  - 对象授权中不属于目标组的协作者和附加能力不删除而是禁用，目标成员之后进组且满足硬限制时自动恢复；显式删除后不再自动恢复。
- 跨项目资源的共享定义和具体项目内应用分开鉴权。
  - 内容监控/视频监控的共享标签定义受组织全局开关限制：默认关闭；开启后 Owner/Admin 和任一有效 T2 可创建、改名、删除，T3 不能执行定义动作。
  - 标签应用仍按具体项目的 Owner/Collaborator 或模块普通写范围判断；仅有查看权限的账号不能应用标签，不因标签定义管理权获得项目权限。
- 消息标签继续组织共享，返回 `creatorUid` 和 `createdGroupId`，筛选为“我创建的 / 当前组成员创建的 / 全部”。筛选只改变列表结果，不改变标签权限；创建者离组后历史标签仍留在原创建组来源，不随账号漂移。
- 【UI交互】频道历史收款信息按组织共享快捷模板设计，不是支付业务记录。所有具备有效业务资格的组织成员可维护；按频道检索、同频道允许多条不同版本/记录且去重，精确去重键留 Spec。选用模板不授予来源支付单访问；已保存支付单保留独立收款信息快照，模板改删不回写。共享范围不改变资金归属和额度校验，不另建复杂版本审批体系。
- 【2026-11-10 已确认】消息中心按上文“邮件邀约和消息”保留原访问、精确对话委派、发件身份和扣量，新增组隔离而非新会话 ACL。聚合卡片、未读、检索及状态也需组隔离，不只是对话正文或选人过滤；未实测及生命周期差异单列研发核验。旧任务列表不纳入本版，尽量不改、默认全组织可用；不等同于新 Campaign/智能营销计划，也不借例外扩张其他项目权限。
