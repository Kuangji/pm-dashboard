# Pre-input v0 · 内容监控二期（v7.6.1）

> 状态：讨论底稿，不是正式 input。
> 目的：帮助 PM 组织 761 的问题空间。

## 1. 目前可讨论的中心问题

761 可能不是“继续补几个页面”，而是要回答：

> 内容监控在 760 完成创建链路后，接下来要如何成为一个能支撑项目复盘、评论洞察和持续追踪管理的工作台？

这个问题还没有被正式拆成需求，需要讨论。

## 2. 候选问题空间

### 2.1 整体交互与视觉重构

可讨论点：

- 项目详情页是否是 761 的主战场？
- 全局监控列表是否需要重做信息层级？
- 任务详情抽屉是否要升级成“单条内容报告页”？
- 自动追踪规则管理是否只做解释增强，还是要重构入口？

### 2.2 Dashboard 与关键指标

可讨论点：

- dashboard 是项目级复盘，还是日常监控看板？
- 默认指标应该服务谁：运营、PM、客户汇报，还是数据分析？
- 现有指标池哪些应该默认展示，哪些放进自定义？
- 成本/回报类指标是否已有足够数据质量支撑？

### 2.3 评论抓取与评论分析

可讨论点：

- 用户说“更多评论抓取”，具体是数量更多、平台更多、频率更高、历史回溯，还是评论维度更细？
- 评论分析优先做情感、高频词、代表性评论，还是风险预警？
- 评论是否进入列表、详情、dashboard、报告，还是只在详情里展示？
- 评论抓取是否需要套餐、配额或手动刷新限制？

### 2.4 更详细分析报告

可讨论点：

- 报告是给站内查看，还是导出给客户？
- 报告按项目生成，还是按单条内容生成？
- 报告是否必须包含评论洞察？
- 报告是否要解释自动追踪来源和规则贡献？

### 2.5 知识库喂入

可讨论点：

- 761 需求讨论过程中的哪些内容应该作为知识库输入？
- 哪些是事实，哪些只是需求意图？
- 上线前和上线后是否要分成两次 promotion？

## 3. 暂存假设池

这些是假设，不是结论：

- 假设 761 重点应落在项目详情页、全局监控列表、任务详情抽屉。
- 假设评论能力要先解决“为什么没数据/抓了多少/何时更新”的解释问题，再谈高级分析。
- 假设报告能力需要先有项目级报告，再考虑单条任务报告。
- 假设自动追踪的来源解释会影响 dashboard、列表和报告。
