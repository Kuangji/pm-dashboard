## 1. 处理方法

本轮把反馈池当作原始证据源处理，而不是直接照搬表格中的 `状态`。

交叉验证来源：

- Excel 原始反馈：89 条非空记录。
- 反馈截图：工作簿内共解析出 82 张 `DISPIMG` 截图，已抽取到 `feedback_screenshots/`，正文以截图 ID 标记。
- 当前线上事实：只读访问 `/video-monitor/monitor-list`，确认当前全局监控列表已展示 dashboard、表格、批量选择、字段列和部分跨项目数据。
- 已沉淀事实：`current_state_facts_v0.md` 与 M08 知识库输入。
- 前端代码：`kol-next` 的 `videoMonitor` 页面、组件和 API。

判断口径：

- `已满足 / 基本已满足`：线上或代码已有主要承载，反馈可能已过期。
- `部分满足`：已有入口或字段，但导出结构、排序、口径、权限或数据同步仍未确认。
- `仍有效`：当前事实未覆盖，且与 761 方向相关。
- `依赖外部/后台`：前端可承载，但需要数据组、后端、套餐、权限、平台数据源或导出服务确认。
- `不建议纳入 761`：偏创建链路、平台扩展、权限治理、自动追踪重管理、独立报告系统或长期 AI 能力。

### 2.2 对 761 最有价值的输入

反馈池验证了一个判断：761 不应只做视觉翻新，用户真实痛点集中在“按时间看增量、按维度汇总、解释为什么数据为空或不准、把结果拿出去复盘”。

最值得纳入 761 input 的主题：

1. **按监控时间区间看增量，而不是只按发布时间筛选内容**
   行 20、36、39、47、72 指向同一类问题：用户要看某段时间内已有内容产生了多少新增效果。

2. **项目维度 dashboard 需要有内容/达人/频道贡献，而不只是累计 KPI**
   行 8、17、32、38、46、47、55、57、66 都在要求更强的汇总和解释能力。

3. **评论和高频词是强反馈，但数据能力不可控**
   行 2、17、32、46、55、65、84 均提到评论、高频词、情感或导出。当前已有详情抽屉展示位和接口痕迹，但样本为空态，因此 761 应做“已有数据的展示与低数据解释”，评论抓取和完整评论报告仍放 TODO/backlog。

4. **短链和成本类指标容易误解，需要明确数据状态**
   行 21、23、31、40、41、64、73 指向短链同步、点击口径、预算/币种、CPV 计算等问题。它们支持当前 input 中“手填成本指标与采集指标分层”的原则。

5. **列表/跨项目视图不是要废掉，而是要降级并统一口径**
   行 4、35、76、88、90 说明老用户仍然需要跨项目查看、筛选、导出和批量操作。761 的 IA 方案应保留跨项目视图，但不再让它与项目列表平级争夺主心智。
