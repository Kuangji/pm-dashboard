# Pre-input Decisions v0 · 内容监控二期（v7.6.1）

> 状态：pre-input 讨论记录，不是正式 input。  
> 来源：基于 `current_state_facts_v0.md` 与 2026-05-07 需求讨论沉淀。  
> 用途：作为后续生成正式 `input_v1.md` 的决策底稿。

## 1. 版本定位

761 是混合型迭代，但以 **复盘能力** 为主。

更准确地说，761 不应被理解为“重型结案报告系统”，而是把内容监控从“能创建、能看列表”推进到“能直观看当前/近期项目状态，并能按需解释结果”。

本期三条轴线：

- 主轴：近期快照与复盘解释能力。
- 辅助轴 1：项目详情页、任务详情抽屉和列表的信息架构/视觉体验重构。
- 辅助轴 2：来源、进度、自动追踪、评论空态等可信度解释。

## 2. 用户角色

### 2.1 主决策用户

PM / 项目负责人是主决策用户。

他们需要判断项目效果、内容贡献、创作者贡献、平台表现，并能讲清楚“当前监控结果说明了什么”。

### 2.2 高频操作者

投放运营是高频操作者。

他们负责日常查看、筛选、维护标签/备注、处理内容异常、查看自动追踪新增内容，并保证项目数据处于可解释状态。

### 2.3 结论消费者

客户成功、销售、客户本人是结论消费者。

他们不一定直接操作系统，但会消费 PM/运营整理后的结论、截图、站内页面或后续可能出现的导出物。

## 3. 核心场景

默认场景是 **进行中快照看板**。

用户打开项目详情页时，第一眼要看懂最近 7 天项目表现如何。它不要求用户进入一个正式复盘动作，而更像运营/PM 的项目体检面板：

- 现在跑得怎么样？
- 哪些内容近期爆发或下滑？
- 有没有数据异常？
- 近期规模和互动质量如何？
- 哪些内容和频道贡献最大？

阶段性复盘和结案式分析通过筛选切片按需触发，例如选择日期范围、选择特定内容、选择频道/创作者，再汇总对应数据。

## 4. Dashboard 决策

### 4.0 看板成立性

现有内容监控指标足够撑起一个轻量但独立的项目看板区域，但不足以撑起品牌分析那种重型策略看板。

761 应采用“现有指标再组织 + 少量派生指标”的方式升级 dashboard：

- 把观看量、互动率、内容数、活跃内容数组织成近期状态摘要。
- 把任务级数据组织成内容级爆发/下滑/数据异常榜。
- 把内容/频道/平台聚合成贡献分析。
- 把评论、短链、预算/成本输入、自动追踪来源组织成数据可信度提示。

品牌分析的可借鉴点是“指标卡 + 分布/排行 + 趋势 + 异动提示”的信息结构，而不是照搬其复杂矩阵、AI 评估或策略报告。

### 4.1 默认时间窗口

Dashboard 默认展示最近 7 天。

用户可以通过日期选择器切换到累计、最近 30 天、项目全周期或自定义区间，用于阶段性/结案式分析。

### 4.2 第一屏优先级

最近 7 天快照的第一屏优先级为：

1. 内容级异常变化。
2. 项目表现规模。
3. 内容/频道贡献。

其中异常变化优先识别：

- 爆发内容。
- 下滑内容。
- 数据异常内容。

停滞内容和自动追踪异常暂不作为 dashboard 第一优先级。

### 4.3 内容级变化识别

内容级变化识别先用占位规则，不在本轮强行定义复杂算法。

占位规则：

- 默认按最近 7 天观看量增量识别爆发/下滑。
- 互动量增量作为第二参考。
- 评论、短链点击、综合分暂不作为默认排序指标，但可以作为辅助信号展示。

需要单独研究的子 topic：

- 最近 7 天应该与哪个时间窗口比较。
- 是否需要阈值、环比、同项目均值或频道历史均值。
- 是否排除刚发布或数据不足内容。
- 如何解释变化原因。

### 4.4 默认指标与可配置指标

默认主指标：

- 观看量。
- 互动率。

副指标：

- 点赞数。
- 评论数。
- 分享数。

可配置指标池：

- Nox 短链点击数。
- 预算消耗。
- CPM。
- CPV。
- CTR。

指标设计应延续现有“自定义数据”能力，支持不同用户按项目目标配置关注指标。

预算、预计花费、预算消耗等成本类数据是用户手动填写的输入数据，默认未填写；CPM、CPV 等指标依赖这些输入，不应与观看、点赞、评论、分享等平台采集指标同等默认展示。

### 4.5 贡献分析

内容贡献与频道/创作者贡献都需要，但默认先展示内容贡献。

频道/创作者贡献作为聚合切换或二级视角，用于回答“哪些 KOL/频道拉动了最近 7 天表现”。

### 4.6 项目列表速览

项目列表一级页面应增加“近期、快速”的项目速览，但不应变成第二个 dashboard。

项目卡片默认建议展示：

- 最近 7 天观看量。
- 最近 7 天互动率。
- 异常内容数。

可作为展开/辅助信息：

- 活跃监控内容数。
- 自动追踪新增内容数。

项目列表顶部可以提供跨项目轻量总览，例如进行中项目数、最近 7 天总观看量、最近 7 天活跃内容数、需要关注的项目数，但需要避免削弱“项目列表 -> 项目详情”的主层级。

## 5. 评论能力决策

评论抓取数量、覆盖平台、刷新频率等能力提升先进入 TODO/backlog，因为依赖数据组抓取能力，当前不可控且无明确预期。

761 如涉及评论，只做已有数据上的分析价值和空态解释。

优先位置：

1. 任务详情抽屉。
2. 内容列表。
3. Dashboard。
4. 报告。

其中任务详情抽屉承载较完整的单条内容评论洞察；列表只展示轻量信号，例如情绪/风险/样本状态。Dashboard 与报告中的项目级评论洞察暂不作为第一优先级。

评论低数据或无数据时，需要为用户留出解释空间，避免让用户误以为系统异常。

## 6. 报告能力决策

761 不优先做独立报告形态。

本期先通过项目详情页和任务详情抽屉增强，让站内页面本身具备“可复盘、可解释、可截图/转述”的报告感。

PDF、Excel、图片导出或报告生成器，除非后续出现明确形式需求，否则进入 backlog。

## 7. 页面范围优先级

页面范围优先级为：

1. 项目详情页整体。
2. 任务详情抽屉。
3. 全局监控列表。
4. 自动追踪规则管理。

项目详情页承接最近 7 天快照和切片分析；任务详情抽屉承接单条内容解释；全局监控列表主要服务运营跨项目排查；自动追踪规则管理不作为本期主战场。

### 7.1 信息架构原则

内容监控的主层级应强调“项目列表 -> 项目详情”。

现有“项目列表 / 监控列表”平级 Tab 容易让用户误解内容监控的主心智：内容监控不是先有一个总内容库再分项目，而是以项目为组织单元的监控工作台。

761 中，原“总监控列表”应从项目列表的平级主功能降级为“跨项目监控内容视图”：

- 项目列表仍是默认入口。
- 项目详情是主工作台。
- 跨项目视图保留，用于老用户延续习惯和运营跨项目排查。
- 跨项目视图允许默认全部项目直接进入。
- 项目列表多选后，也可以进入同一个跨项目视图，并默认筛选所选项目。
- 跨项目视图的内容与交互应贴近单项目详情中的内容列表，而不是另起一套完全不同的信息模型。

具体入口形态在 design 阶段再定，可以是项目列表工具区的弱化入口、二级页面、抽屉或其他形式；pre-input 阶段只确认主从关系和迁移原则。

## 8. 自动追踪决策

760 已经完成较多自动追踪相关内容，且当前设计把规则管理主要收束在新建监控抽屉中。

761 不把自动追踪做重，不把规则管理从创建抽屉中外溢。

本期自动追踪只做到任务来源解释：

- 列表/卡片/详情中显示内容来自自动追踪。
- 最多展示对应规则名。

不在抽屉外展示或重构：

- 规则状态。
- 监控词。
- 频道。
- 续期。
- 暂停/继续。
- 删除。
- 复杂规则配置。

## 9. MVP 范围

### Must

- A. 项目详情页 dashboard：最近 7 天快照、异常变化、规模指标、贡献分析。
- B. 项目详情页内容列表：来源/进度/异常/指标展示优化，支持切片筛选。
- C. 任务详情抽屉：单条内容数据总览、趋势、评论分析/空态、来源规则名。
  - 补充：项目列表卡片增加最近 7 天观看量、互动率、异常内容数，作为一级页面速览。

### Should

- E. 全局监控列表：字段口径和筛选体验统一，不做大重构。
- F. 自动追踪来源解释：来源为自动追踪时展示规则名。
- G. 指标配置：默认指标 + 可配置指标池。
  - 补充：全局监控列表在 IA 上降级为跨项目监控内容视图，保留默认全部项目入口。

### Backlog

- D. 评论分析增强：已有评论数据的情感/高频词/代表性评论/风险信号。
- H. 独立报告/PDF/Excel/报告生成器。

## 10. 后续进入 input 前还需确认

- 最近 7 天内容级爆发/下滑的占位规则是否足以支撑第一版 dashboard。
- 内容列表中的来源、进度、异常、指标展示需要具体到哪些字段。
- 任务详情抽屉里的评论空态解释应如何表达。
- 指标配置是否完全复用现有自定义数据能力，还是需要新配置入口。
- 跨项目监控内容视图的入口形态：项目列表工具区弱入口、二级页面、抽屉，还是其他方式。
- 项目列表顶部跨项目总览是否要做，以及做到什么程度才不会削弱项目列表主心智。
