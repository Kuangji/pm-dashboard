# 主子品牌关系、计算与展示：候选形式比较 v1

2026-11-17（Asia/Shanghai）｜状态：候选讨论稿，未选型，非正式 Input / Spec / Design。

本轮目的：梳理主品牌、子品牌及相关产品线/事业群的关系，比较如何形成可信的总体、保留分项并下钻解释。定制视图服务这条主线，不扩展为通用 BI、工作区治理或任意图表编辑器。

依据：[首轮竞研](../调研报告_v1.md)、[第二轮界面深挖](../deep_dive_2026-11-17/界面与操作深挖报告_v1.md)。下面三种形式是面向聚星任务的推演，竞品只提供局部参考，没有一家被证实完整实现了这些组合。

## 1. 候选比较先固定的对象

### 品牌关系与数据归属分别维护

- **品牌关系**回答“子品牌 A 是否归入主品牌 P、从哪一层向上汇总”。品牌改名、别名、社媒账号和跨平台标识要与这一业务关系区分。
- **内容归属**回答“这条内容命中了哪些品牌或产品线”。同一条内容可以涉及多个子品牌，不能因品牌只有一个上级就强行把内容分成互斥集合。
- **汇总关系**把下属内容纳入上层范围，但不新增一次原始品牌提及。父节点获得子品牌内容，不要求内容再次出现父品牌名称。
- **统计分组**回答“本次想把哪些对象放在一起看”。地区、事业群等可能既是组织结构，也可能只是分析维度，不能只凭名称确定其类型。

### 主品牌的两种数字必须分开

1. **主品牌直接提及**：直接命中主品牌自身识别条件的内容，可与子品牌内容重叠。
2. **品牌家族汇总**：主品牌直接命中与纳入范围的下属品牌/产品线内容，合并后计算。

若上层仅是事业群或统计容器，没有独立识别条件，就只汇总成员；不能伪造一份“事业群直接提及”。父品牌尚未覆盖也不能直接记为零。产品线是否已有独立数据对象、能否准确识别，仍需验证。

关系的共享范围也暂不定：平台维护的公共品牌事实、客户维护的业务结构、个人分析选择应可区分。客户自定义关系不自动写回公共品牌库。

## 2. 三种候选形式

| 维度 | A：主品牌关联包（两层） | B：固定多级品牌结构 | C：品牌结构＋独立统计分组 |
|---|---|---|---|
| 核心对象 | 一个主品牌与一份明确关联清单 | 可复用的多级关系结构 | 一份品牌归属结构，外加不改变归属的统计分组 |
| 关系怎么维护 | 选择主品牌，逐项加入子品牌/产品线，注明关系含义；包内只保留一层 | 明确节点类型和上下级；品牌/产品线可有直接数据，容器节点只聚合；约束循环和重复路径 | 品牌归属在结构中维护；地区、事业群或其他切片另以成员清单/属性条件维护 |
| 怎么计算总体 | 展开关联包，合并主品牌直接命中与成员内容后去重 | 展开所选节点全部后代及其直接数据，同一内容/达人在每个节点内分别去重 | 展开结构及分组范围，解析为确定的数据集合，再计算；多分组可以重叠 |
| 总量和分项怎么组织 | 一份家族总体，下面是各成员行；主品牌直接提及另示 | 任一节点可作为当前总体，下一层作为分项；保留路径和当前范围 | 主线仍是树的总—分；可切换某个具名分组查看相同口径的总体/分项 |
| 怎么下钻 | 成员行→该品牌内容/达人；总体→合并内容/达人 | 总体→下一层→具体品牌/产品线→内容/达人 | 从结构或分组分项进入内容/达人，同时保留当前结构/分组及过滤条件 |
| 定制视图主要保存 | 关联包/成员版本、分析条件、指标、排序 | 根节点、关系版本、展开层级、分析条件、指标、排序 | 结构节点＋统计分组及其版本、范围组合/展开规则、独立数据过滤、分项维度 |
| 适用场景 | 明确的主品牌＋少量子品牌；优先解决几个离散品牌合起来看 | 集团—事业群—品牌—产品线多层反复使用；用户经常逐级找原因 | 品牌归属稳定，但同一品牌还要按地区/业务单元等交叉分析 |
| 主要代价 | 包与包之间可能重复维护；复杂组织扁平化；不能自然逐层展开 | 关系录入、纠错、变更历史、容器定义与迁移成本高；单树不擅长交叉归属 | 同时维护归属与统计分组，最容易出现重叠分项、范围误解和历史漂移 |

这里的代价是产品与数据维护的定性判断，不是工期或性能估算。**三种形式都需要可靠的多品牌合并与去重计算，A 不因界面简单而自动省掉这部分代价。**

### A：主品牌关联包

关系示意：`主品牌 P → {子品牌 A、子品牌 B、产品线 L}`。

用户先建立要观察的品牌家族范围，随后反复打开同一份总—分视图。每个成员仍保留独立身份与原始数据，不复制成一个新的采集品牌。可以表达“这些对象属于本次主品牌分析范围”，但不冒称已经完整维护集团组织。

若需要看事业群，可另建一份包；包与包没有自动父子继承。它比普通品牌对比多了明确的主品牌、关联含义和合并总体，但对三层以上的关系表达较弱。

适用假设：主要痛点是少数关联品牌之间的数据离散，用户无需长期管理复杂层级。若同一份层级要被多个包反复抄写，维护成本会快速增加。

### B：固定多级品牌结构

关系示意：`集团容器 G → 事业群 D → 主品牌 P → 子品牌 A → 产品线 L`。这是候选示例，不要求所有客户都具备这些层级，也不要求品牌与公司法律架构一致。

所选节点提供家族汇总，下一层提供分项；点击某一分项时，它成为新的总体。节点的直接提及与继承下属的数据需要可区分，防止把同一内容重复算进自己和孩子。

本候选先按一个清晰的主要上级表达业务归属；如果真实客户存在多上级，需先确认它是多重归属，还是不同统计视角。直接允许任意多父节点会引入重复路径、循环及贡献解释成本，不能仅靠树控件解决。

适用假设：层级本身是用户反复分析和沟通的语言。其主要价值是关系可复用、逐级汇总和下钻清楚；主要风险是先建立了一棵看似准确但实际维护不动的树。

### C：品牌结构＋独立统计分组

关系示意：品牌归属仍按 B 维护；另有`北美业务负责的品牌组={A、B}`、`某业务观察范围={A、L}`等分组，成员可交叉。组名描述业务成员，不代表已经筛选这些品牌的北美内容。

该形式保留主子品牌结构，同时容纳地区/业务单元等跨层选择。统计分组不改变品牌的主要归属，保存分析视图也不自动修改结构。若一个事业群确实是主要归属节点，放在结构中；若是交叉统计范围，就放在分组中，而不是两边随意复制。

分组总体仍是合并去重结果。分组之间的比较不保证可相加，界面须区分“各组相关表现”与“整体贡献分解”。动态属性组还需要预览实际成员并留存版本，否则同名视图在不同日期可能覆盖不同品牌。

**为使本轮计算可比较，C先采用一组明确的演算假设，不作为最终默认规则：**

- 当前树节点展开为其自身及下属的数据对象集合；统计组只列明具体品牌/产品线成员，不因选中一个祖先就默默加入全部后代。
- 当前根范围与组成员**取交集**后，再应用日期、平台、地区等数据过滤，并在实际内容集合上合并去重。组中其他根下面的成员不自动带入。
- 例如P的范围为`{P、A、B、L}`，组成员为`{A、B、X}`，X不属于P。本例最终只取A/B，按后文数据是160条，标题应为“所选子品牌A/B汇总”，不能仍称P全家族185条。
- 若还要看某地区数据，须另应用具有明确业务含义的地区条件。仅选名为“北美业务”的品牌组，并不能证明内容来自北美；地区字段指达人所在地、内容来源还是目标市场也需核对。
- 并集、直接替代根范围、以及组内祖先自动展开都是其他可能策略，会改变结果；若继续比较它们，要分别命名并保存解析方式，不能在同一视图里含糊切换。正式默认仍待确定。

因此C保存的不只是组名，还包括成员/条件版本、根范围、范围组合与展开规则，以及独立的数据过滤。

适用假设：客户同时需要稳定归属和多维切片；主要代价是双重模型的认知与维护负担。不能为了模仿企业级看板，提前把所有任意分组和公式配置纳入范围。

## 3. 三种候选共用的计算约束

下面是为了公平比较候选而提出的计算要求，**尚未确认为聚星生产规则**。实际单位、时间定义、指标公式和服务端实现仍须逐项核实。

### 总体先确定集合，再计算指标

在相同日期、平台、地区等过滤条件下，对品牌 P 定义：

`家族内容集合 = P 的直接命中内容 ∪ 本次纳入的全部下属内容`。

内容以稳定的内容身份去重，不能仅把各品牌已经汇总的数字相加。候选去重键可从`平台＋内容ID`出发；它表达平台内发布内容，不能自动识别跨平台转载的“同一素材”。整体与分项应采用可对齐的数据批次/截至时间。

| 指标类型 | 总体的比较口径 | 不可直接沿用的简化 |
|---|---|---|
| 内容数 | 对总体内容集合计数；品牌分项保留各自相关内容 | 多品牌内容数之和当去重总量 |
| 达人/频道数 | 对总体内容涉及的频道身份去重；跨平台同人需独立映射证据 | 同一人在不同平台直接认成一个达人；直接相加各品牌达人总数 |
| 播放、互动 | 在去重后的内容集合上按同一字段/快照聚合 | 同一条多品牌内容的播放/互动被累加多次；把播放量称独立触达人数 |
| 比率、均值、中位数 | 按各指标定义从总体数据重新计算 | 平均各品牌参与率，或平均品牌中位数作为总体中位数 |
| 花费、估值、触达 | 单独核对来源、归因与共享记录；不足时先保留分项 | 以内容去重替代费用归因，或把账号受众之和当去重人数 |
| 趋势 | 每个时间桶按同一成员/关系口径计算；时间字段含义一致 | 对齐了日期标签就假定发布时间、发生时间及快照一致 |

增加无有效数据/未覆盖的成员不应悄悄成为“完整家族总量”。需要区分真实零值、采集未覆盖、数据不完整与历史不支持；不得以补零制造完整感。

### 统一虚构样例：三个候选都应解释得通

数据仅用于解释集合关系，不是聚星或竞品实测：

- 子品牌 A 相关内容 100 条，B 为 80 条，二者共有 20 条。
- 主品牌 P 名称直接命中 40 条，其中 15 条也在 A/B 内容集合中。
- 所以家族去重总体为 `(100 + 80 - 20) + (40 - 15) = 185` 条。

| 正常分项阅读 | 数量 | 解释 |
|---|---:|---|
| 家族去重总体 | 185 | 整个范围的唯一内容数 |
| A 相关内容 | 100 | 包含同时与 B 相关的内容 |
| B 相关内容 | 80 | 包含同时与 A 相关的内容 |
| P 直接提及 | 40 | 其中15条同时涉及子品牌，不可再完整累加 |

这些分项用于理解各品牌表现，合计不应硬凑为185。如果要展示可相加的内容构成，可单独分解为：

| 互斥内容构成 | 数量 |
|---|---:|
| 仅涉及 A 的子品牌内容（不涉及 B） | 80 |
| 仅涉及 B 的子品牌内容（不涉及 A） | 60 |
| 同时涉及 A 与 B | 20 |
| 只直接提及 P、不涉及 A/B | 25 |
| 合计 | 185 |

前两行仍可与 P 的直接命中重叠；“仅”限定在 A/B 之间，不表示完全不提 P。两套表是不同阅读方式，不要把第一套直接画成各项合计100%的堆叠图或贡献饼图。

不在本轮选择“按归因次数”“等分分摊”或“指定主要品牌”来凑齐贡献。这些会改变业务含义，需要单独讨论；默认也不因为品牌结构有单上级，就把共同内容强制归给一个子品牌。

## 4. 总—分展示应怎样与关系对应

三种候选的共有阅读链是：**我在看哪一组关联品牌 → 去重总体 → 各品牌/下一级相关表现 → 贡献内容与达人**。下面是信息组织讨论，不是页面布局定稿。

1. 当前范围必须能被读出：主品牌/节点、纳入哪些成员、关系或成员版本、日期与平台过滤。
2. 总体和主品牌直接提及分别命名；统计容器不假装是一个独立品牌。
3. 分项默认保留业务关系与相关数据；涉及交叉时解释不可相加，并提供共同内容的查看路径。
4. 点击分项进入明细时保留相同的有效范围与过滤。不是仅保留标题，而是数据内容也应吻合；第二轮Meltwater实际样例的日期显示差异提示这一点需要验证。
5. 切换到一部分子品牌时，明确现在看的是“所选子品牌汇总”，不能仍把它叫整个品牌家族的总量。

候选差别在第一个动作：A打开一个关联包；B选择树节点；C在树节点上叠加统计分组。后面的统计解释与明细闭环应保持一致。

## 5. 定制视图到底保存什么

优先保存可重现的分析定义，而不是先做自由画布：

| 保存层 | 三种候选都需要讨论的内容 | 与其他对象的边界 |
|---|---|---|
| 关系/范围 | 主品牌/根节点；关联包、成员或分组；引用版本及是否跟随更新 | 保存视图不等于改品牌归属 |
| 统计条件 | 平台、地区等过滤；时间窗口、时区及相对/绝对时间 | “最近30天”回访会变，不是固定结果快照 |
| 计算解释 | 引用的汇总/去重口径版本；相关表现或互斥构成的阅读方式 | 不开放随意相加公式来掩盖交集 |
| 展示选择 | 分项层级/维度、指标、排序、展开状态 | 卡片可见性只是展示偏好，不是数据关系 |

两类保存行为需区分，暂不选默认：

- **跟随关系更新**：引用当前关联包/结构/分组，适合持续监控；需让用户知道成员变了，历史复看可能采用新的结构解释。
- **固定分析定义**：固定成员或关系版本及过滤，适合固定口径复盘；若底层数据仍更新，数字仍可能变化。要保留某日数字还需另行保存结果/导出，不能把固定成员叫数据快照。

关系调整后的历史按当前归属重算，还是按当时归属解释，是另一项待定政策，不能由“保存视图”按钮偷偷决定。共享视图也不能扩大底层品牌权限；父级汇总遇到部分授权时采用何种阅读范围，后续需单列核验，本轮不扩展账号权限设计。

## 7. 聚星当前静态证据与共同工程代价

本轮对新旧服务端做了有限只读核对，详见[静态基线](../evidence/nox_brand_static_baseline_2026-11-17.md)。已经读到多`pkIds`参数，以及按平台、品牌分别返回的批量统计；这不等于已经具备家族去重总体。单品牌统计还涉及视频/平台去重、频道归并与sum/avg/percentile等不同运算。

因此三种候选共同需要确认：品牌标识和产品线范围映射；集合解析后的去重聚合；跨品牌交集的保留；整体/分项的过滤和数据批次一致性；关系/视图版本对历史的解释。

本轮没有接口、线上或真实数据实测，也没有前端页面验收。不能据有限检索断言聚星已有/没有品牌关系模型，不能给工期或直接复用承诺。

## 8. 如何继续比较，而不提前选定

| 如果真实任务主要是… | 值得优先验证的候选 | 验证它的关键问题 |
|---|---|---|
| 将几个已知子品牌聚合给管理者看 | A | 两层是否足够；同一成员是否被多个包重复维护 |
| 沿固定组织层级反复下钻、解释总量 | B | 层级是否真实稳定；谁维护；产品线/事业群是否确有数据与节点含义 |
