## 1. 版本目标和阅读口径

在一期底层替换生效的前提下，把组织事实变成用户能实际使用的完整产品：组织成员管理、业务分组、权限策略、项目协作、普通配额、支付资金限制、成员与数据生命周期，以及按组和账号查看的使用情况看板。

本版闭环是：配置组织与分组 → 引入和分配成员 → 设置能力与配额 → 在业务模块中协作和消耗 → 查看使用与业务结果 → 调整配置、迁移或清退成员 → 保留历史归属与审计。

组织、权限、资金和统计共用同一套企业、组、成员及对象事实。研发可以按依赖并行开发、分模块验收和灰度，但不以独立后续版本承接本版尚未做完的必要环节。

本文使用四类状态：

- **本版交付**：已有目标规则，或属于用户本次明确新增范围；仍需细化 Spec 与实现。
- **本版待确认**：留在本版问题清单中收口，不能解释为已获批的具体方案，也不能直接标成后续版本。
- **回归**：一期或既有实现已覆盖，验证与新组织模型兼容。
- **已否决/历史废案**：只留追溯，不恢复为需求。

## 2. 一期与本版的边界

### 2.1 按一期已生效规划，不重复立项

| 一期承接的基础 | 本版使用方式 | 接收证据 |
| --- | --- | --- |
| 企业、默认组、企业成员和组成员四张基础表 | 从统一组织事实读写组织与业务上下文 | 一期实际交付清单、接口和迁移验收 |
| 业务资源企业归属与已确认的组承载字段 | 用户创建、查看、协作与迁移时使用稳定归属 | 逐表映射与异常清单 |
| 企业权益、会员和旧接口兼容 | 保持套餐归属与组织总额，补组/成员约束 | 权益及配额兼容验收 |
| Owner/Creator 字段适配及兼容约束 | 根据对象模型计算权限，不从字段名称猜身份 | 模块字段语义与兼容白名单 |
| 一期已经交付的离职任务、身份和会话适配 | 复用其能力，补本版产品流程和缺口 | 状态、任务、模块覆盖及失败处理清单 |

“一期已生效”是本次规划前提，不代表本轮已完成上线核验。仅有建表、字段或预留列，不能标记为本版业务能力已完成。研发附件引用的 `account-data-change-phase1.md`、`account-init-four-tables.md` 等配套材料尚未作为完整证据包纳入本项目，需要接收实际交付版。

### 2.2 本版承接全部用户可感知与必要适配

一期只启用默认组，与本版支持多组并不矛盾；新表已有 `parent_id` 预留，也不代表组级配额已经生效。凡涉及新建业务组、多组身份、跨模块权限、分组消费、移交或历史统计的新增行为，均须在本版完成相应接口、鉴权和产品流程。

具体指标来源不足时应留为本版待核验，明确补数、记录新事件、限定历史范围或调整指标的方案。不能把缺失数据当 0，也不能因为第一期没有历史多组数据，就取消目标多组能力。

## 3. 根模型沿用与上次草案修正

### 3.1 沿用已确认目标

- 组织有唯一 Owner、0..N Admin，其余为 Member；组织身份与业务组身份解耦。
- 【2026-11-10 已确认】Admin 采用全组织管理，不配置逐人管理组范围或范围重叠。Admin 可邀请成员、创建组；组织策略另设“Admin 可移除成员”和“Admin 可归档组”，均仅 Owner 可配置、默认关闭。前者控制移出组织及移出某组、撤销尚未完成的单组移除、组织侧确认无业务项的关系结束；不限制有效组长处理既有本组业务交接，不能通过换入口绕过。后者不代表彻底删除组；Owner 不受这两个开关限制，Admin 不能自行开启。全组织管理不授予业务对象权限，其余动作仍按具体矩阵收口。
- 同一账号可加入 1..N 个业务组，每条 GroupMembership 独立保存 T2/T3、状态和可分配配额；每组允许 0..N 个 T2。
- 项目型对象固定归属于一个组，保留唯一业务 Owner；CRM 不建项目容器，同一达人可在不同组分别维护独立业务记录。记录对接人是可空、可转交的业务负责人（Owner/Assignee），达人基础资料共享。
- 全局当前组决定新建对象及无对象业务动作的上下文；已有对象始终按自身稳定组鉴权。
- 不支持跨组协作、跨组直接转交Owner；本期不支持项目迁组，加入其他组不搬项目、CRM记录或标签。
- 接入协作者体系的对象统一使用 Collaborator，提供模块常规业务读写；不提供只读协作者或通用对象级显式只读 ACL。CRM 是固定例外：无显式或隐式协作者；先校验记录所属组，再沿用现有四项写设置、对接人及空对接人兼容分支，改派沿用同一普通写规则，不受 `t2Collaborator` 控制。正式支付单同组读取及收藏夹既有可见范围按模块规则保留，不改造成通用 Viewer 身份。
- 组织 Owner/Admin 不因管理身份天然获得全部业务明细；`t2Collaborator` 是组织全局策略，默认关闭。开启后，已接入协作对象所属组的全部有效 T2 通过动态系统来源取得普通读写，在协作者列表中锁定勾选展示，不持久写入显式 ACL。关闭、降级或退组只撤销该隐式来源，独立显式协作者及附加能力保留；T2 来源不自动附带 `can_manage_collaborators` 或 `can_execute_payment`。
- 不新增通用模块禁用开关；Scope 类型、组织 Entitlement、可分配上限和对象权限各自判断。跨境支付的组支付开通是已确认业务例外，未开通时整模块 placeholder（含草稿），见 §5.8，不由普通 Scope 余量替代。
- 组不彻底删除，允许带遗留数据和 REMOVING 成员关系冻结归档；归档须二次确认并说明不可自行恢复，不提供解除归档入口，异常恢复转线下处理。组织始终保留一个有效默认组，默认组不可归档。
- 普通配额允许同父级下子级上限之和超配，执行逐层校验；支付部门资金分配另守资金约束。
- 邮件发送与邮箱解锁沿用现有各入口的预检、落账及复用逻辑，不统一“谁操作扣谁”，也不统一改扣 Owner 或原始创建者。实际 actor 的审计/统计归因与配额核算主体分开，详见 [本轮代码核对](./email_quota_code_evidence_2026-11-09.md)。
- 内容监控保留现有配额语义和各项设置权限，不新增 `can_manage_collaborators` 委派；协作者可维护监控内容及自动追踪，项目治理不随普通读写授予。仅增量接入业务组硬边界与默认关闭的全局组长隐式普通协作；研发实现差异独立核对，不作为合法权限沿用。

## 4. 研发规划需要对齐的差异

| 差异或缺口 | 本版处理要求 |
| --- | --- |
| 附件以一个当前组兼容一期 | 区分“当前组唯一”和“成员关系可多条”；本版补多组切换、请求上下文和缓存隔离 |
| 研发附件保留自有企业 Owner 身份暂停、加入外企后离职恢复的路径 | 已被 §5.3 的本轮确认否决；须回核一期实际交付、登录/邀请接受/会员与离职恢复链路，移除或隔离旧路径，不得将注销中间态视为干净账号。历史审计可保留，但不能恢复有效组织/组身份或跨组织转移业务数据 |
| 资源组可能由旧 `parent/parent_uid` 承载 | 明确逐表映射；产品语义用 groupId，不把旧字段值或 Owner UID 默认视为组 |
| CRM 一期清单主要明确企业归属，未形成完整记录业务组契约；支付表亦主要补企业归属 | 补记录/支付对象稳定组与历史迁移方案，不能只做分组页面而保留企业级越权 |
| 五张项目根表存在 Creator 与 Owner 兼容镜像 | 不承诺这些 Creator 是原始创建者，也不直接用它统计个人历史产出 |
| 部分配额历史在交接中继续改写 UID | 区分额度核算、事件操作人、历史统计归因；不能把兼容 UID 当作不可变 actor |
| 研发按明确接收人、Group Owner、企业 Owner 兜底 | 与同组单一接收人、组织管理员不默认介入业务、CRM 未分配模型对齐；无合法接收人保留责任快照并冻结，不能跨组静默兜底 |
| 研发离职完成可删除组成员关系，Input 用 REMOVED 表达完成 | 产品状态不强制等于一张表的枚举；即使活动关系删除，任务、审计和历史归属必须可查询 |
| 研发交接采用分页、幂等、断点续跑，Input 强调按组原子完成 | Spec 明确准备、执行、最终完成及中途失权，不能把分页副作用描述成已能数据库全量回滚 |
| 附件明确排除精选任务和 TikTok Shop 私信项目的部分离职交接 | 历史研发排除事实保留；2026-11-12目标已确认未归档组全部业务对象均须接入清退移交，含精选任务及TikTok Shop私信，不再以排除/冻结保留作候选。真实接入覆盖仍须验收，归档免交接及资金历史快照例外不变 |
| 共享标签、模板、旧 CRM 分组设置与新业务组不同 | 旧CRM分组暂定弃用，视图/旧权限来源不自动删除；标签两域现按§5.9组隔离，收款模板仍组织共享。不能因字段名group就替换业务组或误将两者共享范围一并改动 |
| 收藏夹旧私有/团队公开/指定成员三模式，数量、单夹容量与联系方式解锁分属不同计量 | 已确认适配为私有/本组公开/指定成员，内容读写与 Owner 专属治理分离，详见 §5.5 及[分层证据](./collection_permission_quota_evidence_2026-11-09.md)。RQ-COL-01/02/03 仍待研发核验，不把新目标或静态代码当作线上已实现 |
| 内容监控普通业务协作、项目治理、标签及配额各自有原规则，预检与用量归集不完全一致 | 保留既有口径，仅增量适配组边界与组长隐式协作；不新增名单管理委派，不用通用改名权限放开治理。RQ-MON-01–05 分别核核算、交接、鉴权、归档和后台链路，见 [监控证据](./monitor_permission_quota_evidence_2026-11-09.md) |
| 退款、冲正和异步消费依赖各自支付/任务链路 | 资金与权限验收覆盖已有承诺、重试和回补；结构预留不能代表已闭环 |

以上是文档对照发现的适配要求，不是本轮已验证的线上缺陷或数据规模结论。

## 5. 统一版本功能范围

下表是同一版本的功能域，不是独立发布期数；优先级用于讨论和开发顺序，不改变闭环义务。

本版不提供组合并或项目跨业务组迁移；组冻结归档及组内责任交接保留，默认组上线归组属于存量初始化，不是开放迁组功能。

| 功能域 | 本版交付内容 | 待收口边界 |
| --- | --- | --- |
| 组织与管理身份 | Owner 迁移、Admin 任免、Admin 全组织管理、组织管理与业务权限分离、管理汇总；Owner-only 的 Admin 移除成员/归档组开关，默认关闭 | 其余完整动作矩阵；不再讨论逐 Admin 分组范围 |
| 成员管理与邀请 | 仅 Owner/Admin 邀请；可选首组、默认默认组；昵称/邮箱检索、组与状态筛选、邀请/接受/撤销、席位反馈、配置摘要；待接受邀请不编辑，撤销后重邀 | 接受时的状态、席位与组资格并发校验 |
| 业务分组 | 建空组、改名、多组成员、0..N T2、组身份切换、二次确认归档；默认组始终有效且不可归档 | 归档任务与遗留责任的实现；不提供自助解除归档 |
| 普通配额 | Owner/Admin 配置组织内各组上限；组长在委派开关允许时逐 Scope 配置本组成员 inherit/capped；三级消费、组内批量增加、可见性、实际周期与剩余 | Scope 可分配矩阵及现有周期内调额；无全局个人额度配置；年度父额度下另设月度预算留 TODO，不在本期 |
| 项目协作及 CRM 模块权限 | 邮件、收藏夹、内容监控、支付单/草稿接入同组协作；CRM 同达人各组独立业务记录，组内可读，写及改派沿用现有 CRM 规则且不能越过记录组，无协作者或组长隐式来源。收藏夹与内容监控不提供名单管理委派 | 各模块动作与可见范围的实现/迁移验收；CRM 历史归组和关联入口改造留 Spec，收藏夹 RQ-COL-01/02/03、监控 RQ-MON-01–05 不因产品定案自动关闭 |
| 业务责任转交 | 收藏夹、内容监控等支持此动作的对象允许同组 Owner 主动转交，并清理新 Owner 重复 ACL；不提供原 Owner 转协作者快捷勾选、不自动新增协作；CRM 对接人改派沿模块规则 | 邮件项目与支付单不提供日常主动 Owner 转交，仅在账号级生命周期交接时适配；其他独立授权来源正常计算 |
| 支付协作与资金 | 正式单同组只读、草稿协作、敏感字段、can_execute_payment；未开通组全模块 placeholder、专用组余额及存量默认组共享例外；原承担人的退款额度恢复 | 账本原子性、原账务币种/手续费复用、历史身份缺失及回补幂等；不新增自助改账/纠错配置 |
| 支付审核与收款信息 | 组长审核放行规则、待办/筛选/通知；频道历史收款人作为组织共享快捷模板，所有有效业务成员可维护，同频道多条不同记录去重 | 审核状态边界、模板去重键及支付单独立快照 |

### 5.2 支付闭环不再按版本排除

### 5.4 会员到期、续费与超额成员（2026-10-28 补充）

### 5.5 配额配置的分层职责（2026-11-03 确认）

- 本组有效 T2 在既有组织全局 `t2Quota` 委派开关允许时，配置自己及本组 T2/T3 的各项成员额度、执行组内批量增加；不能超出组上限、修改组上限或其他组成员额度。保留该开关及可调整自己/同组成员的既有规则，不因本次分层而撤销。

| 处理本组业务交接 | 本组管理 → 业务交接，当前组有效组长 | 不依赖由哪个组织管理者发起，包含单组移除及组织清退中的本组子任务；可选择已有同组接收人并完成本组数据交接，不能更改人员移除决定、撤销移除或操作其他组 |

人员移除决定与业务交接可复用影响预检、同组接收、REMOVING/REMOVED 和结果通知，但不能把发起、撤销与业务处理授权混为一谈。组长完成本组业务交接后，由系统按既定移除决定结束相应关系，不是组长另行作出移除决定。任务中心只承接具体成员/组产生的任务，不以两个空泛的“账号 + 来源组”选择框作为主要发起方式。仅移出最后一个有效组时仍可先进入 REMOVING，但完成前须由组织管理者安排另一有效组或走组织清退。

本组业务交接权不依赖 `t2Quota` 配额委派开关，也不依赖任务的原发起人或原发起入口；该开关只控制额度配置。Owner/Admin 若同时为本组有效组长，可按业务身份处理本组交接，不能仅凭组织管理身份逐项分配业务数据。组长不能更改其他组长的成员关系或处理其他组数据。

未归档组无有效组长且存在需要人工决策的业务交接项时，等待组织安排业务负责人，不回退为 Admin 逐项分配数据；无业务处理项时可由组织侧确认结束。组织侧仍可看进度、安排负责人及处理人员关系，但不因此取得日常业务明细或改派权限。

选择“各组组长分别处理”的组织清退生效后，为每个未归档涉及组建立关联具体交接任务的待办通知，由该组当前有效组长在“通知与记录”查看；组织管理身份本身不取得该业务待办。点击通知进入“本组管理 → 业务交接”并定位对应成员任务；若目标组不是当前组，先显示目标组并确认切换，打开任务不等于执行移交。任一有效组长可选择同组 ACTIVE 项目接收人，CRM 另选接收人或置未分配；未提交可继续等待，不要求清退发起时当场决定。任务完成或改为统一接替后不再提供原待办处理入口，降级/失效组长不能继续处理；未归档组无组长时待办保留，任命后按实时资格承接。永久归档组无需业务接收人，原责任、ACL 和资金快照留历史，待办标“归档免交接”并关闭；先归档后发起清退同理。统一汇总“x/y组已处理”，明细区分“已交接 / 归档免交接”，不得称全部数据已移交。全部必要组已处理才最终清退；单组移除最后有效组仍须安排另一有效组或改走组织清退，不因归档免交接跳过关系结束条件。归档本身不发起清退或清退普通成员，不新增特殊组长、归档交接权或自助恢复状态机。

【UI交互】【UI反馈】Dashboard 另设独立实时待办区承接上述任务，不受统计日期、所选成员、统计视角或资源显示筛选影响。Owner/Admin 只看组织清退进度及摘要，可进入组织移交任务，不以此获得业务明细或逐项选择接收人的兜底权限；同时为目标组有效组长时合并相应处理能力。组长只见自己管理组的业务待办，进入“本组管理 → 业务交接”，跨当前业务组仍先显式确认切组，取消不切组、不移交。普通组员不可见他人待办；处于组织 REMOVING 的本人只看自己的清退进度摘要和失权说明，不能查看统计、业务详情或操作交接。

本节覆盖 2026-11-03 “组长可主动移出本组组员”及按发起来源限制业务交接的结论；保留组织/当前组入口分区。组长不能邀请或主动移出成员已确认；Admin 移除成员须由 Owner 打开对应组织策略，不改变本组组长既有交接任务的业务处理权。

### 5.7 组织清退的接手路径与组关系继承（2026-11-10 收口）

组织清退保留三条接手路径：邀请新账号完整接替；指定一个已有账号增量接替；清退后由各组组长分别处理数据移交。Owner，或“Admin 可移除成员”开启时的 Admin，可将前两条作为清退中的专用生命周期管理动作直接提交，由系统按组统一执行；这不是日常任意逐项目改派、查看业务内容或编辑订单的权限。第三条仍按 §5.6 由各组长处理未归档组子任务；未归档组无组长且有人工决策业务时等待组织安排业务负责人，永久归档组免交接。

【已确认】【UI交互】前两条不增加确认或审批节点：指定现有接收人并提交清退后，系统自动开始移交；新邀请提交清退并发送邀请后进入 `WAITING_FOR_TARGET`，受邀人接受组织邀请且资格、席位和组关系校验通过后自动开始移交。不要求组长批准、接收人确认接替或操作者另点“确认接替/执行统一移交”；接受邀请是建立组织关系，不是移交审批。提交/执行时的权限、目标资格及范围校验、影响摘要、进度和完成通知继续保留，不能因免去额外确认而跳过。

接替时**只继承组关系，不继承原账号的组长角色**：接收人缺少涉及组的有效关系时，补建关系默认组员；已具备该组关系时，保留接收人自己的组内身份，既不因原账号是组长而自动升级，也不降低接收人原有组长身份。组织身份不随本规则复制。原账号如为某组唯一组长，接替后允许该组暂无组长；任命业务负责人为组长须显式操作，不能用接替自动完成。

【已确认】【UI反馈】业务接替、配额不合并。接收人在某组已有有效关系时，逐 Scope 保留自己的上限配置、已用和占用；缺失组关系按新增默认值建立，普通可分配项为 `inherit`、个人支付上限为 `unlimited`，仍受组织/组上限、组支付启用和余额约束。不复制或相加离职者的个人上限、未用额度、历史用量或支付承担；已失效或退组中的关系不能自动复活。新增默认值可能比离职者原 `capped` 更宽，影响摘要须明确说明；需继续限制时由获委派组长在既有组内配额入口配置，不在移交表单提供 Admin 调额或额外确认勾选。

“收回离职账号配额”仅指收回其继续消费的资格和个人上限配置的生效资格，不是退还已消耗次数、释放既有支付占用或增加组织/组余额。普通个人上限本来不预占父级额度，未用上限不是可划回的资金；旧配置、消耗及占用记录继续留作审计和结算。历史创建人、操作人、用量及既有 `fundingUid/fundingGroupId` 不改写，真实核算字段仍按模块证据和研发契约验证。

前两条整体接替将该离职账号在未归档组涉及的项目 Owner、CRM 对接人和其他接入对象的有效显式协作关系交给同一个接收人；各组项目/CRM 记录留原组，不触及其他账号的对象，不复制禁用 ACL 或系统派生来源。CRM 没有记录 ACL 可移交，只改对接责任；其他组员仍按有效组身份及既有 CRM 策略计算读写。第三条各组长分别处理时，CRM 仍可另选 0..1 名接收人，未选置为未分配。永久归档组不执行业务接替，不补接收人组关系，原 Owner/Assignee/创建人/ACL/资金快照留历史，按“归档免交接”计为已处理。等待接收人期间不提前改写未归档对象责任；开始执行后按组推进，全部必要组已处理后才最终 `REMOVED`，汇总“x/y组已处理”、明细区分实际交接和免交接，不能把异步中途成功或归档免交接写成全部数据已移交。

【Demo示意】预置沈岚（`u-removing`），组织及增长团队、品牌团队关系均为 `REMOVING`，已选择“各组长分别处理”；每组各有一个收藏夹 Owner 待交接。完成一组仅结束该组待办，另一组继续等待，组织账号仍为 `REMOVING`；也可在满足资金条件后永久归档其中一组，按“归档免交接”关闭该组业务待办、保留原对象历史。全部必要组已处理后才为 `REMOVED`，汇总统一“x/y组已处理”。此样本不改变既有7个 ACTIVE 账号、席位/待接受邀请、资金及历史用量基线，不据此推导真实席位释放时点。未归档组无组长仍等待任命。

### 5.8 跨境支付资金：专用组余额与存量默认组共享例外（2026-11-10 更新）

- **资金归属**：组织钱包集中保管，尚未分到专用组的可用部分展示为「待分配余额」。普通业务组的新付款仅使用本组当前启用周期专用可用额，不自动借用该余额或其他组资金；提交仍校验对象执行资格、组织钱包、适用资金来源及组内个人上限。个人 `unlimited` 只是不额外加个人上限，不绕过组启用或余额，不在此裁决提现或注销清理。
- **存量默认组迁移例外已确认**：存量已有支付权限的组织，上线时默认组自动开通支付，使用组织共享余额，不另划一笔默认组专用资金。共享可用额只含组织尚未分配、尚未占用的可用部分，绝不能使用其他组专用余额；后续线下充值直接增加该共享可用部分。该默认组仍按组记录业务归属及个人资金承担，不与组织账重复计算。此为保证存量继续支付的迁移例外，不恢复所有组可选共享/专用或模式切换能力；其他及新建业务组继续使用专用余额。
- **组启用与入口**：新建业务组可在建组时配置是否开通支付，默认关闭；开通可零余额，之后另行分配，与充值不绑定。未开通时，整个支付模块页面显示不可用 placeholder，草稿也不能新建或保存；旧单、历史账目及既有资金责任保留，后台结算、释放和退款不因模块入口关闭被取消。具体历史查询入口留 Spec，不将保留旧单误解为未开通页面仍可业务操作。
- **分配主入口**：组织 Owner/Admin 按管理权限进入「组织资金 → 组支付余额 → 分配」，向有效且已开通的专用资金组分配。共享默认组不接受重复专用划拨；无需选择充值记录，实际可分配金额以提交时组织当前待分配可用部分为准，不按某笔充值建额度批次或计算该笔剩余。分给专用组后共享可用部分同步减少，同一笔钱不能两边同时花。
- **充值保持现状**：继续既有线下充值流程，不在充值时选择组、不自动划拨；到账成功后增加组织尚未分配的可用部分，专用组余额不变，符合迁移例外的共享默认组可直接使用新增共享可用额。不新增实时推送或通知中心消息。
- **到账后页内提示**：有权人员在「组织资金」看到「有新充值到账」，可关闭提示或点「分配到组」打开与主入口同规则的分配表单。资金明细行保持只读，不提供分配操作。仅已确认成功的充值触发该提示；退款、释放、内部归还及其他正金额记录不是充值。关闭只隐藏提示，不改变余额、流水或是否分配；从提示发起的分配成功后处理该提示并新增独立内部划转，不标记该笔充值“全部分配”。提示的持久化及跨人员处理范围留待 Spec。
- **提示中的分配建议**：目标只含有效且已开通的专用资金组，不预选共享默认组；没有专用目标时不要求分配，共享默认组不需该步骤即可使用新到账。原充值金额仅为可修改建议值，不是上限或专属来源，提交仍按当前待分配可用额校验。分配记录可选关联充值 `recordId`，不要求关联、不约束资金批次。
- **分配和归还记账**：专用资金分配及未承诺余额归还均新增不可修改、可追溯的记录，不改原流水、不收回已承诺资金，不用普通总额编辑替代归还。内部划转不改变钱包实际总资金，充值与随后分配是不同事件，不能重复计充值。正常归还不是纠错；本期不另设纠错、币种、手续费配置或自助改账入口，异常冲正沿现有人工处理，币种及手续费沿现有账务口径。
- **关闭、归档、重新开启**：关闭支付时整个模块入口不可用，归档同时停止组普通业务；二者均不取消旧单或资金责任。专用组本周期未承诺可用额归还组织待分配，专用余额归零，既有占用/已付/退款和流水保留；专用组重新开启从零的新周期按新分配使用，不自动承接旧周期退款。共享默认组没有专用余额可归还，关闭不清零组织共享资金、不动其他组专用款；其历史承诺按冻结来源继续处理，重新启用等精确实现留 Spec，不新增类型切换入口。
- **归档资金例外（2026-11-12 确认）**：仍需组内人员主动推进的资金事项须先完成，或转既有人工流程妥善处置；未处置前阻塞归档，不能先归档再通过特殊组长/归档业务权限收尾。可按既定后台链路继续结算的已有承诺不一概阻塞归档。免业务交接不取消、核销资金占用、退款或结算责任，原 `fundingUid/fundingGroupId` 及承担快照保持，释放/退款仍走原来源和周期规则；转人工不等于可将未结资金直接弃掉。
- **承诺、结算与组资金回补**：正式或预约提交时冻结 `fundingUid`、`fundingGroupId`、来源及适用启用周期，执行/审批人另记；已占用结算从占用转已付，不二次扣当前余额。共享来源的取消/失败释放或退款回组织未分配可用部分；专用来源仅在原组有效、开通且匹配原周期时回原组，否则回组织未分配。历史仍挂原付款和承担快照，不改为当前执行人或新周期支付。
- **退款恢复个人可用额已确认**：按成功退款金额冲回原 `fundingUid + fundingGroupId` 承担关系的已用，部分退款相应恢复个人可用额，不抬高其配置上限，不转给接替人、提交人或放行人；原成员已退组/冻结/清退时也不复活使用资格。退款恢复个人用量与组/组织资金回补分别记账，资金回到组织不妨碍原承担关系冲回已用；周期字段、历史关系定位与幂等方式留 Spec，不再将“是否恢复”列为产品待定。
- **存量承诺和使用情况**：上线前组织钱包承诺按原账路继续，不重绑默认组周期、不补造专用划拨、不二次扣款或改历史承担人；原组织来源释放/回补归组织未分配。看板区分组织总钱包、待分配/共享可用、专用组可用/占用/已付及来源，默认组共享业务投影不能与组织总额重复相加，内部划转不当充值或消费。存量默认组自动开通及共享例外已定，具体迁移映射和对账仍须验收，不以 Demo 预置值证明已部署。
- **Spec／研发实施口径**：补回调/重试幂等、缺失历史来源/身份、原承担关系个人已用恢复、精确账本字段及原币种/手续费规则复用。分配提交重验状态和余额，不因打开过提示而保留额度；不新增独立金融配置、纠错产品或自助改账。上述产品取舍已定，未细化的工程边界不自动成为新用户能力。

- **CRM 记录结构已确认，方案 B**：同一达人可在不同业务组分别维护 CRM 业务记录，各自保存对接人和合作状态；达人基础资料仍共享。记录身份必须区分组织、业务组、平台和达人，不因当前操作者或对接人切组而改变。不设显式/隐式 Collaborator、协作者名单或 `can_manage_collaborators`，不受 `t2Collaborator` 开关影响。
- **CRM 权限最终确认，方案 A**：尽量不改线上已闭环的模块权限，只增加记录所属组硬边界。有效同组成员可读；写权限继续使用对接人和组织现有四项设置，四项授权取并集但不能越过记录组，默认值沿用现有配置，不强制全开。当前对接人可写；其他有效同组成员是否可写由原 CRM 策略决定，不能将成员身份本身视为写授权。管理员是 CRM 已配置的存量授权来源，不反向赋予其他模块业务权限。
- **CRM 四项来源不扩张**：权限 1 沿用现有解析出的单个 `adminUid`（无对应子账号管理员时回退父账号），不能直接等同新模型所有 Owner/Admin；权限 2/3 沿用对接人既有组关系的组长/成员来源，不直接改为记录组全体组长/成员。任何来源都先受记录所属组有效身份限制。空对接人配置 `[]/1/2/3` 沿原管理员兜底，包含 `4` 时仅本记录组有效成员全员可写；真实多 Admin、新旧组来源映射留 Spec，不由 Demo 扩权。
- **CRM 对接人及改派沿用现状**：对接人是可空、可转交的记录业务负责人，不是组织 Owner，也不强造项目容器。谁拥有该条记录现行 CRM 普通写权限，谁就能按原流程指派/改派；不额外限定为“当前对接人或组长”，不新增组长独立分工权。空对接人沿用现有管理员兼容分支，并同样先校验记录组；未分配不会向所有组员开放写权限。具体管理动作、候选与字段约束沿现有模块规则核验，不新增 Owner-only 治理。此前“全组读写”“仅对接人/组长改派、空时仅组长指派”均被本条覆盖。
- **CRM 旧设置与实施边界**：四项 CRM 写设置继续生效并保留设置入口，不能与暂定弃用的“旧 CRM 分组设置”混为一谈。旧 CRM 分组不承担新业务组归属；旧账号组、自定义视图与标签定义分别识别，不因此一并删除。D09 核心已定，剩余旧记录初始归组、四项实际来源在组边界内的映射、旧分组入口退出、导入/去重/消息联动/导出及共享基础资料/组内字段边界留 Spec/研发验收；不自动向全部组复制旧记录，不随对接人入组迁移，不宣称加入组边界完全无权限变化。
- **CRM 迁移风险须验收**：未分配记录所在组若没有有效的原解析 CRM 管理员、且配置不含 4，可能无可编辑者；必须在迁移/配置方案中处理，不能静默新增组长首次指派权或允许管理员越过记录组。整体接替也不继承原 CRM 管理员身份；对接人改派后相关旧组来源按既有规则重新计算，不凭“移交”复制权限。
- **标签旧事实与最新覆盖**：旧monitor有独立组织字典，CRM/消息/达人资料共用另一字典；原达人标签`uid`写父账号，不是创建人。这些静态事实保留，但目标现已确认按业务组隔离，不再维持组织共享或提供组织/组共享切换；旧“全局监控限制”“CRM定义删除Owner-only”“共享切换待讨论”均由以下规则覆盖，不宣称已经部署。
- **两类标签域**：creator达人标签在同组CRM、消息中心、达人详情共用同一字典和对应组业务打标；monitor监控标签独立字典，保留原分类。两域都归业务组，不能跨组读写定义或引用，也不按页面再拆第三套字典。创建人、创建时组和当前归属组分开保存/解释，不用成员当前所在组倒推历史。
- **两个独立组策略**：每组分别设置“限制组员维护达人标签定义”“限制组员维护监控标签定义”，均默认关闭，不是组织全局开关，也不受`t2Collaborator`。Owner/Admin在“组织管理 → 业务组 → 组策略”管理目标组配置，与支付审核组策略同页；组长在“本组管理 → 本组策略”只读查看。维护定义则至少要求该目标组ACTIVE成员关系及有效业务资格，不能凭组织身份跨组。限制关闭时有效本组成员可增删改；开启后仅有效同组组长、且具有该组有效身份的组织Owner/Admin可维护，保留管理例外但不越组。
- **定义与应用分层**：定义新增/改名/删除受上述对应域策略；对对象应用/移除已有标签仍按原项目ACL或CRM记录写规则，不因有定义权开放对象内容，也不因CRM普通写自动得到定义权。删除只作用当前组对应域，展示该组跨CRM/消息/达人详情或监控项目的引用影响并确认；不能把旧`starCount`当完整影响数，不跨组清理同名定义。本人偏好按下条独立规则处理，不扩入共享定义限制。
- **本人偏好例外（2026-11-12 确认）**：两域标签的置顶、个人偏好及本人展示配置不受定义限制开关控制，只能由使用者本人配置且只影响本人；不能变更他人偏好、共享字典定义、业务数据或指标，不能借此取得无权对象的读取或写入。现有字段若实际共用，须适配为本人隔离存储/读取并验收，不以“沿用线上”保留跨人副作用；是否改写共享字段属于工程核验，不再是产品规则待定。
- **消息筛选**：当前组达人标签仅“我创建的/本组全部”两项，不再保留“本组成员创建的/全组织全部”的冗余或越组项；来源筛选不授会话/项目权限。`creatorId`未知历史显示未知，仍在本组全部，不伪装本人创建；成员离组或同组换Owner不搬标签。
- **空组与存量兼容**：新组初始无项目、无两域标签，不自动复制其他组字典。存量上线由真实默认组承接原两字典及已有应用关系，用户无需重新打标；一期实际交付/历史归组仍需验收，不能因Demo预置视为完成。无法可靠回填创建人/创建时组时保留未知，当前承接归属与历史来源分别解释。
- **不随人员移动标签**：creator是组业务标签，非Owner项目资产；CRM和监控项目均留原组，成员加入其他组不复制任一域定义或打标关系，同组换Owner/成员离组也不搬标签。项目迁组本期已取消，monitor按引用复用/复制/重绑也无本期流程；仅历史上曾讨论“分类+名称映射、保留创建来源、不动源字典其他项目”，未来若重启需重新评审，不实现该复制链。
- **界面与研发**：“业务组 → 组策略”集中两个标签开关和支付审核开关；monitor沿原标签管理，CRM模块设置增加达人标签管理，消息入口进入同一张表，模块仅说明规则及设置跳转。达人详情等第三入口只作真实映射说明，不新造第三字典/管理表。核两域读写/删除引用、全入口组边界、创建身份未知及默认组无感承接；不得在入组或组管理遗留可执行迁组/复制标签入口，静态事实与环境验收分开。

### 5.10 邮件项目与消息对话：保留现状并增量组隔离（2026-11-10 确认）

本节以 [权限与消息静态核查](./email_message_permission_evidence_2026-11-10.md) 和 [邮件核算证据](./email_quota_code_evidence_2026-11-09.md) 为依据，区分已确认的兼容目标与尚未实测的部署/迁移事实。不把通用协作抽象变成新增业务限制。

- **邮件项目边界**：稳定业务组绑定邮件任务 `kol_email_task`，各轮次 `kol_email_project` 通过 `email_task_id` 继承，不从轮次 UID 或当前操作者反推项目组。负责人和有效正式协作者保留内容/收件人读写与发送；改任务名、删除整任务仍仅负责人且遵循原状态限制。未核实的独立项目说明字段不因通用模型新增。
- **邮件名单管理已收口**：负责人或具有 `canManageMembers=1` 的有效正式协作者可维护名单，名单管理员仍可向其他同组有效正式协作者授予/收回该能力，沿用线上，不新增“只有 Owner 能授予、非 Owner 不可继续授予”的限制。普通协作者与组长隐式来源不自动获得名单管理能力。此为邮件模块例外，不推广到支付执行权或其他模块；收藏夹与内容监控仍不委派名单治理。
- **邮件设置入口与分权已确认（2026-11-11）**：复用邮件任务卡的编辑弹窗，不新建独立协作者页面。负责人可编辑名称和显式协作名单/名单管理能力；名单管理员名称只读，只维护显式协作及该管理能力；普通协作者（含仅有组长隐式来源者）只查看项目设置，不出现可修改的治理表单。此处“只查看”不改变其原有邮件内容/收件人读写与发送资格，不新增只读协作者角色。组长来源锁定展示、显式与隐式独立，组织策略仍在全局策略页；原邮件设置继续承接发件、签名和自动回复。表单取消不保存，保存不得使非Owner的名称或其他越权字段生效。具体视觉与生产提交契约留Spec/Design；[映射审阅](../../../documents/02-project-documents/account_permission_collaboration/email_real_page_mapping_review_2026-11-11.md)仅本条已确认，其他建议不自动批准。
- **邮件无日常 Owner 转交**：不提供通用项目主动转交入口；仅在账号级退组、清退和整体接替等既定生命周期流程中交接，具体任务/轮次字段、正式名单与核算映射须研发验收。普通协作者不能因可编辑内容而改任务名。既有 `email[12]` 管理员强制协作按迁移真值承接，不等同于默认关闭的全局组长隐式来源。
- **团队邮件数据原抽屉仅收窄账号范围（2026-11-11 确认）**：原“团队邮件数据”账号选择范围限制为当前业务组；其余 11 项指标、日期与邮件项目筛选、账号列表→任务八项展开、刷新/更新时间及导出行为均保留，不新增原抽屉 UI 或重设计指标。服务端必须在候选、汇总、查询、展开和导出统一验证当前组，不能只过滤前端账号选项；当前是否已支持该组上下文仍属研发核验。原抽屉使用业务当前组，不变成跨组组织看板。见 [现状证据与研发问题](./email_dashboard_evidence_2026-11-11.md)。
- **精确对话与访问来源**：普通邮件对话继承源项目负责人/正式协作者，另保留既有精确对话转交来源；按业务类型、源项目、达人、平台及负责人定位，不能只按组织或达人匹配。默认“沟通中”要求已有回复，但单方成功发信可出现在“建联中/全部”，不能说整个消息中心都只收有回复的邮件串。
- **对话转交不是项目转交**：仅源任务负责人维护 `0..50` 名转交人，可保存空名单全部撤销；候选与保存、实际使用同时限制为源项目组有效成员，排除负责人本人和正式项目协作者。`canManageMembers` 或组织管理身份不增加对话转交管理权；转交不改项目 Owner、正式协作者或项目 ACL，转交人不因此获得整个项目权限，Owner 仍能发送。
- **发件身份保留细分**：普通 Owner/项目协作者默认使用任务 Owner 的发件资源，也可按既有规则显式选择本人可用邮箱；对话转交人须使用自己的授权配置，不静默回退 Owner。站内头像/昵称展示真实操作者，实际发件邮箱及显示名快照另记，Reply-To 继续沿独立配置，不承诺随转交自动改成转交人地址。
- **通知与撤销**：有有效转交人时，普通未读/NIM 提醒路由抑制 Owner、通知转交人，其他项目协作者仍保留提醒；Owner 的发送权不受影响。全部撤销后恢复未来消息的 Owner 跟进路由，不恢复历史未读。其他回复提醒邮件渠道尚未实测，不泛称所有通知均被关闭或恢复。
- **扣量不随授权改写**：已有普通 YJ 对话回复不新增 Scope21；RW2 首次直接联系且无发送历史时仍可能新增一次发送，新邮箱解锁仍可能消费 Scope4，按入口既有资源主体与复用规则处理。普通邮件自动多轮跟进不等同于已有对话回复；本节不关闭 `RQ-MAIL-01/02/03`，不统一改扣 actor、Owner 或创建人。
- **组隔离必须覆盖聚合与旁路**：会话正文、草稿、附件、发送/定时/批量、转交和协作同步之外，达人卡片摘要、最后消息、未读、检索及置顶/星标/归档等状态和批量操作也不得混入其他组。跨项目卡片现有投影需按组适配，具体键/回填/重建方案留 Spec；新服务导入、后台发送、导出及 CRM 联动逐入口验收，不以候选列表加过滤代替完整隔离。
- **Spec／研发保留核验**：隐式组长互斥、发件身份优先级、退组/清退/同组整体接替后的委派失效与提醒回退、历史投影及迟到任务须验；不套显式ACL恢复，不落隐式来源为正式名单。项目迁组本期取消，不设计其委派恢复链；真实部署/通知和历史快照仍待核，名单管理可再授予不重开决策。
- **【UI交互】【UI反馈】审阅示意边界**：邮件页区分内容读写、Owner 设置和名单管理能力；消息页按精确对话展示来源项目/组、委派名单、Owner 保留发送权及发送身份。本地转交/清空、来信与提醒路由模拟、发送身份预览即可辅助审阅；不真实发信、不扣量，不以完整异步状态机或持久化作为本 Demo 门槛。

### 6.4 归因与数据边界

- 当前资源归属统计、历史业务活动统计和配额核算是三种口径。Owner 交接后资源可计入新负责人当前名下，已发生动作不应伪装成新负责人完成。
- 单人及组员动作排行须有真实actor事件，只统计该账号执行的动作；项目总量、Assignee名下记录或当前Owner不得代替。工作量不自动等于绩效/因果，自动任务单列，具体成功/失败/skip/重试及历史覆盖按来源核验，不给全部协作者分摊同一项目结果。
- 历史数据没有可靠 actor/组快照时，只在证据支持的组织或对象范围展示；不能用今天所在组回填历史部门业绩。
- 已可靠留存的历史组快照不因退组、归档、同组Owner变化或其他历史数据修正而回写；历史未归属须说明，不因归因核验开放本期已取消的项目迁组。
- 多组账号按事件所属组统计，同一组织汇总去重，不能因账号属于多个组重复累计。
- 组织共享主数据、个人配置与无项目对象的统计维度需逐项确认，不强制所有指标都有 groupId。
- Creator 兼容镜像和会被改写的历史 UID 不作为稳定个人业绩证据；沿已有可靠事件/身份记录核验归因并注明历史起算，不将新增历史快照存储作为本看板先决条件。
- 邮件发送/解锁用量按各入口既有核算主体展示，实际操作人的业务活动另行归因；配额历史 UID、轮次 UID 或任务 UID 不能直接当作稳定 actor，也不按看板操作者重记用量。
- 邮件发送/消息时间、CRM业务记录创建日期、监控项目/条目新增日期与daily观察期、资源有效记录时间按各自已定语义取数，不使用一个updateTime兜底。实时当前状态不等于期间变化、当前累计不等于区间增量；有缺失/时延/基线不明时标未覆盖或待核，不能假0。期间资源发生量与当前额度/占用/剩余分列，不因选期重写当前核算。
- 零记录、接口失败和权限不足分开处理；前端不能用统一返回空数组替代数据状态。
- 2026-11-11 补充已登录配额页的 23／22 项只读展示事实，详见线上盘点；没有验证真实组层接口、Scope 全量下分资格、历史归组或性能。当前配额接口和既有模块看板的可复用能力仍须在目标分支核验，静态代码观察不代表部署事实。

- **日期与筛选**：合法整体邮件仍按发送时间选数据、观察截至更新时间效果，沟通三项按消息时间；个人/选单人按实际动作发生时间，项目只作本人动作过滤。整体项目统计限所辖有效组长资格，Admin不凭组织管理权选项目整体；日期、范围及条件用于相应查询/展开/导出，不扩大正文权限。
- **四线趋势（2026-11-11 确认，后续取消重复漏斗）**：趋势同时展示发送、送达、已读（原openCount/打开数）、回复，按原发送日期观察截至更新时间的效果。邮件效果漏斗与顶部指标重复，已确认删除，不单独展示。回复未被追踪到打开时可高于已读，保留实际原值并说明，不裁数、补数或强制递减；三率仍除发送数，不改成相邻阶段转化率。对话沟通新增两项按消息事件另列，见§6.9，不混入四线或原11项。
- **趋势粒度（2026-11-11 确认）**：邮件趋势提供日/周/月分桶，独立于全局日期范围，切粒度不改选期。周从周一开始，周/月首末桶裁到所选日期；四封数按桶汇总，原三率按对应总数量除发送数重算，不平均日比率。对话两项仍按完整选期精确去重，不把每日去重数相加；分桶不新增时间×账号周/月明细、自由报表或任务导出。
- **UI可读性（2026-11-12 确认）**：趋势刻度按可用宽度取舍，优先首尾并剔除重叠刻度，移动端减少刻度但不删数据；保留统一日期点读数和表格替代。核心状态、单位、上限及必读口径使用规范的可读字号/对比，详细说明可展开，不靠长提示替代准确标签。
- **账号与任务明细（2026-11-12 收口）**：原邮件抽屉继续保留账号→任务八项及原分页/导出，是旧业务归属明细的承接入口；Dashboard保留11项及获准组长项目中的统计明细，不宣称全身份完整替代原抽屉，不为补等价给Admin新增项目统计权。旧task.uid等归属数据不是新单人actor接口；个人/选单人仅展示来源支持的实际动作，不能为凑齐11项/任务八项复制整体来信/效果。组织/组人数、会话重新去重不求成员和，整体三率按总数重算，不平均成员比率。
- **刷新和导出**：沿用刷新与更新时间的能力，Demo 只示意，不强制刷新线上。原模块邮件导出沿现有 Summary 11 项 + 账号明细八项，不新增任务维度导出或把已展开任务写进导出；新增Dashboard对话沟通汇总单列，不冒充旧导出已经支持。与当前日期、项目、账号和授权范围一致，真实异步服务/字段仍须验收，不因按钮示意认定已交付。
- **独立研发核验**：`RQ-DASH-01` 验证当前组候选及伪造 ID、summary/list/tasks/export 同范围；`RQ-DASH-02` 核消息汇总 `task.uid` 与成员兼容 `pm.uid`、跟进公式/提示差；`RQ-DASH-03` 核邮件/消息时间、边界/时区、跨账号/组去重与历史交接归因；`RQ-DASH-04` 核实际部署刷新/`lastRefreshTime`、导出及 Campaign 完整覆盖。它们不新增产品决策卡，不使前端自行改原业务/公式或把 UID 当实际 actor。
- **本轮证据边界**：线上 summary/list/tasks 三个接口成功返回并只读核对三率分母；未强刷或导出，未保存客户数据。所查前后端分支不是全部线上部署证明，尤其线上刷新/时间字段与本地 ref 有差异；仅接口结构吻合不能宣称所有 SQL、历史和新业务组隔离已验证。

### 6.8 非邮件时间口径（2026-11-11 确认）

完整已确认规则、23项资源分类、静态依据和 `RQ-TIME-01–04` 见 [非邮件时间规则](./dashboard_time_rules_2026-11-11.md)。以下不是候选方案，不再将 CRM/监控/资源日期语义整体列待定。

- **CRM**：按该组业务记录创建日期筛选，展示期间新增记录、其中当前合作中、其中当前已完成；当前状态实时查询。10月新增、11月完成的记录，11月回查10月新增范围，其当前完成状态会更新，不能称“10月完成数”。记录updateTime不充当跟进/合作完成时间，共享达人基础资料创建日期不替代组业务记录日期。
- **监控**：新项目按project.createTime，新条目按task.createTime加入监控日期，不用videoPublishTime。观看/互动区间增长复用既有daily_mv观察期能力，统计所选范围获准内容在观察期的增长，不能只筛期间新建内容；当前存量累计可辅助且标“当前累计”。所查服务只读取到昨天，必须标实际截止/覆盖，缺失、无基线、待更新与真实0区分；不另建快照替代已有daily能力。
- **资源**：消耗/解锁按原首次有效记录或有效消费发生时间计期间量，保留原单位和返还/复用；容量和资格标当前，不伪装区间消费。当前上限、占用和剩余依原规则实时读取，不能由任意区间发生量重新计算。24调整日期、45/89性质及日/月导出单位等仍明确待核，不影响23项显示或用0掩盖未知。
- **研发验收**：`RQ-TIME-01`核CRM字段/历史，`02`核daily覆盖截止/基线/去重，`03`核Scope日期单位返还及24/45/89/导出，`04`核新组与存量历史归组/同组交接/导出范围和SLA；不因历史核验恢复本期已裁剪项目迁组，不新增产品卡或关闭工程核验。

### 6.9 对话沟通新增两项（2026-11-11 确认）

完整规则见 [邮件趋势与对话沟通](./mail_dashboard_conversation_rules_2026-11-11.md)。两项独立展示在Dashboard“对话沟通”，不是原邮件11项中的人数/消息数改名，也不改原邮件模块或消息中心业务。

- **新增沟通对话**：期内首次收到红人有效回复、由建联进入沟通的精确对话数。首次回复须核全历史，不能拿日期范围内第一条回复当首次；精确对话去重，不按组织达人全局去重。
- **期间活跃对话**：已经进入沟通且期内有有效收/发消息的精确对话数，老对话也计；首次有效回复本身即计活动，不要求额外再收发，未回复单向邀约及仅回复前的发送不计。历史完整且范围相同时新增不大于活跃；历史不足时两项分别保留可信结果/未知，不一并假0。
- **时间与身份**：整体对话按消息事件时间，与整体邮件发送日期效果分开；用真实精确键，不用跨项目达人卡片数。组织/组对话重新去重不求成员和，Owner交接或转交不因换人重算新沟通。个人/选单人只统计有证据的实际沟通动作，不把收到回复或项目整体新增/活跃对话直接当某人动作，效果分摊未核不承诺。
- **范围与缺失**：沿三类报表资格及组边界/筛选，不授正文；全历史首次回复/有效消息不足标未知，不假0或算新。历史归组和同组交接不改写原历史，不据此开放项目迁组。
- **导出与研发**：新Dashboard CSV单列两项对话汇总及口径/范围/日期/更新时间，原模块Summary11+账号8、任务八项及旧导出不变。`RQ-CONV-01`核精确键和全历史首次回复，`02`核有效消息/活动窗口/历史覆盖，`03`核组迁移/授权归属/接口导出/SLA；定义已确认，真实新服务待验，不以Demo示意认定交付。
- **阅读重排边界**：跨模块总览、日/周/月和核心/展开布局保留，但必须随§6.10模式区分实际动作与合法整体结果；未知/无权/延迟及实际截止不省略。范围、分桶、去重和导出继续RQ-CONV-03及RQ-ACTOR核验，不新增决策卡。时间×账号周/月明细仅后续考虑，本轮不新增自定义报表、寄样或短链。

### 6.10 实际动作与整体结果分开（2026-11-11 最新确认）

规则、静态证据及`RQ-ACTOR-01–04`见 [实际动作与整体统计](./dashboard_actor_workload_rules_2026-11-11.md)。本条覆盖旧“个人获准项目整体/管理单人按业务归属”的目标，不回写历史验收或原线上事实。

- 个人及管理者选单人=该账号实际执行的动作；普通账号选项目只筛本人动作。组长有本组整合/成员动作/所辖组项目整体，个人仍按普通成员。Admin仅凭组织身份看组织/组/个人汇总，兼组长时同页合并其可用入口，无须换身份，仍可切统计范围；项目统计不授正文或写ACL。

- `RQ-ACTOR-01`核真实actor不可变落库，`02`核各入口人工/自动及有效成功/失败/skip/重试，`03`核历史起算/缺失及交接不改actor/发生组，`04`核三类报表权限/同页入口合并/去重/导出和SLA；不新增D产品卡，不关闭原模块核验。
