## 1. 版本目标和阅读口径

在一期底层替换生效的前提下，把组织事实变成用户能实际使用的完整产品：组织成员管理、业务分组、权限策略、项目协作、普通配额、支付资金限制、成员与数据生命周期，以及按组和账号查看的使用情况看板。

本版闭环是：配置组织与分组 → 引入和分配成员 → 设置能力与配额 → 在业务模块中协作和消耗 → 查看使用与业务结果 → 调整配置、迁移或清退成员 → 保留历史归属与审计。

组织、权限、资金和统计共用同一套企业、组、成员及对象事实。研发可以按依赖并行开发、分模块验收和灰度，但不以独立后续版本承接本版尚未做完的必要环节。

本文使用四类状态：

- **本版交付**：已有目标规则，或属于用户本次明确新增范围；仍需细化 Spec 与实现。
- **本版待确认**：留在本版问题清单中收口，不能解释为已获批的具体方案，也不能直接标成后续版本。
- **回归**：一期或既有实现已覆盖，验证与新组织模型兼容。
- **已否决/历史废案**：只留追溯，不恢复为需求。

## 2. 一期与本版的边界

### 2.1 按一期已生效规划，不重复立项

| 一期承接的基础 | 本版使用方式 | 接收证据 |
| --- | --- | --- |
| 企业、默认组、企业成员和组成员四张基础表 | 从统一组织事实读写组织与业务上下文 | 一期实际交付清单、接口和迁移验收 |
| 业务资源企业归属与已确认的组承载字段 | 用户创建、查看、协作与迁移时使用稳定归属 | 逐表映射与异常清单 |
| 企业权益、会员和旧接口兼容 | 保持套餐归属与组织总额，补组/成员约束 | 权益及配额兼容验收 |
| Owner/Creator 字段适配及兼容约束 | 根据对象模型计算权限，不从字段名称猜身份 | 模块字段语义与兼容白名单 |
| 一期已经交付的离职任务、身份和会话适配 | 复用其能力，补本版产品流程和缺口 | 状态、任务、模块覆盖及失败处理清单 |

“一期已生效”是本次规划前提，不代表本轮已完成上线核验。仅有建表、字段或预留列，不能标记为本版业务能力已完成。研发附件引用的 `account-data-change-phase1.md`、`account-init-four-tables.md` 等配套材料尚未作为完整证据包纳入本项目，需要接收实际交付版。

### 2.2 本版承接全部用户可感知与必要适配

一期只启用默认组，与本版支持多组并不矛盾；新表已有 `parent_id` 预留，也不代表组级配额已经生效。凡涉及新建业务组、多组身份、跨模块权限、分组消费、移交或历史统计的新增行为，均须在本版完成相应接口、鉴权和产品流程。

具体指标来源不足时应留为本版待核验，明确补数、记录新事件、限定历史范围或调整指标的方案。不能把缺失数据当 0，也不能因为第一期没有历史多组数据，就取消目标多组能力。

## 3. 根模型沿用与上次草案修正

### 3.1 沿用已确认目标

- 组织有唯一 Owner、0..N Admin，其余为 Member；组织身份与业务组身份解耦。
- 【2026-11-10 已确认】Admin 采用全组织管理，不配置逐人管理组范围或范围重叠。Admin 可邀请成员、创建组；组织策略另设“Admin 可移除成员”和“Admin 可归档组”，均仅 Owner 可配置、默认关闭。前者控制移出组织及移出某组、撤销尚未完成的单组移除、组织侧确认无业务项的关系结束；不限制有效组长处理既有本组业务交接，不能通过换入口绕过。后者不代表彻底删除组；Owner 不受这两个开关限制，Admin 不能自行开启。全组织管理不授予业务对象权限，其余动作仍按具体矩阵收口。
- 同一账号可加入 1..N 个业务组，每条 GroupMembership 独立保存 T2/T3、状态和可分配配额；每组允许 0..N 个 T2。
- 项目型对象固定归属于一个组，保留唯一业务 Owner；CRM 不建项目容器，同一达人可在不同组分别维护独立业务记录。记录对接人是可空、可转交的业务负责人（Owner/Assignee），达人基础资料共享。
- 全局当前组决定新建对象及无对象业务动作的上下文；已有对象始终按自身稳定组鉴权。
- 不支持跨组协作、跨组直接转交 Owner；项目迁组是独立显式动作。
- 接入协作者体系的对象统一使用 Collaborator，提供模块常规业务读写；不提供只读协作者或通用对象级显式只读 ACL。CRM 是固定例外：无显式或隐式协作者；先校验记录所属组，再沿用现有四项写设置、对接人及空对接人兼容分支，改派沿用同一普通写规则，不受 `t2Collaborator` 控制。正式支付单同组读取及收藏夹既有可见范围按模块规则保留，不改造成通用 Viewer 身份。
- 组织 Owner/Admin 不因管理身份天然获得全部业务明细；`t2Collaborator` 是组织全局策略，默认关闭。开启后，已接入协作对象所属组的全部有效 T2 通过动态系统来源取得普通读写，在协作者列表中锁定勾选展示，不持久写入显式 ACL。关闭、降级或退组只撤销该隐式来源，独立显式协作者及附加能力保留；T2 来源不自动附带 `can_manage_collaborators` 或 `can_execute_payment`。
- 不新增统一模块禁用开关；Scope 类型、组织 Entitlement、可分配上限和对象权限各自判断。
- 组不彻底删除，允许带遗留数据和 REMOVING 成员关系冻结归档；归档须二次确认并说明不可自行恢复，不提供解除归档入口，异常恢复转线下处理。组织始终保留一个有效默认组，默认组不可归档。
- 普通配额允许同父级下子级上限之和超配，执行逐层校验；支付部门资金分配另守资金约束。
- 邮件发送与邮箱解锁沿用现有各入口的预检、落账及复用逻辑，不统一“谁操作扣谁”，也不统一改扣 Owner 或原始创建者。实际 actor 的审计/统计归因与配额核算主体分开，详见 [本轮代码核对](./email_quota_code_evidence_2026-11-09.md)。
- 内容监控保留现有配额语义和各项设置权限，不新增 `can_manage_collaborators` 委派；协作者可维护监控内容及自动追踪，项目治理不随普通读写授予。仅增量接入业务组硬边界与默认关闭的全局组长隐式普通协作；研发实现差异独立核对，不作为合法权限沿用。

## 4. 研发规划需要对齐的差异

| 差异或缺口 | 本版处理要求 |
| --- | --- |
| 附件以一个当前组兼容一期 | 区分“当前组唯一”和“成员关系可多条”；本版补多组切换、请求上下文和缓存隔离 |
| 研发附件保留自有企业 Owner 身份暂停、加入外企后离职恢复的路径 | 已被 §5.3 的本轮确认否决；须回核一期实际交付、登录/邀请接受/会员与离职恢复链路，移除或隔离旧路径，不得将注销中间态视为干净账号。历史审计可保留，但不能恢复有效组织/组身份或跨组织转移业务数据 |
| 资源组可能由旧 `parent/parent_uid` 承载 | 明确逐表映射；产品语义用 groupId，不把旧字段值或 Owner UID 默认视为组 |
| CRM 一期清单主要明确企业归属，未形成完整记录业务组契约；支付表亦主要补企业归属 | 补记录/支付对象稳定组与历史迁移方案，不能只做分组页面而保留企业级越权 |
| 五张项目根表存在 Creator 与 Owner 兼容镜像 | 不承诺这些 Creator 是原始创建者，也不直接用它统计个人历史产出 |
| 部分配额历史在交接中继续改写 UID | 区分额度核算、事件操作人、历史统计归因；不能把兼容 UID 当作不可变 actor |
| 研发按明确接收人、Group Owner、企业 Owner 兜底 | 与同组单一接收人、组织管理员不默认介入业务、CRM 未分配模型对齐；无合法接收人保留责任快照并冻结，不能跨组静默兜底 |
| 研发离职完成可删除组成员关系，Input 用 REMOVED 表达完成 | 产品状态不强制等于一张表的枚举；即使活动关系删除，任务、审计和历史归属必须可查询 |
| 研发交接采用分页、幂等、断点续跑，Input 强调按组原子完成 | Spec 明确准备、执行、最终完成及中途失权，不能把分页副作用描述成已能数据库全量回滚 |
| 附件明确排除精选任务和 TikTok Shop 私信项目的部分离职交接 | 记录为模块覆盖缺口；本版需确认纳入移交还是冻结保留，不能在界面宣称“全部移交” |
| 共享标签、模板、旧 CRM 分组设置与新业务组不同 | 旧 CRM 分组设置暂定弃用，不映射为本版业务组；旧账号组、旧四项写范围和保存筛选条件的自定义视图分别识别。视图不自动删除，标签/模板共享范围另议，禁止因字段名为 group 就自动改范围 |
| 收藏夹旧私有/团队公开/指定成员三模式，数量、单夹容量与联系方式解锁分属不同计量 | 已确认适配为私有/本组公开/指定成员，内容读写与 Owner 专属治理分离，详见 §5.5 及[分层证据](./collection_permission_quota_evidence_2026-11-09.md)。RQ-COL-01/02/03 仍待研发核验，不把新目标或静态代码当作线上已实现 |
| 内容监控普通业务协作、项目治理、标签及配额各自有原规则，预检与用量归集不完全一致 | 保留既有口径，仅增量适配组边界与组长隐式协作；不新增名单管理委派，不用通用改名权限放开治理。RQ-MON-01–05 分别核核算、交接、鉴权、归档和后台链路，见 [监控证据](./monitor_permission_quota_evidence_2026-11-09.md) |
| 退款、冲正和异步消费依赖各自支付/任务链路 | 资金与权限验收覆盖已有承诺、重试和回补；结构预留不能代表已闭环 |

以上是文档对照发现的适配要求，不是本轮已验证的线上缺陷或数据规模结论。

## 5. 统一版本功能范围

下表是同一版本的功能域，不是独立发布期数；优先级用于讨论和开发顺序，不改变闭环义务。

本版不提供组合并；组冻结归档和指定 Owner 名下项目整批迁组仍按各自规则交付。

| 功能域 | 本版交付内容 | 待收口边界 |

| 组织与管理身份 | Owner 迁移、Admin 任免、Admin 全组织管理、组织管理与业务权限分离、管理汇总；Owner-only 的 Admin 移除成员/归档组开关，默认关闭 | 其余完整动作矩阵；不再讨论逐 Admin 分组范围 |

| 业务分组 | 建空组、改名、多组成员、0..N T2、组身份切换、二次确认归档；默认组始终有效且不可归档 | 归档任务与遗留责任的实现；不提供自助解除归档 |

| 项目协作及 CRM 模块权限 | 邮件、收藏夹、内容监控、支付单/草稿接入同组协作；CRM 同达人各组独立业务记录，组内可读，写及改派沿用现有 CRM 规则且不能越过记录组，无协作者或组长隐式来源。收藏夹与内容监控不提供名单管理委派 | 各模块动作与可见范围的实现/迁移验收；CRM 历史归组和关联入口改造留 Spec，收藏夹 RQ-COL-01/02/03、监控 RQ-MON-01–05 不因产品定案自动关闭 |

### 5.1 关键生命周期必须一起成立

- 账号加入目标组时，只迁移指定 Owner 在指定来源组的名下项目，不触及其他 Owner；成员关系建立和迁移任务结果分别展示。
- 项目迁组时，目标组外的显式授权禁用而不删除；成员之后入组满足硬限制时恢复原授权快照，显式永久删除后不再恢复。
- 人员关系的加入、移出单组、组织清退、身份任免及撤销移除在组织侧操作；Admin 发起移出单组或组织清退须满足 Owner 配置的“Admin 可移除成员”开关，默认关闭。组长不主动移出成员，但可处理组织侧产生的本组业务交接，包括组织清退中的本组子任务。人员决定与业务交接按 §5.6 分开，REMOVING 即失去对应范围权限；仅移出单组可由组织侧在最终完成前撤销，组织清退不可撤销。
- 项目留在原组，移交给合法同组接收人；CRM 可以按组批量改派或在最终完成时置为未分配。

### 5.2 支付闭环不再按版本排除

- 支付没有项目容器，协作者绑定每一张支付单/草稿，草稿转正式单延续同一对象身份。Owner/Collaborator 有常规读写；正式单对全部有效同组成员固定可读，不因可读自动授予写权限。草稿仅 Owner 和有效显式/隐式 Collaborator 可见，不向全组开放；全局 `t2Collaborator` 开启时，同组有效 T2 因隐式协作可查看并填写草稿。
- 正式提交、预约和支付者放行需 Owner 或有效 can_execute_payment；T2 系统协作不自动产生执行权。
- 组织钱包是资金总边界；待分配余额不能直接支付，组付款仅使用当前已启用组的专用余额。组织管理者逐笔分配或归还未承诺资金；成员上限由本组组长按 §5.5 配置。启用、充值、关闭、回补和迁移以 §5.8 为准，不提供共享用资选项。
- 正式或预约提交即占用，冻结 `fundingUid`、`fundingGroupId` 和资金来源/启用周期；执行人不替代承担人。移交或项目迁移不改写既有承诺；已占用的款项结算时不重复扣减。
- 组长审核采用已确认的组级策略，默认关闭，不设组织默认值或继承；实时作用于尚未开始实际转账的相关支付单，不按创建时策略快照隔离。多名有效同组组长任一人放行即可；实际提交人在到达闸门时是同组 ACTIVE 组长则豁免，不能用后来变更的单据 Owner 代替实际提交人。
- 立即支付在系统审核通过后等待组长最终放行；手动支付在支付者放行后等待组长最终放行；定时支付在系统审核通过后、预约时点前完成预审核。预约时点未满足系统审核及组长审核条件时进入逾期，不因迟到补审突然自动执行。列表提供“待我放行”、预约提示及带组名的通知；审核权不自动授予 Collaborator 或 can_execute_payment。

### 5.5 配额配置的分层职责（2026-11-03 确认）

- Owner/Admin 按全组织管理权限配置组织内各组的各项可分配配额上限；支付按 §5.8 负责组资金分配和未承诺余额归还。不另设逐 Admin 管理组范围，也不因此取得成员个人额度配置权。
- 本组有效 T2 在既有组织全局 `t2Quota` 委派开关允许时，配置自己及本组 T2/T3 的各项成员额度、执行组内批量增加；不能超出组上限、修改组上限或其他组成员额度。保留该开关及可调整自己/同组成员的既有规则，不因本次分层而撤销。

### 5.6 组织与当前组管理入口（2026-11-04 修订）

- 组织管理包括全局策略、组织成员、业务组治理及组总额度、组织资金和组织移交任务；组长不因业务身份获得这些组织治理入口。
- 当前组管理跟随全局当前组，集中展示本组成员及待处理业务交接，并提供按 §5.5 委派配置组员额度的入口。组长不发起或撤销人员移除；模块私有设置仍留在对应业务模块，不混入全局策略。
- 组织管理者可以管理指定目标组，目标组不必等于其业务当前组；该管理视图不开放个人额度越级编辑。组长管理的当前组则不另设独立的目标组选择器。

| 流程 | 发起入口 / 身份 | 影响与后续 |
|---|---|---|
| 将成员移出组织 | 组织成员行，Owner/“Admin 可移除成员”开启时的 Admin | 全部组及组织业务资格立即失效，不可撤销；接手安排按 §5.7，组长可处理其中本组业务子任务，全部必要交接完成后系统最终清退 |
| 将成员移出某组 | 组织业务组详情的成员行，Owner/“Admin 可移除成员”开启时的 Admin | 仅该组进入 REMOVING，组织身份和其他组保留；组织侧在最终完成前可撤销，Admin 撤销或确认无业务项结束关系仍受该开关约束；业务交接由本组组长处理 |
| 处理本组业务交接 | 当前组业务交接任务，当前组有效组长 | 不依赖由哪个组织管理者发起，包含单组移除及组织清退中的本组子任务；可选择已有同组接收人并完成本组数据交接，不能更改人员移除决定、撤销移除或操作其他组 |

人员移除决定与业务交接可复用影响预检、同组接收、REMOVING/REMOVED 和结果通知，但不能把发起、撤销与业务处理授权混为一谈。组长完成本组业务交接后，由系统按既定移除决定结束相应关系，不是组长另行作出移除决定。任务中心只承接具体成员/组产生的任务，不以两个空泛的“账号 + 来源组”选择框作为主要发起方式。仅移出最后一个有效组时仍可先进入 REMOVING，但完成前须由组织管理者安排另一有效组或走组织清退。

本组业务交接权不依赖 `t2Quota` 配额委派开关，也不依赖任务的原发起人或原发起入口；该开关只控制额度配置。Owner/Admin 若同时为本组有效组长，可按业务身份处理本组交接，不能仅凭组织管理身份逐项分配业务数据。组长不能更改其他组长的成员关系或处理其他组数据。

无有效组长且存在需要人工决策的业务交接项时，等待组织安排业务负责人，不回退为 Admin 逐项分配数据；无业务处理项时可由组织侧确认结束。组织侧仍可看进度、安排负责人及处理人员关系，但不因此取得日常业务明细或改派权限。

本节覆盖 2026-11-03 “组长可主动移出本组组员”及按发起来源限制业务交接的结论；保留组织/当前组入口分区。组长不能邀请或主动移出成员已确认；Admin 移除成员须由 Owner 打开对应组织策略，不改变本组组长既有交接任务的业务处理权。

### 5.7 组织清退的接手路径与组关系继承（2026-11-10 收口）

组织清退保留三条接手路径：邀请新账号完整接替；指定一个已有账号增量接替；清退后由各组组长分别处理数据移交。Owner，或“Admin 可移除成员”开启时的 Admin，可将前两条作为清退中的专用生命周期管理动作直接提交，由系统按组统一执行；这不是日常任意逐项目改派、查看业务内容或编辑订单的权限。第三条仍按 §5.6 由各组长处理本组子任务，无组长且有人工决策业务时等待组织安排业务负责人。

【已确认】【UI交互】前两条不增加确认或审批节点：指定现有接收人并提交清退后，系统自动开始移交；新邀请提交清退并发送邀请后进入 `WAITING_FOR_TARGET`，受邀人接受组织邀请且资格、席位和组关系校验通过后自动开始移交。不要求组长批准、接收人确认接替或操作者另点“确认接替/执行统一移交”；接受邀请是建立组织关系，不是移交审批。提交/执行时的权限、目标资格及范围校验、影响摘要、进度和完成通知继续保留，不能因免去额外确认而跳过。

接替时**只继承组关系，不继承原账号的组长角色**：接收人缺少涉及组的有效关系时，补建关系默认组员；已具备该组关系时，保留接收人自己的组内身份，既不因原账号是组长而自动升级，也不降低接收人原有组长身份。组织身份不随本规则复制。原账号如为某组唯一组长，接替后允许该组暂无组长；任命业务负责人为组长须显式操作，不能用接替自动完成。

【已确认】【UI反馈】业务接替、配额不合并。接收人在某组已有有效关系时，逐 Scope 保留自己的上限配置、已用和占用；缺失组关系按新增默认值建立，普通可分配项为 `inherit`、个人支付上限为 `unlimited`，仍受组织/组上限、组支付启用和余额约束。不复制或相加离职者的个人上限、未用额度、历史用量或支付承担；已失效或退组中的关系不能自动复活。新增默认值可能比离职者原 `capped` 更宽，影响摘要须明确说明；需继续限制时由获委派组长在既有组内配额入口配置，不在移交表单提供 Admin 调额或额外确认勾选。

“收回离职账号配额”仅指收回其继续消费的资格和个人上限配置的生效资格，不是退还已消耗次数、释放既有支付占用或增加组织/组余额。普通个人上限本来不预占父级额度，未用上限不是可划回的资金；旧配置、消耗及占用记录继续留作审计和结算。历史创建人、操作人、用量及既有 `fundingUid/fundingGroupId` 不改写，真实核算字段仍按模块证据和研发契约验证。

前两条整体接替将该离职账号涉及的项目 Owner、CRM 对接人和其他接入对象的有效显式协作关系交给同一个接收人；各组项目/CRM 记录留原组，不触及其他账号的对象，不复制禁用 ACL 或系统派生来源。CRM 没有记录 ACL 可移交，只改对接责任；其他组员仍按有效组身份及既有 CRM 策略计算读写。第三条各组长分别处理时，CRM 仍可另选 0..1 名接收人，未选置为未分配。等待接收人期间不提前改写对象责任；开始执行后按组推进，全部必要交接完成后才最终 `REMOVED`，不能把异步中途成功当成清退完成。

### 5.8 跨境支付资金：仅组专用余额（2026-11-06 确认）

- **资金归属**：组织钱包集中保管，未分到组的可用资金展示为「待分配余额」；它不作为付款资金来源，向组分配时从该余额扣减，不在此裁决提现或注销清理。组的新付款仅使用本组当前启用周期内的专用可用余额，不提供共享资金模式。提交仍须满足对象执行资格、组织钱包、组专用余额和组内账号上限；个人 `unlimited` 只是不额外加个人上限，不能绕过组启用和余额。
- **组启用**：默认组也须显式启用，可一并从已有待分配余额分配资金，也可先不分配；新建组默认未启用、余额为零。启用与充值不绑定。
- **分配主入口**：组织 Owner/Admin 按管理权限进入「组织资金 → 组支付余额 → 分配」，向有效且已启用支付的组分配。无需选择充值记录，实际可分配金额以提交时组织当前待分配余额为准，不按某笔充值建额度批次或计算该笔剩余。
- **充值保持现状**：继续使用既有线下充值流程，不在充值时选择组，不自动划拨；到账成功后资金全部进入组织待分配余额，组余额不变。不新增实时推送或通知中心消息。此前“充值时预选组并一并分配”的表述由本规则替代。
- **到账后页内提示**：有权人员在「组织资金」看到「有新充值到账」，可关闭提示或点「分配到组」打开与主入口同规则的分配表单。资金明细行保持只读，不提供分配操作。仅已确认成功的充值触发该提示；退款、释放、内部归还及其他正金额记录不是充值。关闭只隐藏提示，不改变余额、流水或是否分配；从提示发起的分配成功后处理该提示并新增独立内部划转，不标记该笔充值“全部分配”。提示的持久化及跨人员处理范围留待 Spec。
- **提示中的分配建议**：仅当组织只有一个有效组、且该组是已启用支付的默认组时，才预选它；其他情况需手动选择有效且已启用的组。原充值金额只作为可修改的建议值，既不是上限也不是专属来源；提交仍按当前待分配余额校验。分配记录可选关联该充值的 `recordId` 以便追溯，不要求关联、不约束资金批次。
- **分配和归还记账**：分配、未承诺余额归还均新增不可修改的记录并可追溯来源；不改原流水、不收回已承诺资金，不以普通总额编辑替代归还。组可用余额与组织待分配余额之间的划转不改变钱包实际总资金；充值到账与随后确认的组分配是不同事件，不能重复计为充值。正常归还不是纠错冲正；独立纠错动作及权限仍待细化。
- **关闭、归档、重新开启**：关闭组支付或归档组即禁止新的支付承诺；本周期未承诺的可用余额归还组织待分配，组的可用额归零，既有占用、已付、退款责任和历史流水保留。关闭不等于自动取消订单，旧承诺的结算、符合条件的取消与退款按原流程处理，也不因此授予已失权账号操作资格。重新开启支付开始新的启用周期，初始余额为零，须按新分配获得可用额；不能借重新开启承接旧周期退款或自动恢复原余额。
- **承诺、结算与回补**：创建正式或预约付款时冻结承担人 `fundingUid`、资金组 `fundingGroupId`、资金来源与启用周期；执行/审批人另记。已占用金额结算时从占用转已付，不再用当前组可用额二次扣款。取消、失败释放或退款时，只有原资金组仍有效、仍启用且匹配原周期，才回到该组专用余额；否则回组织待分配。历史事件仍挂原付款和承担快照，不把退款算成当前执行人或新周期的原始支付。
- **存量承诺和使用情况**：上线前已形成的组织钱包承诺按原账务路径继续，不重绑到默认组启用周期、不新扣组余额、不改历史承担人；原组织来源的释放/回补归组织待分配，不流向新启用的组。看板分别呈现组织钱包、待分配、组专用可用/占用/已付及归还/退款来源，内部划转不当作新增充值或消费；口径待正式账本对账。
- **存量切换待定**：旧承诺不受迁移影响；对正在付款的存量组织，上线前另行确认默认组何时启用、首笔专用资金如何获得授权及如何提示，避免无感切换却静默阻断新付款。不能从 Demo 预置启用和初始分配推导生产迁移规则。
- **未决实现口径**：币种、手续费、回调/重试幂等、存量来源缺字段以及账号个人支付上限在退款时的恢复规则仍留待 Spec；不得从组余额回补推导个人限额自动恢复。分配提交时重验组状态和余额，不因曾打开充值记录而冻结组资格或保留余额。未启用时是否同时禁建/禁存草稿是业务入口边界，不因「不能形成资金承诺」自动得出，另行细化。

既有能力证据：此前只读查看 `/payment/history` 的资金明细；本地 `KOLServer` 的 `WalletService.java:81` 显示充值事务更新组织钱包并写成功充值日志，`WalletChangeLogMapper.xml:21` 的明细映射包含 `recordId`、类型、状态及金额。它们是沿用线下到账及识别记录的依据，不代表组织资金页内提示已上线；本轮仅确认规则与本地示意，不改生产充值流程，不新增实时推送或通知中心消息。

本节替代旧“未分配组使用组织共享余额”及双模式方案。完整旧方案仅见 [支付资金备份](./payment_funding_backup.md)，不进入本期实现、验收或用户界面。

### 5.9 项目协作与模块独立规则的核查边界（2026-11-10 补充）

本节记录本轮代码事实、既定目标和待讨论项，不因可实现就自动批准新方案。邀请/清退/建组/任免/组织策略、配额配置、组织资金管理，以及搜索/榜单/详情等通用查询，不放入“项目协作例外”对照；它们仍按本 Input 各自章节交付，不是取消需求。

- **CRM 现状事实**：当前记录 `ownerUser` 表达对接人，读取主要按组织范围，四项写配置为可叠加授权来源；当前单记录没有显式 Collaborator，已有 `viewAuthors` 属于自定义视图治理，不给视图中记录授权。当前普通写权限也能改派，主要按组织 + 平台 + 达人定位记录。以下已确认目标不代表这些旧实现已经适配。见 [静态证据与目标覆盖](./crm_label_code_evidence_2026-11-10.md)。
- **CRM 记录结构已确认，方案 B**：同一达人可在不同业务组分别维护 CRM 业务记录，各自保存对接人和合作状态；达人基础资料仍共享。记录身份必须区分组织、业务组、平台和达人，不因当前操作者或对接人切组而改变。不设显式/隐式 Collaborator、协作者名单或 `can_manage_collaborators`，不受 `t2Collaborator` 开关影响。
- **CRM 权限最终确认，方案 A**：尽量不改线上已闭环的模块权限，只增加记录所属组硬边界。有效同组成员可读；写权限继续使用对接人和组织现有四项设置，四项授权取并集但不能越过记录组，默认值沿用现有配置，不强制全开。当前对接人可写；其他有效同组成员是否可写由原 CRM 策略决定，不能将成员身份本身视为写授权。管理员是 CRM 已配置的存量授权来源，不反向赋予其他模块业务权限。
- **CRM 四项来源不扩张**：权限 1 沿用现有解析出的单个 `adminUid`（无对应子账号管理员时回退父账号），不能直接等同新模型所有 Owner/Admin；权限 2/3 沿用对接人既有组关系的组长/成员来源，不直接改为记录组全体组长/成员。任何来源都先受记录所属组有效身份限制。空对接人配置 `[]/1/2/3` 沿原管理员兜底，包含 `4` 时仅本记录组有效成员全员可写；真实多 Admin、新旧组来源映射留 Spec，不由 Demo 扩权。
- **CRM 对接人及改派沿用现状**：对接人是可空、可转交的记录业务负责人，不是组织 Owner，也不强造项目容器。谁拥有该条记录现行 CRM 普通写权限，谁就能按原流程指派/改派；不额外限定为“当前对接人或组长”，不新增组长独立分工权。空对接人沿用现有管理员兼容分支，并同样先校验记录组；未分配不会向所有组员开放写权限。具体管理动作、候选与字段约束沿现有模块规则核验，不新增 Owner-only 治理。此前“全组读写”“仅对接人/组长改派、空时仅组长指派”均被本条覆盖。
- **CRM 旧设置与实施边界**：四项 CRM 写设置继续生效并保留设置入口，不能与暂定弃用的“旧 CRM 分组设置”混为一谈。旧 CRM 分组不承担新业务组归属；旧账号组、自定义视图与标签定义分别识别，不因此一并删除。D09 核心已定，剩余旧记录初始归组、四项实际来源在组边界内的映射、旧分组入口退出、导入/去重/消息联动/导出及共享基础资料/组内字段边界留 Spec/研发验收；不自动向全部组复制旧记录，不随对接人入组迁移，不宣称加入组边界完全无权限变化。
- **CRM 迁移风险须验收**：未分配记录所在组若没有有效的原解析 CRM 管理员、且配置不含 4，可能无可编辑者；必须在迁移/配置方案中处理，不能静默新增组长首次指派权或允许管理员越过记录组。整体接替也不继承原 CRM 管理员身份；对接人改派后相关旧组来源按既有规则重新计算，不凭“移交”复制权限。
- **标签事实**：内容监控有独立组织标签字典；CRM、消息中心和频道资料卡共用达人标签字典。应按实际共享字典核查政策，不能按页面机械各设一套。定义的可见/共享范围、定义增删改和对业务对象应用/移除已有标签是三类动作，不能由项目协作统一推导；共同字典的变更须检查全部使用入口。
- **标签待讨论**：用户提出的“全组织共享开关 + 非组织共享时仅组长可维护组标签”尚未确认，不新增开关或落成默认行为。它涉及组织标签转组标签、多组引用、历史归属和删改影响；当前监控保持组织共享及默认关闭的定义限制开关继续生效，CRM 标签删除继续独立治理。“暂保留共享范围、仅按标签域细化维护权”也只是建议，不视为本轮新定案。
- **标签研发核验**：当前达人标签实体没有可靠实际创建人/业务组字段，新增时 `uid` 写父账号，不能把它当 `creatorUid`。既定消息标签来源筛选需要补真实创建人和创建时组快照，并核验历史是否可回填；未知历史来源不得用今天所在组倒推。来源筛选不变成标签 ACL，也不开放业务内容。监控标签原 `groupId=1/2/3` 仍是分类而非新业务组。

### 5.10 邮件项目与消息对话：保留现状并增量组隔离（2026-11-10 确认）

本节以 [权限与消息静态核查](./email_message_permission_evidence_2026-11-10.md) 和 [邮件核算证据](./email_quota_code_evidence_2026-11-09.md) 为依据，区分已确认的兼容目标与尚未实测的部署/迁移事实。不把通用协作抽象变成新增业务限制。

- **邮件项目边界**：稳定业务组绑定邮件任务 `kol_email_task`，各轮次 `kol_email_project` 通过 `email_task_id` 继承，不从轮次 UID 或当前操作者反推项目组。负责人和有效正式协作者保留内容/收件人读写与发送；改任务名、删除整任务仍仅负责人且遵循原状态限制。未核实的独立项目说明字段不因通用模型新增。
- **邮件名单管理已收口**：负责人或具有 `canManageMembers=1` 的有效正式协作者可维护名单，名单管理员仍可向其他同组有效正式协作者授予/收回该能力，沿用线上，不新增“只有 Owner 能授予、非 Owner 不可继续授予”的限制。普通协作者与组长隐式来源不自动获得名单管理能力。此为邮件模块例外，不推广到支付执行权或其他模块；收藏夹与内容监控仍不委派名单治理。
- **邮件无日常 Owner 转交**：不提供通用项目主动转交入口；仅在账号级退组、清退和整体接替等既定生命周期流程中交接，具体任务/轮次字段、正式名单与核算映射须研发验收。普通协作者不能因可编辑内容而改任务名。既有 `email[12]` 管理员强制协作按迁移真值承接，不等同于默认关闭的全局组长隐式来源。
- **精确对话与访问来源**：普通邮件对话继承源项目负责人/正式协作者，另保留既有精确对话转交来源；按业务类型、源项目、达人、平台及负责人定位，不能只按组织或达人匹配。默认“沟通中”要求已有回复，但单方成功发信可出现在“建联中/全部”，不能说整个消息中心都只收有回复的邮件串。
- **对话转交不是项目转交**：仅源任务负责人维护 `0..50` 名转交人，可保存空名单全部撤销；候选与保存、实际使用同时限制为源项目组有效成员，排除负责人本人和正式项目协作者。`canManageMembers` 或组织管理身份不增加对话转交管理权；转交不改项目 Owner、正式协作者或项目 ACL，转交人不因此获得整个项目权限，Owner 仍能发送。
- **发件身份保留细分**：普通 Owner/项目协作者默认使用任务 Owner 的发件资源，也可按既有规则显式选择本人可用邮箱；对话转交人须使用自己的授权配置，不静默回退 Owner。站内头像/昵称展示真实操作者，实际发件邮箱及显示名快照另记，Reply-To 继续沿独立配置，不承诺随转交自动改成转交人地址。
- **通知与撤销**：有有效转交人时，普通未读/NIM 提醒路由抑制 Owner、通知转交人，其他项目协作者仍保留提醒；Owner 的发送权不受影响。全部撤销后恢复未来消息的 Owner 跟进路由，不恢复历史未读。其他回复提醒邮件渠道尚未实测，不泛称所有通知均被关闭或恢复。
- **扣量不随授权改写**：已有普通 YJ 对话回复不新增 Scope21；RW2 首次直接联系且无发送历史时仍可能新增一次发送，新邮箱解锁仍可能消费 Scope4，按入口既有资源主体与复用规则处理。普通邮件自动多轮跟进不等同于已有对话回复；本节不关闭 `RQ-MAIL-01/02/03`，不统一改扣 actor、Owner 或创建人。
- **组隔离必须覆盖聚合与旁路**：会话正文、草稿、附件、发送/定时/批量、转交和协作同步之外，达人卡片摘要、最后消息、未读、检索及置顶/星标/归档等状态和批量操作也不得混入其他组。跨项目卡片现有投影需按组适配，具体键/回填/重建方案留 Spec；新服务导入、后台发送、导出及 CRM 联动逐入口验收，不以候选列表加过滤代替完整隔离。
- **Spec／研发保留核验**：隐式组长与现有“正式项目协作者不可同时转交”排斥规则、发件身份优先级须验证，不把隐式来源写入正式名单。退组、清退、整体接替、项目迁组后委派失效及是否恢复、未来提醒回退、历史投影和迟到任务须明确并验收，不套用显式项目 ACL 的恢复规则。真实部署、其他通知渠道和历史身份快照仍未实测；名单管理可再授予已是已确认规则，不再列为待产品决定。
- **【UI交互】【UI反馈】审阅示意边界**：邮件页区分内容读写、Owner 设置和名单管理能力；消息页按精确对话展示来源项目/组、委派名单、Owner 保留发送权及发送身份。本地转交/清空、来信与提醒路由模拟、发送身份预览即可辅助审阅；不真实发信、不扣量，不以完整异步状态机或持久化作为本 Demo 门槛。

### 6.3 指标候选与事实要求

以下是本版需要收口的指标池，不是已经承诺全部可算。最终选择应优先满足管理决策价值、聚星业务完整性和稳定归因，而非界面卡片数量。

| 领域 | 候选内容 | 必须确认的统计语义 |
| --- | --- | --- |
| 邮件与触达 | 触达创作者、发送、打开、回复及相关比率 | 唯一人还是封数、实发身份还是操作人、退信/重试、结果归发送批次还是发生时间 |
| 合作管理 | 新增合作、推进中、合作完成 | CRM 状态、任务/Campaign/合作记录各自含义；不能把有邮件往来等同合作完成 |

### 6.4 归因与数据边界

- 当前资源归属统计、历史业务活动统计和配额核算是三种口径。Owner 交接后资源可计入新负责人当前名下，已发生动作不应伪装成新负责人完成。
- 历史数据没有可靠 actor/组快照时，只在证据支持的组织或对象范围展示；不能用今天所在组回填历史部门业绩。
- 已可靠留存的历史组快照不因成员退组、组归档、项目迁组或 Owner 变化被回写。组织汇总和组汇总如因历史未归属不能对齐，应明确未归属部分。
- 多组账号按事件所属组统计，同一组织汇总去重，不能因账号属于多个组重复累计。
- 组织共享主数据、个人配置与无项目对象的统计维度需逐项确认，不强制所有指标都有 groupId。
- Creator 兼容镜像和会被改写的历史 UID 不作为稳定个人业绩证据；必要时本版开始保存新事件快照，并注明历史起算范围。
- 邮件发送/解锁用量按各入口既有核算主体展示，实际操作人的业务活动另行归因；配额历史 UID、轮次 UID 或任务 UID 不能直接当作稳定 actor，也不按看板操作者重记用量。
- 零记录、接口失败和权限不足分开处理；前端不能用统一返回空数组替代数据状态。
- 当前配额接口和现有模块看板可复用能力需要在目标分支核验；上一轮静态代码观察不代表当前部署事实。本轮未新增线上取数或性能结论。

### 6.5 看板视图和角色范围的待讨论方案（2026-11-10）

以下是继续讨论的组织方式，不是已确认的首版展示矩阵；D10 仍未关闭，现有 Demo 不能反向决定权限范围。

| 视图 | 候选范围 | 不应混淆的口径 |
| --- | --- | --- |
| 本人工作与资源 | 本人实际活动及各组内既有配额核算 | 活动 actor、配额承担账号可能不同；不能用邮件扣量 UID 直接生成个人业绩 |
| 有权参与的项目结果 | 负责人或有效协作者获准项目的整体结果，包括他人协作产生的结果 | 是项目结果，不是当前查看者个人完成量；项目汇总不默认开放其他成员的个人跨项目明细 |
| 组管理汇总 | 组长查看本组汇总及组内成员活动/资源明细 | 既有汇总权不依赖组长隐式协作开关，但不自动开放组成汇总的对象详情；具体指标/历史范围待定 |
| 组织管理汇总 | Owner/Admin 查看组织、各组及成员汇总 | 汇总管理不是业务协作；支付金额等敏感指标及下钻范围需专项确认 |

例如某项目由甲负责、乙和丙分别发送 100/50 封邮件，项目结果为 150 封；不能因为甲负责或丁可协作，就把 150 都计为甲或丁的个人活动。即使既有邮件规则将配额记在负责人链路，活动、项目结果和配额仍分列。可靠 actor 缺失时标明历史未覆盖，不伪造个人归因。现有不回写历史、跨组去重和导出不扩权的边界继续生效。
