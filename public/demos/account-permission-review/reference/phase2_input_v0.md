# 聚星账号体系改造｜一期后统一版本 Input v0

> 更新：2026-10-19。状态：Input 范围重新组织，尚未进入新 Spec。
> 已确认的版本边界：一期完成用户无感知的底层替换；一期之外的遗留需求与新增用户使用情况看板统一组织成一个版本，不再拆成后续二期、三期或 2A/2B/2C 独立版本。
> 文件沿用 `phase2_input_v0.md`，便于继续引用。“二期”若继续用于沟通，仅指一期后的这一个统一版本。
> 需求和规则来源：[原始 Input](./input_v0.md)、[功能设计梳理](./账号和权限功能设计梳理.md)、[Scope 规则](./scope_quota_product_rules.md)、[研发确认](./pm_confirmation_code_evidence_2026-08-18.md)，以及研发附件 `account-system-refactor-final.md` 与 2026-10-15 提供的竞品看板截图。
> 本次确认的是版本组织方式。此前未确认的产品规则仍待确认，历史废案不因此恢复；旧文档的“后续版本/TODO/Backlog”不再自动构成本版排除理由。

## 1. 版本目标和阅读口径

在一期底层替换生效的前提下，把组织事实变成用户能实际使用的完整产品：组织成员管理、业务分组、权限策略、项目协作、普通配额、支付资金限制、成员与数据生命周期，以及按组和账号查看的使用情况看板。

本版闭环是：配置组织与分组 → 引入和分配成员 → 设置能力与配额 → 在业务模块中协作和消耗 → 查看使用与业务结果 → 调整配置、迁移或清退成员 → 保留历史归属与审计。

组织、权限、资金和统计共用同一套企业、组、成员及对象事实。研发可以按依赖并行开发、分模块验收和灰度，但不以独立后续版本承接本版尚未做完的必要环节。

本文使用四类状态：

- **本版交付**：已有目标规则，或属于用户本次明确新增范围；仍需细化 Spec 与实现。
- **本版待确认**：留在本版问题清单中收口，不能解释为已获批的具体方案，也不能直接标成后续版本。
- **回归**：一期或既有实现已覆盖，验证与新组织模型兼容。
- **已否决/历史废案**：只留追溯，不恢复为需求。

## 2. 一期与本版的边界

### 2.1 按一期已生效规划，不重复立项

| 一期承接的基础 | 本版使用方式 | 接收证据 |
| --- | --- | --- |
| 企业、默认组、企业成员和组成员四张基础表 | 从统一组织事实读写组织与业务上下文 | 一期实际交付清单、接口和迁移验收 |
| 业务资源企业归属与已确认的组承载字段 | 用户创建、查看、协作与迁移时使用稳定归属 | 逐表映射与异常清单 |
| 企业权益、会员和旧接口兼容 | 保持套餐归属与组织总额，补组/成员约束 | 权益及配额兼容验收 |
| Owner/Creator 字段适配及兼容约束 | 根据对象模型计算权限，不从字段名称猜身份 | 模块字段语义与兼容白名单 |
| 一期已经交付的离职任务、身份和会话适配 | 复用其能力，补本版产品流程和缺口 | 状态、任务、模块覆盖及失败处理清单 |

“一期已生效”是本次规划前提，不代表本轮已完成上线核验。仅有建表、字段或预留列，不能标记为本版业务能力已完成。研发附件引用的 `account-data-change-phase1.md`、`account-init-four-tables.md` 等配套材料尚未作为完整证据包纳入本项目，需要接收实际交付版。

### 2.2 本版承接全部用户可感知与必要适配

一期只启用默认组，与本版支持多组并不矛盾；新表已有 `parent_id` 预留，也不代表组级配额已经生效。凡涉及新建业务组、多组身份、跨模块权限、分组消费、移交或历史统计的新增行为，均须在本版完成相应接口、鉴权和产品流程。

具体指标来源不足时应留为本版待核验，明确补数、记录新事件、限定历史范围或调整指标的方案。不能把缺失数据当 0，也不能因为第一期没有历史多组数据，就取消目标多组能力。

## 3. 根模型沿用与上次草案修正

### 3.1 沿用已确认目标

- 组织有唯一 Owner、0..N Admin，其余为 Member；组织身份与业务组身份解耦。
- 同一账号可加入 1..N 个业务组，每条 GroupMembership 独立保存 T2/T3、状态和可分配配额；每组允许 0..N 个 T2。
- 项目型对象固定归属于一个组，保留唯一业务 Owner；CRM 使用可空 Assignee，不能因研发字段叫 Owner 就强行改成项目 Owner。
- 全局当前组决定新建对象及无对象业务动作的上下文；已有对象始终按自身稳定组鉴权。
- 不支持跨组协作、跨组直接转交 Owner；项目迁组是独立显式动作。
- 对象协作者统一为 Collaborator，提供模块常规业务读写；模块固定只读范围与附加能力另行表达。
- 组织 Owner/Admin 不因管理身份天然获得全部业务明细；T2 默认协作由组织全局策略控制，默认关闭。
- 不新增统一模块禁用开关；Scope 类型、组织 Entitlement、可分配上限和对象权限各自判断。
- 组不彻底删除，允许带遗留数据和 REMOVING 成员关系冻结归档。
- 普通配额允许同父级下子级上限之和超配，执行逐层校验；支付部门资金分配另守资金约束。

### 3.2 撤回上次草案未经确认的收缩

| 上次草案表述 | 本次处理 |
| --- | --- |
| 多组未验证时先按单组首发 | 撤回。保留多组目标，核验实现和兼容成本 |
| 组长先限制为 0..1 | 撤回。保留已确认的 0..N T2 |
| Admin 默认改为全组织管理 | 撤回默认裁决，回到 Admin 范围与动作矩阵待确认 |
| 邀请接受后自动进入默认组 | 仅作为候选，不能替代“邀请首组是否移除”的决策 |
| 支付、月度配额、组合并另设后续包 | 撤回按版本排除，全部回到统一版本清单 |
| 看板收缩成配额使用页 | 撤回。同时梳理业务活动、业务结果和配额资源三个方面 |
| 任务反馈和最小审计为可裁 P1 | 修正。写配置、资金和迁移所依赖的反馈与审计为必要验收内容 |
| 用上一轮静态代码结果直接描述当前线上 | 修正。证据附日期和验证方式，部署状态需重新核验 |

## 4. 研发规划需要对齐的差异

| 差异或缺口 | 本版处理要求 |
| --- | --- |
| 附件以一个当前组兼容一期 | 区分“当前组唯一”和“成员关系可多条”；本版补多组切换、请求上下文和缓存隔离 |
| 资源组可能由旧 `parent/parent_uid` 承载 | 明确逐表映射；产品语义用 groupId，不把旧字段值或 Owner UID 默认视为组 |
| CRM 一期清单主要明确企业归属，未形成完整记录业务组契约；支付表亦主要补企业归属 | 补记录/支付对象稳定组与历史迁移方案，不能只做分组页面而保留企业级越权 |
| 五张项目根表存在 Creator 与 Owner 兼容镜像 | 不承诺这些 Creator 是原始创建者，也不直接用它统计个人历史产出 |
| 部分配额历史在交接中继续改写 UID | 区分额度核算、事件操作人、历史统计归因；不能把兼容 UID 当作不可变 actor |
| 研发按明确接收人、Group Owner、企业 Owner 兜底 | 与同组单一接收人、组织管理员不默认介入业务、CRM 未分配模型对齐；无合法接收人保留责任快照并冻结，不能跨组静默兜底 |
| 研发离职完成可删除组成员关系，Input 用 REMOVED 表达完成 | 产品状态不强制等于一张表的枚举；即使活动关系删除，任务、审计和历史归属必须可查询 |
| 研发交接采用分页、幂等、断点续跑，Input 强调按组原子完成 | Spec 明确准备、执行、最终完成及中途失权，不能把分页副作用描述成已能数据库全量回滚 |
| 附件明确排除精选任务和 TikTok Shop 私信项目的部分离职交接 | 记录为模块覆盖缺口；本版需确认纳入移交还是冻结保留，不能在界面宣称“全部移交” |
| 共享标签、模板、CRM 自定义分组与新业务组不同 | 逐项确定组织共享/组隔离/个人私有，禁止因字段名为 group 就自动改范围 |
| 退款、冲正和异步消费依赖各自支付/任务链路 | 资金与权限验收覆盖已有承诺、重试和回补；结构预留不能代表已闭环 |

以上是文档对照发现的适配要求，不是本轮已验证的线上缺陷或数据规模结论。

## 5. 统一版本功能范围

下表是同一版本的功能域，不是独立发布期数；优先级用于讨论和开发顺序，不改变闭环义务。

| 功能域 | 本版交付内容 | 待收口边界 |
| --- | --- | --- |
| 组织与管理身份 | Owner 迁移、Admin 任免、组织管理与业务权限分离、管理汇总 | Admin 管理范围和完整动作矩阵 |
| 成员管理与邀请 | 昵称/邮箱检索、组与状态筛选、邀请/接受/撤销、席位反馈、配置摘要 | T2 邀请、邀请首组、待接受时配置变更 |
| 业务分组 | 建空组、改名、多组成员、0..N T2、组身份切换、组归档 | 恢复归档、组合并的动作与数据边界 |
| 普通配额 | 类型化 Scope、组与成员 inherit/capped、三级消费、批量增加、可见性、实际周期与剩余 | Scope 可分配矩阵、月度下级控制、结转与调额 |
| 项目协作 | 邮件、收藏夹、内容监控、CRM、支付单/草稿的同组授权；T2 默认协作策略；附加能力 | 现有各模块动作差异、通用显式只读是否裁掉 |
| 业务责任转交 | 同组 Owner 主动转交、新 Owner 重复 ACL 清理；CRM Assignee 分配和改派 | 原 Owner 留协作者快捷项是否取消；支付仍禁止主动转交 |
| 支付协作与资金 | 正式单同组只读、草稿协作、敏感字段、can_execute_payment、组资金分配、账号上限、占用与冲正 | 账本原子性、币种/手续费、退款、历史身份缺失 |
| 支付审核与收款信息 | 组长审核放行规则、待办/筛选/通知；频道历史收款人组织内复用 | 策略关闭影响、敏感变更、收款信息治理 |
| 成员和资源生命周期 | 加入组、Owner 名下项目整批迁组、ACL 禁用/恢复、退组/移出组织、单接收人整体移交 | 模块对象覆盖、任务原子边界、归档后未完责任 |
| 标签与搜索增量 | CRM 标签删除控制、监控标签定义限制、消息标签来源筛选、联系/合作个人团队范围 | 标签应用与共享范围的模块差异 |
| 使用情况看板 | 组织/组/账号汇总、业务活动和结果、资源配额、趋势及明细 | 指标选择、历史归因、权限、更新周期、导出 |
| 审计与结果反馈 | 配置影响、权限来源、并发版本、迁移任务、重试、摘要、完成通知 | 最小事件范围与保存时间；不扩大成全站审计中台 |

### 5.1 关键生命周期必须一起成立

- 邀请、入组和配额配置形成连续流程，明确成员何时具备有效业务组身份。
- 账号加入目标组时，只迁移指定 Owner 在指定来源组的名下项目，不触及其他 Owner；成员关系建立和迁移任务结果分别展示。
- 项目迁组时，目标组外的显式授权禁用而不删除；成员之后入组满足硬限制时恢复原授权快照，显式永久删除后不再恢复。
- 退组由 Owner/Admin 发起，REMOVING 即失权，允许稍后处理移交；仅退组可撤销，组织移出不可撤销。
- 项目留在原组，移交给合法同组接收人；CRM 可以按组批量改派或在最终完成时置为未分配。
- 组冻结归档允许遗留对象和 REMOVING 关系存在，但不得取消已形成的资金承诺或抹除历史。
- 如果提供“组合并”，必须处理成员去重、T2 身份、Owner/Assignee、显式授权、共享配置、配额、资金和历史统计；本版先确认规则，不用单账号迁组冒充。

### 5.2 支付闭环不再按版本排除

- 支付单与草稿延续同一对象身份；Owner/Collaborator 有常规读写，正式单同组成员固定只读，草稿不向全组开放。
- 正式提交、预约和支付者放行需 Owner 或有效 can_execute_payment；T2 系统协作不自动产生执行权。
- 组织硬上限是钱包当前可用余额；组可以使用未分配共享余额或被逐笔追加分配部门上限，部门分配不得超发；账号默认不追加个人上限。
- 组上限正常操作只增不减；减少走带原记录引用的受控冲正/收回，保留审计。
- 正式提交预约即占用，承担人和承担组使用 fundingUid/fundingGroupId 快照；执行人不替代承担人。移交或项目迁移不改写既有承诺。
- 组长审核采用已讨论的组级策略：多 T2 任一人放行；实际提交人在到达闸门时是同组 ACTIVE T2 则豁免。立即、定时和手动三类时机分别定义，含预约前审核、超时和通知。
- 退款、取消、失败、重试、策略变更与归档后的责任处理必须进入同一验收清单；有待确认项就留在本版收口，不能再写成“只预留结构”。

## 6. 新增用户使用情况看板

### 6.1 目标与参考

管理者需要按组织、业务组和账号了解“做了哪些工作、产生什么结果、用了多少资源”，成员可以查看自己有权查看的数据。参考截图的结构包括数据总览、月度趋势、账号明细，以及邮件、合作、寄样、视频和追踪链接等领域。

截图是需求讨论参考，不直接证明聚星存在对应指标或全量历史数据。本版看板不能被替代成配额页换皮，也不默认复制截图中所有卡片、漏斗、自定义控件和周期选择器。

### 6.2 统一范围与结构建议

- 提供组织/组/账号和统计时间范围；组织管理汇总与业务当前组分开，不因汇总授权直接开放项目详情。
- 总览、趋势和明细共用查询条件；账号和组筛选只返回操作者允许的范围。
- 总览展示少量核心业务活动与结果；趋势选择一个指标或同单位指标对比；明细按账号或组下钻到获准查看的内容。
- 业务统计时间与套餐配额周期分开显示。按月看邮件不等于每月重置额度，也不要求先设计月度配额。
- 指标附定义、统计窗口和更新时间；“真实为零”“尚无记录”“历史未覆盖”“数据延迟”“无权限”和“来源异常”使用不同状态。
- 看板导出纳入本版讨论，限定当前授权范围和指标口径；是否复用通用导出任务在 Spec 确认，不因旧文档的导出专项被后置而一律禁止。

### 6.3 指标候选与事实要求

以下是本版需要收口的指标池，不是已经承诺全部可算。最终选择应优先满足管理决策价值、聚星业务完整性和稳定归因，而非界面卡片数量。

| 领域 | 候选内容 | 必须确认的统计语义 |
| --- | --- | --- |
| 邮件与触达 | 触达创作者、发送、打开、回复及相关比率 | 唯一人还是封数、实发身份还是操作人、退信/重试、结果归发送批次还是发生时间 |
| 合作管理 | 新增合作、推进中、合作完成 | CRM 状态、任务/Campaign/合作记录各自含义；不能把有邮件往来等同合作完成 |
| 寄样与物流 | 寄样、签收、待签收 | 企业物流配置不一定有组，运单/包裹/样品数不同，关联项目与操作者是否可确定 |
| 内容监控 | 新建监控、上线内容、观看和互动 | 新增对象数量、期间增长、当前累计值分别表达；监控操作者不等于内容发布者 |
| 追踪链接 | 创建链接、点击 | 个人短链配置与业务组不天然一一对应；点击去重、时间和归因待确认 |
| 配额与资源 | 各可分配 Scope 使用、上限、剩余、容量占用 | 次数、席位、天数等单位分列；不可分配门禁不伪造剩余量 |
| 支付 | 订单量、支付状态、金额汇总 | 与资金账本对账；币种、手续费、退款、敏感汇总权限独立校验 |
| 成员活动 | 有业务动作的成员及最近活动 | 需要具体事件定义，不能把登录、拥有项目或有 GroupMembership 直接称为活跃 |

### 6.4 归因与数据边界

- 当前资源归属统计、历史业务活动统计和配额核算是三种口径。Owner 交接后资源可计入新负责人当前名下，已发生动作不应伪装成新负责人完成。
- 历史数据没有可靠 actor/组快照时，只在证据支持的组织或对象范围展示；不能用今天所在组回填历史部门业绩。
- 已可靠留存的历史组快照不因成员退组、组归档、项目迁组或 Owner 变化被回写。组织汇总和组汇总如因历史未归属不能对齐，应明确未归属部分。
- 多组账号按事件所属组统计，同一组织汇总去重，不能因账号属于多个组重复累计。
- 组织共享主数据、个人配置与无项目对象的统计维度需逐项确认，不强制所有指标都有 groupId。
- Creator 兼容镜像和会被改写的历史 UID 不作为稳定个人业绩证据；必要时本版开始保存新事件快照，并注明历史起算范围。
- 零记录、接口失败和权限不足分开处理；前端不能用统一返回空数组替代数据状态。
- 当前配额接口和现有模块看板可复用能力需要在目标分支核验；上一轮静态代码观察不代表当前部署事实。本轮未新增线上取数或性能结论。

## 10. 进入 Spec 的条件与整体验收

接下来仍在 Input 阶段逐项确认，本文件不直接充当研发定稿。可以按功能域编写 Spec 章节，但共享同一个版本范围表、权限词汇、状态机、指标字典和验收清单。

- 一期实际交付与本版净新增有明确清单；预留字段、异常数据和未接入模块不被误记为完成。
- 组织管理配置必须在所有本版接入对象和服务端动作生效，不能只完成配置页面。
- 成员进入、换组、离组、移交、归档和资金承诺都有前后状态、影响清单和失败处理。
- 看板用量、业务活动、业务结果和资金汇总各自对齐真实来源；不能以当前责任人覆盖历史操作人。
- 权限扩展、权限收紧和无感兼容分别验收，特别覆盖旧 Admin 强制协作、CRM 范围和支付正式单宽写缺口。
- 本版所有遗留项都有可追溯的“交付/回归/待确认/明确排除”结果；任何后续排除都记录理由和对闭环的影响，而不是预先命名一个第三期承接。
